# Git 규칙

**TL;DR**: `main`은 사용자 전용. Claude는 `claude_*` 브랜치에서 작업. **작업 스코프(루트/프로젝트)별 repo 분리** — 변경 파일 경로로 결정. 모든 병합 `--no-ff` + 병합 전 사용자 승인. Identity는 `김은수 <eunsu.kim@to-doc.com>`, AI 표시(Co-Authored-By 등) 절대 금지.

## 브랜치 모델

| 브랜치 | 용도 | 분기 원점 | 병합 대상 |
|---|---|---|---|
| `main` | 릴리즈 전용 (사용자 직접 관리) | — | — |
| `claude_main` | Claude 측 안정 브랜치 | `main` | `main` (사용자 승인 시) |
| `claude_develop` | 지속 개발 | `claude_main` | `claude_main` |
| `claude_feature_*` | 기능 구현/수정 | `claude_develop` | `claude_develop` |
| `claude_hotfix` | main 긴급 수정 | `claude_main` | `claude_main` + `claude_develop` |

## 브랜치 규칙

> [!CAUTION]
> `main`에 직접 커밋·푸시 **절대 금지**. 사용자가 릴리즈 시점에 직접 관리한다.

- Claude의 모든 작업은 `claude_` 접두사 브랜치에서 수행.
- 기능 개발: `claude_develop`에서 `claude_feature_<설명>` 분기 → 완료 후 `claude_develop`에 병합.
- 안정 병합: 사용자 요청 시 `claude_develop` → `claude_main` 병합.
- 긴급 수정: `claude_main`에서 `claude_hotfix` 분기 → 수정 후 양쪽에 병합.

## 병합 규칙

- **모든 병합은 `--no-ff`** (fast-forward 금지)로 수행. merge commit을 남겨서 이력 보존.
- 사용자가 명시적으로 요청할 때만 커밋 정리(squash/rebase).

## 작업 흐름 (기본: 브랜치 체크아웃)

1. 파일 수정 전, feature 브랜치 생성 후 `git checkout`으로 전환.
2. 작업 완료 후: 커밋 → **사용자 확인** → `--no-ff` 병합 → feature 브랜치 삭제.
3. 커밋 완료 후, 대상 브랜치에 병합하기 전에 **반드시 사용자에게 확인**을 받는다.

> [!IMPORTANT]
> 커밋과 병합은 별개의 단계다. 커밋이 끝났다고 바로 병합하지 말 것.

## 워크트리 (사용자 명시 요청 시에만)

- 사용자가 "워크트리로 작업"이라고 명시한 경우에만 워크트리 생성.
- 디렉토리 이름: `wt_<브랜치명>` 형식.
- 병합 완료 후 워크트리 제거.

> [!WARNING]
> 병합 전에 워크트리를 제거하지 말 것. 커밋 유실 위험.

## 작업 스코프 (Repo 분리)

> [!IMPORTANT]
> **작업이 일어난 디렉토리가 아닌, 변경 파일 경로 기준**으로 어느 repo에 커밋할지 결정한다. 루트(`E:\Claude`)에서 세션을 열고 `projects/<이름>/` 내부를 작업해도, 그 변경은 **해당 프로젝트 repo**에 커밋한다.

### 스코프 판정

| 변경 파일 경로 | 커밋 대상 repo |
|---|---|
| `projects/<이름>/...` 아래 | 해당 프로젝트 repo |
| 그 외 (`docs/`, `tools/`, `CLAUDE.md`, `.claude/memory/` 등) | 루트 repo |

### 혼합 변경 처리

루트와 프로젝트가 한 작업에서 동시에 바뀌면 **각 스코프를 별도 커밋·별도 브랜치**로 분리한다.

1. 루트 측 변경 → 루트 `claude_*` 브랜치에서 커밋·병합
2. 프로젝트 측 변경 → 프로젝트 `claude_*` 브랜치에서 커밋·병합
3. 두 작업 간 의존이 있으면 `tasks/<모듈>/<작업>/`의 `연계` 컬럼·peer link로 표현

### 커밋 직전 체크리스트

- [ ] `git status`로 staged 파일 경로 확인
- [ ] 모든 staged 파일이 **같은 스코프**인지 확인 — 섞여 있으면 `git reset HEAD <파일>` 후 분리
- [ ] 현재 브랜치가 해당 스코프의 `claude_*` 브랜치인지 확인

### 위반 시 복구

| 시나리오 | 복구 |
|---|---|
| 잘못된 repo에 staging | `git reset HEAD <파일>` 후 올바른 repo에서 다시 staging |
| 잘못된 repo에 커밋 (push 전) | `git reset --soft HEAD~1` → 올바른 repo에서 재커밋. 원 repo는 변경 폐기 |
| push 후 발견 | 사용자에게 보고. revert 또는 cherry-pick 필요 — 사용자 판단 |

## 프로젝트별 적용

각 `projects/<이름>/` repo도 동일한 브랜치 모델과 작업 흐름·`--no-ff` 병합·Git Identity 규칙을 독립적으로 적용한다. 프로젝트 고유 사항은 해당 프로젝트 `CLAUDE.md`에 기술.
