# 폴더 구조 및 작업 레지스트리

**TL;DR**: docs/ 폴더는 `지침/`·`tasks/` 2대 카테고리(회고는 지침에 흡수, 사용방법·참고는 Wiki). tasks는 모듈/작업 2레벨 고정, 작업 폴더명은 `YYYYMMDD_<slug>` 날짜 prefix. 표준 산출물 4파일: 요구사항.md·분석.md·계획.md·이력 및 결과.md. 작업 레지스트리는 `list.md`(작업 단위 생애주기)·`모듈 현황.md`(모듈 단위 헬스) 2축.

## 1. 전체 레이아웃

```
docs/
├── 지침/                           영속 — 작업 규칙·컨벤션·검증 체크리스트 (회고 흡수)
│   ├── 작업 규칙.md                (마스터 체크리스트)
│   ├── 일반/
│   │   ├── 문서 작성 규칙.md (인덱스)
│   │   ├── 문서/                  (분할 — 폴더-구조·메타-frontmatter·작성-스타일)
│   │   ├── 작업 진행 규칙.md (인덱스)
│   │   └── 작업/                  (분할 — 4단계-프로세스·완료처리)
│   ├── Git/
│   ├── 코딩/
│   └── (프로젝트 특화 지침)
└── tasks/                          작업 스코프
    ├── list.md                     작업 레지스트리 (작업 단위 생애주기)
    ├── 모듈 현황.md                모듈 인덱스 (모듈 단위 헬스, Wiki sync 진입판단용)
    └── <모듈>/                      작업 폴더 (활성·완료 무관 영구 위치)
        └── YYYYMMDD_<작업슬러그>/  (날짜 prefix — Z-1, 2026-05-18~)
            ├── 요구사항.md
            ├── 분석.md
            ├── 계획.md             (코딩 작업은 구현계획.md alias 호환)
            └── 이력 및 결과.md     (시계열 로그 + 완료 시 요약 추가)
```

> [!NOTE]
> Task α (2026-05-15) 후속 — Package C (2026-05-18): `_modules.md` → `모듈 현황.md`, `이력.md` → `이력 및 결과.md` 명명 변경, 작업 폴더 날짜 prefix 도입, `회고/` 폐지(지침 흡수). `사용방법/`·`참고/`는 **Wiki Vault**로 이전(영속 콘텐츠 단일 출처). `_archive/` 폴더 폐지(작업 폴더 위치 영구).

## 2. 영속 문서 (persistent)

- 유형별 **폴더 이름 자체가 카테고리** 역할. 파일명에 프리픽스 안 붙임
- **지침/** 은 **각 스코프 독립** 영속 폴더:
  - 루트 `지침/` — 전역 공통 지침 (작업 규칙·Git·코딩·일반) + 회고 흡수분 (`maturity: experimental`)
  - 프로젝트 `지침/` — 프로젝트 특화 지침 (예: Sound1 `지침/레지스터 변경 검증 체크리스트.md`)
- **체크리스트·검증 기준은 지침의 하위 유형**이므로 `지침/` 에 직접 배치 (`기준/` 폴더 사용 금지)
- 지침/ 하위는 2레벨까지 허용 (`일반/`, `Git/`, `코딩/`). 그 이상 깊이는 지양 — 단 분할된 거대 지침은 `일반/문서/`·`일반/작업/` 같이 3레벨 OK (2026-05-18~)
- **사용방법·참고**는 **Wiki Vault**(`projects/wiki/사용방법/`·`projects/wiki/참고/`)로 이전. 각 repo `docs/`에서 폐지
- 파일명은 **의미 있는 제목**으로 간결히 (예: `커뮤니케이션 규칙.md`)
- 모든 영속 .md는 frontmatter에 `maturity: core | stable | experimental` 명시 ([`메타-frontmatter.md`](메타-frontmatter.md) §1 참조)

## 3. 작업 문서 (task-scoped)

- 경로: `tasks/<모듈>/YYYYMMDD_<작업슬러그>/`
- **2레벨 고정**: 모듈 아래 바로 작업 폴더. 서브토픽(brightness/dimming/pattern 등)은 폴더가 아닌 **list.md의 태그**로 표현
  - 이유: 3레벨은 경계 판단 애매(한 작업이 복수 서브토픽에 걸침)로 분류 경직화 위험
- 모듈 이름은 **도메인 용어** (루트: `meta`/`git`/`docs`/`tools` 등 / Sound1: `LED`/`touch`/`power` 등)
- 작업 슬러그는 **`YYYYMMDD_<kebab-case>`** 권장 (날짜 prefix 2026-05-18~). 날짜는 작업 시작일. 한글도 허용하되 의미 명확할 때만
- 필수 파일: `요구사항.md`, `분석.md`, `계획.md`, `이력 및 결과.md` (코딩 작업의 `구현계획.md`는 alias로 호환)
- `이력 및 결과.md`는 **단계 ① 시작과 동시에 생성** — 시계열 로그(진행 중 누적) + 완료 요약(종료 시 추가). 상세: [`../작업/4단계-프로세스.md §2`](../작업/4단계-프로세스.md)

## 4. 완료 처리

사용자 *"작업 끝났어. 마무리해"* 시그널 수신 시 다음 절차로 완료 처리한다. **archive 폴더 폐지(2026-05-15~)** — 작업 폴더는 위치 그대로, `list.md` 상태 컬럼으로 완료 표시.

### 4.1 절차

1. **`이력 및 결과.md` 완료 요약 섹션 추가** — 시계열 로그는 진행 중 누적되어 이미 존재 (형식은 §4.2)
2. **`list.md` 갱신** — 단일 표의 해당 행 `상태`를 `완료`로 변경 + `완료일` 기록
3. **`모듈 현황.md` 갱신** — 모듈 인덱스에 작업 반영 ([`../작업/완료처리.md`](../작업/완료처리.md))
4. **커밋 → 사용자 승인 → `--no-ff` 병합**

### 4.2 `이력 및 결과.md` 완료 요약 섹션 형식

`이력 및 결과.md` 본문 골격은 [`../작업/4단계-프로세스.md §2`](../작업/4단계-프로세스.md) 참조. 완료 시 추가되는 `## 완료 요약` 섹션:

```markdown
## 완료 요약

**기간:** YYYY-MM-DD ~ YYYY-MM-DD
**모듈/태그:** <모듈> / <쉼표 구분 태그>
**병합:** `<대상 브랜치>` ← `<작업 브랜치>` (`<merge commit hash>`)
**연계 작업:** → [...](...) (없으면 생략)

### 무엇을 했는가
한 문단. 결과물 중심으로.

### 핵심 결정
- 왜 이렇게 했는지 — 대안 대비 선택 이유 (1~3개)

### 후속 영향
- 추가 작업 / 지침 갱신 등 (없으면 생략)
```

> [!NOTE]
> 작업의 4개 문서(`요구사항.md`/`분석.md`/`계획.md`/`이력 및 결과.md`)는 작업 폴더에 영구 보존. `이력 및 결과.md`의 시계열 로그가 진행 중 모든 결정·이슈를 누적하고, 완료 요약 섹션은 "원본 산출물 들춰볼지 판단하기 위한 1페이지 요약" 역할.

## 5. 작업 레지스트리 — `tasks/list.md`

### 5.1 목적

모든 작업의 **활성/완료 상태**, 모듈·태그, 요약, 연계 관계를 중앙 관리한다. 새 작업 시 기존 작업 맥락을 한눈에 확인. 작업 단위 생애주기 추적.

(`모듈 현황.md`와 차원이 다름: list는 작업 단위, 모듈 현황은 모듈 단위 헬스 스냅샷)

### 5.2 파일 구조 (단일 표)

```markdown
# 작업 목록 (tasks index)

## 작업 목록

| 작업명 | 모듈 | 태그 | 상태 | 시작·완료 | 폴더 | 연계 | 요약 |
|---|---|---|---|---|---|---|---|
| ... | ... | ... | 진행 | YYYY-MM-DD | [...](...) | → [...](...) | ... |
| ... | ... | ... | 완료 | YYYY-MM-DD ~ YYYY-MM-DD | [...](...) | - | ... |

## 상태 정의

| 상태 | 의미 |
|---|---|
| `진행` | 작업 진행 중 |
| `대기` | 선행 조건 충족 대기 |
| `차단` | 외부 요인으로 진행 불가 |
| `완료` | 병합·릴리즈 완료 |
| `취소` | 작업 취소 |

## 갱신 이력

| 날짜 | 이벤트 |
|---|---|
```

### 5.3 컬럼 정의

| 컬럼 | 내용 | 예 |
|---|---|---|
| 작업명 | 사람이 읽을 수 있는 작업 이름 | `docs 폴더 구조 세분화` |
| 모듈 | 도메인 구분 (폴더명과 일치) | `meta`, `LED`, `touch` |
| 태그 | 쉼표 구분 서브토픽·특성 키워드 | `docs, convention` |
| 상태 | `진행` / `대기` / `차단` / `완료` / `취소` | `진행` |
| 시작·완료 | `YYYY-MM-DD` (진행 중) 또는 `시작~완료` (완료 후) | `2026-04-24` 또는 `2026-04-24 ~ 2026-04-27` |
| 폴더 | 작업 폴더 상대 링크 (날짜 prefix 포함) | `[meta/20260518_docs-architecture-rebuild](meta/20260518_docs-architecture-rebuild/)` |
| 연계 | 다른 작업 peer 링크 (symmetric), 없으면 `-` | `→ [LED/20260420_pwm-tune](../LED/20260420_pwm-tune/)` |
| 요약 | 1줄 요약 (25자 이내 권장) | `계층·list·태그 도입` |

### 5.4 갱신 이벤트 (자동 동기화 대상)

| 이벤트 | 동작 |
|---|---|
| 작업 시작 (폴더 생성 시) | `list.md` 작업 목록에 행 추가 (상태=`진행`) |
| `이력 및 결과.md` 시계열 로그 갱신 | 해당 행의 `상태`·`요약` 업데이트 (필요 시) |
| 사용자 `작업 끝났어. 마무리해` 시그널 | (1) `이력 및 결과.md` 완료 요약 추가 → (2) `list.md` 행의 `상태`를 `완료`로 변경·`완료일` 기록 → (3) `모듈 현황.md` 해당 모듈 행 갱신 ([`../작업/완료처리.md`](../작업/완료처리.md)) |

### 5.5 새 작업 라우팅 절차

사용자가 새 작업을 지시하면 Claude는:

1. 해당 스코프의 `tasks/list.md` 조회
2. 같은 모듈·태그의 관련 작업이 있으면 사용자에게 확인:
   > **"기존 `<폴더>`에서 이어가시겠어요, 신규로 분리하시겠어요?"**
3. 확인 답변대로 기존 폴더 재사용 또는 신규 폴더 생성 (신규는 `YYYYMMDD_<slug>` 날짜 prefix)
4. 신규 생성 시 `list.md` 활성 섹션에 등재

## 6. 모듈 인덱스 — `tasks/모듈 현황.md`

### 6.1 목적

**모듈 단위 헬스 스냅샷**. 모듈별 최종 업데이트·작업 수·최근 작업을 한눈에. Wiki sync 등 외부 소비자가 본 파일만 읽어 마지막 sync 시점 이후 변경된 모듈 식별.

list.md(작업 단위 생애주기 추적)와 차원이 다름. 둘 다 유지가 정답(통합 시 정렬 모순).

### 6.2 갱신 트리거

작업 종료 처리 시 자동 갱신 — [`../작업/완료처리.md`](../작업/완료처리.md) 참조.

## 7. Cross-module 연계 표현

### 7.1 peer-to-peer 링크

- 작업 A가 작업 B의 결과에 의존하거나 기능적으로 얽힐 때 사용
- 각 행의 `연계` 컬럼에 상대 작업 마크다운 링크 (양쪽 symmetric하게 서로 참조)
- 예:
  - A: `→ [LED/20260420_pwm-tune](../LED/20260420_pwm-tune/)`
  - B: `→ [debug/20260418_rtt-ext](../debug/20260418_rtt-ext/)`

### 7.2 feature 태그

- 3개 이상 작업이 하나의 상위 기능을 구성할 때 사용
- 공통 태그 `feature:<이름>` 을 모든 관련 작업에 부착
- 예: `feature:auto-dim` 태그로 LED·sensor·comms 작업 묶어 식별

### 7.3 두 방식은 병행 가능

| 상황 | 방식 |
|---|---|
| 2개 peer 관계 | 연계 링크 |
| 3개 이상 feature 그룹 | feature 태그 |
| 둘 다 | 연계 링크 + feature 태그 |

### 7.4 upgrade 경로 (현 단계 미도입)

feature 규모가 커져 공통 아키텍처·요구사항 문서가 필요해지면 `docs/features/<기능명>/` 폴더 도입 후 `list.md`에서 해당 feature 태그로 집계. 지금은 YAGNI로 미도입.
