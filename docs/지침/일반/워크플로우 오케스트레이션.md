# 워크플로우 오케스트레이션

**TL;DR**: `Workflow` 도구가 없는 세션에서도 일반 `Agent` **다중 동시 호출 + 본 지침**으로 동적 오케스트레이션을 재현한다. 핵심은 4대 패턴(parallel·pipeline·loop-until-dry·adversarial-verify), 검증 루프(단계 ④ 연동), fan-in 컨텍스트 예산이다. **도구가 아니라 작업 패턴**이라 모델·effort와 무관하게 적용된다. 단발·병렬 기본 규칙은 [`서브에이전트 활용.md`](서브에이전트%20활용.md)가 규정하고, 본 지침은 그 위의 다노드 오케스트레이션을 다룬다.

## 1. 개념 — 도구가 아니라 패턴

`Workflow` 도구는 특정 모델·모드에서만 호출 가능하지만, 그 핵심 가치(여러 서브에이전트를 구조적으로 엮어 병렬·검증·반복 수행)는 **`Agent` 도구를 한 응답에 여러 개 묶어 호출**하는 것으로 근사할 수 있다. 본 지침은 그 근사 규칙을 정의한다.

- 단발 위임의 임계치·프롬프트 자기완결성·타입 선택은 [`서브에이전트 활용.md`](서브에이전트%20활용.md)가 규정한다. 본 지침은 그 위에서 **여러 노드를 엮는 오케스트레이션**을 다룬다.
- 메인 세션은 **오케스트레이터(orchestrator)** 역할로, 노드를 spawn하고 결과를 fan-in(수렴)·합성한다.

## 2. 4대 오케스트레이션 패턴

| 패턴 | 트리거 조건 | Agent 다중 호출 매핑 | 수렴·실패 처리 |
|---|---|---|---|
| **parallel** (배리어) | 서로 독립인 N개 작업 — 모든 결과가 한꺼번에 필요 | 의존 없는 `Agent` 호출 N개를 **한 응답에 묶어** 동시 기동 | 전 노드 완료까지 대기. 한 노드 실패는 누락 처리·나머지로 진행. 결과 병합 규칙 명시 |
| **pipeline** (단계 의존) | 단방향 stage 의존(앞 결과 → 다음 입력) | stage별 순차 `Agent` 호출, 직전 결과를 다음 프롬프트에 핸드오프 1줄로 전달 | stage 실패 시 해당 아이템 드롭. `Agent`는 호출당 완결 반환이라 **stage 경계는 항상 배리어**(허용 손실) |
| **loop-until-dry** (반복) | 미지 규모 탐색(버그·이슈·엣지케이스) — 발견이 마를 때까지 | 큐가 빌 때까지(또는 K회 연속 무수확) 오케스트레이터가 노드 재spawn | **종료조건·무한루프 상한 필수**(기본 3회). 반복 사이 잔여 큐는 구조화 상태객체로 전달(§4) |
| **adversarial-verify** (교차검증) | 산출물의 진위·정합성을 독립 검증 | 2차 노드(`Explore`)가 1차 산출물을 **반증 시도**. 다수결·합의 집계 | 과반 반증 시 기각. judge-panel(N개 독립 판정 + reducer 집계)은 이 패턴의 특수형 |

**보충**:

- parallel은 [`서브에이전트 활용.md §2.2`](서브에이전트%20활용.md) "의존 없으면 무조건 병렬"과 1:1 일치한다.
- 동시 호출 수는 과도하게 늘리지 말고(컨텍스트·관리 비용), 작업 규모에 비례시킨다. "간단한 확인"은 소수, "철저한 감사·리뷰"는 다수 + 검증 패스.

## 3. 검증 루프 오케스트레이션 (단계 ④ 연동)

[`작업/4단계-프로세스.md`](작업/4단계-프로세스.md)의 **단계 ④ 구현·처리** 직후 검증을 오케스트레이션으로 수행한다.

1. **검증 fan-out**: 빌드·테스트·회귀·스타일(또는 문서 작업이면 broken link·grep 잔존·번호 일관성) 검증자를 **`Explore` 서브에이전트로 병렬 기동**한다.
2. **수렴(fan-in)**: 각 검증자는 결론만 구조화 반환(§4), 오케스트레이터가 reducer로 합산한다.
3. **검증 루프**: 실패 항목이 있으면 **단계 ④ 구현으로 루프백**해 수정 후 재검증한다.
   - 수정이 **계획 변경(재설계)**을 유발하면 단계 ③으로 돌아가 **계획 재승인**([`계획 모드 자동 진입.md`](계획%20모드%20자동%20진입.md))을 받는다.
   - 단순 버그·오류 수정이면 재승인 없이 구현 ↔ 검증 루프만 반복한다.
4. **상한**: 검증 루프 반복은 **기본 3회**까지. 3회 내 수렴 실패 시 추가 진행하지 않고 은수님께 에스컬레이션한다.
5. **수렴 종결**: 전 검증자 PASS 시 완료 처리([`작업/완료처리.md`](작업/완료처리.md))로 진입한다.

> [!NOTE]
> **검증 정의 이원화** — 코드 작업의 검증은 빌드·테스트 PASS, 문서·메타 작업의 검증은 broken link 0·grep 잔존 0·단계 번호 일관성이다.

## 4. fan-in 컨텍스트 예산 (폭발 방지)

다수 노드를 병렬 기동하면 결과 fan-in 지점에서 컨텍스트가 선형 폭발할 수 있다. 다음을 강제한다.

- **노드 반환 상한**: 각 노드는 **결론 위주 최대 3줄(200자)** 구조화 반환 — (1) 핵심 결론, (2) 근거 `파일경로:라인`, (3) 다음 노드·오케스트레이터용 핸드오프 1줄. raw 로그·전체 파일 인용·중간 사고과정은 메인으로 **전파 금지**.
- **오케스트레이터 합성**: 노드 raw 결과를 본문에 재인용하지 않고 **통합 결론만** 합성한다.
- **reducer 1단**: 노드 수가 많으면(가변·다수) 중간 집계 서브에이전트(reducer)를 한 단 더 두어, 메인으로 올라오는 양을 **상수로 묶는다**.
- **loop 상태 예외**: loop-until-dry의 반복 노드는 잔여 큐·검증 결과를 담은 **구조화 상태객체** 반환을 허용한다(3줄 강제의 예외 — 상태 전달이 목적).

> fan-in 예산은 [`서브에이전트 활용.md §2.3`](서브에이전트%20활용.md)에 정본이 있다. 본 §4는 오케스트레이션 맥락의 요약이며, 근거는 [`컨텍스트 절약 규칙.md`](컨텍스트%20절약%20규칙.md) 파일 재출력 금지 원칙을 노드 산출에도 동일 적용하는 것이다.

## 5. read-only / 쓰기 fan-out 경계 (승인 게이트 정합)

동적 워크플로우는 4단계 프로세스에 **기본 흡수**된다(별도 키워드 불요). 단 단계 ③ 계획 승인 게이트와의 충돌을 막기 위해 경계를 둔다.

- **read-only fan-out(조사·분석·검증 탐색)**: 단계 ①~② 에서 **승인 전에도 상시 허용**한다. `Explore` 등 읽기 전용 노드로 영향 범위·가설을 병렬 조사하는 것은 승인 게이트에 저촉되지 않는다.
- **쓰기 fan-out(구현)**: 파일을 **수정·생성하는 노드의 병렬 기동은 단계 ③ 계획 승인 이후**(단계 ④)에만 허용한다.
- 즉 "분석은 마음껏 병렬, 손대는 건 승인 후"가 원칙이다.

## 6. 동시성 주의 (병렬 쓰기 충돌)

- `Agent` 다중 호출은 병렬 쓰기 충돌을 **자동으로 막아주지 않는다**.
- 따라서 쓰기 fan-out 시에는 **각 노드에 서로 다른 파일·디렉토리를 할당**해 충돌을 절차적으로 회피한다(같은 파일을 두 노드가 동시에 수정하지 않게).
- 동일 파일을 여러 관점에서 고쳐야 하면 병렬 대신 pipeline(순차)으로 전환한다.
