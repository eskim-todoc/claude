# 서브에이전트 활용

**TL;DR**: 모든 작업에서 서브에이전트를 **되도록 가능한 최대로 활용**한다. 병렬 처리(독립 작업 동시 실행)와 처리 효율(광범위 탐색·다중 가설 분석·대용량 로그 처리)이 1차 목표. 컨텍스트 격리는 부수 효과. 한 응답에 multiple Agent 호출로 병렬 처리하고, 명확한 역할별 서브에이전트 종류(`Explore`/`general-purpose`/`Plan`)를 골라 자기완결적 프롬프트로 위임한다. **default는 활용** — 단순 단일 lookup만 예외, 의심스러우면 무조건 활용.

## 1. 적용 범위와 강도

| 항목 | 내용 |
|---|---|
| 적용 범위 | **모든 작업** — 코딩·문서 작성·분석·메타·조사 등 차이 없이 |
| 활용 강도 | **되도록 가능한 최대로 활용**. 단순 위임이 아닌 first-class 도구로 |
| 우선 고려 | 작업 계획 수립 시(단계 ①·②·③) "서브에이전트로 분리·병렬화 가능한 부분이 있나?"를 **반드시** 점검 |

> [!IMPORTANT]
> 서브에이전트는 비용·지연이 있으므로 **단일 lookup·소량 작업에는 부적합**. 그 외 모든 경우는 **활용이 default**. "쓸지 말지" 판단의 default는 **활용 쪽**이며, 의심스러우면 **무조건 활용**한다 (2026-05-18 Package C 후속 강화).

## 2. 활용이 적합한 작업 패턴

### 2.1 작업 패턴별 매핑

| 작업 패턴 | 활용 |
|---|---|
| 광범위 코드베이스 탐색 (3+ 검색) | `Explore` 위임 |
| 한 키워드·심볼 단일 lookup | 직접 `Grep`/`Glob` |
| 다중 가설 분석 (root cause 3개+) | 가설별로 `general-purpose` 병렬 |
| 독립적인 멀티 파일 변경 | 파일군별 분리 가능하면 분기 위임 |
| 대용량 빌드/테스트 로그 분석 | `general-purpose`에 로그 경로 + 분석 지시 |
| 외부 정보 조사 (웹·문서) | `general-purpose` |
| 설계·계획 수립 | `Plan` (구현 시작 전 별도 계획 검토 받을 때) |
| 단순 반복 작업 (frontmatter 일괄 추가 등) | `general-purpose`에 명확한 지시 위임 |

### 2.2 병렬 호출

서로 독립적인 서브에이전트 호출은 **한 응답에 multiple Agent 호출**로 병렬 처리한다.

```
한 응답:
  Agent(subagent_type=Explore, prompt=...)  ← LED 모듈 탐색
  Agent(subagent_type=Explore, prompt=...)  ← Touch 모듈 탐색
  Agent(subagent_type=general-purpose, ...) ← 빌드 로그 분석
```

> [!TIP]
> 의존성이 있는 작업(앞 결과를 다음 입력에 사용)은 순차로. 의존성 없으면 **무조건 병렬**.

### 2.3 fan-in 컨텍스트 예산

다수 노드를 병렬 기동한 결과를 메인으로 모을 때(fan-in) 컨텍스트가 폭발하지 않도록 통제한다.

- **노드 반환 상한**: 각 노드는 결론 위주 **최대 3줄(200자)** 구조화 반환 — (1) 핵심 결론, (2) 근거 `파일경로:라인`, (3) 다음 노드·오케스트레이터용 핸드오프 1줄. raw 로그·전체 인용·사고과정은 메인으로 전파 금지.
- **reducer 1단**: 노드 수가 많으면(가변·다수) 중간 집계 서브에이전트(reducer)를 한 단 더 두어 메인 유입량을 상수로 묶는다.
- **loop 상태 예외**: 반복(loop-until-dry) 노드는 잔여 큐·검증 결과를 담은 구조화 상태객체 반환을 허용한다(3줄 강제의 예외 — 상태 전달이 목적).

> [!NOTE]
> 다단계 fan-out·검증 루프·반복을 구조적으로 엮는 **동적 오케스트레이션 4패턴**(parallel·pipeline·loop-until-dry·adversarial-verify)은 [`워크플로우 오케스트레이션.md`](워크플로우%20오케스트레이션.md)에서 규정한다.

## 3. 서브에이전트 종류

| 종류 | 용도 | 도구 권한 |
|---|---|---|
| `Explore` | 읽기 전용 빠른 검색·코드 위치 파악 | 읽기·검색만 |
| `general-purpose` | 다단계 조사·실행·복합 작업 | 전부 |
| `Plan` | 구현 계획 설계 (코드 작성은 안 함) | 읽기·검색·계획 출력 |

> [!NOTE]
> 작업의 권한 범위에 맞춰 가장 좁은 서브에이전트를 선택한다 (불필요한 권한 부여 금지).

### 3.1 기본 모델·Effort

Agent 호출 시 `model`과 `effort`를 **항상 명시** 한다. 세션 모델(Opus 등)과 무관하게 아래 기본값을 사용한다.

| 항목 | 기본값 | 비고 |
|---|---|---|
| `model` | `"sonnet"` (최신 Sonnet) | 비용 절감·속도. 세션이 Opus여도 서브에이전트는 Sonnet |
| `effort` | `"high"` | extended thinking 활성화로 판단 품질 보장 |

작업 특성상 다른 tier가 **명확히** 맞을 때만 예외 — 단순 기계적 작업은 `"low"`, 최고 난도 설계는 `"xhigh"`.

## 4. 좋은 프롬프트 작성

### 4.1 자기완결성

서브에이전트는 본 대화 컨텍스트를 **모른다.** 프롬프트에 다음을 반드시 담는다:

- 무엇을 하려는지(목적)
- 이미 알고 있는 사실·시도해본 것
- 출력 형식·길이
- 관련 파일 경로·심볼명 등 단서

### 4.2 짧은 응답 강제

- 회신 분량을 미리 제한 — "보고는 200자 이내"·"표 5행 이내" 등
- 구체적 산출물 형식 지정 — "각 가설별 ✅/⚠️/❌ 표시"

### 4.3 판단 위임

- "찾아라"보다 "판단해라" — 단순 lookup이라면 직접 도구 사용이 더 빠름
- 서브에이전트의 가치는 **그 대신 생각해주는 것**

## 5. 안티패턴

| 안티패턴 | 문제 | 대안 |
|---|---|---|
| 단일 lookup 위임 | 오버헤드 > 절감 | 직접 `Grep`/`Read` |
| 같은 검색을 본인이 다시 검증 | 중복 비용·신뢰 부족 | 결과 신뢰. 의심되면 더 구체적인 후속 질문 |
| 좁은 명령형 프롬프트 | 서브에이전트가 맥락 부족으로 부실 답변 | 자기완결 프롬프트 (§4.1) |
| 결과 무시·재검색 | 컨텍스트 낭비 | 결과를 받아 그대로 다음 단계에 사용 |
| 중복 병렬 호출 (같은 작업 분할 X) | 결과 일관성 손상 | 한 작업은 한 서브에이전트에 |
| **서브에이전트 사용 회피 (직접 진행)** | 메인 컨텍스트 폭발 + 병렬 기회 손실 | **의심스러우면 활용** — default가 활용 |

> [!NOTE]
> **adversarial-verify 예외**: 위 "같은 검색을 본인이 다시 검증"·"결과 무시·재검색"의 재검증 금지는 **무계획적 중복 재실행**(같은 작업을 의심만으로 다시 돌리는 것)에 한정된다. **사전 설계된 독립 검증 노드**가 다른 에이전트의 산출물을 교차검증·반증하는 것(adversarial-verify·judge-panel, [`워크플로우 오케스트레이션.md §2`](워크플로우%20오케스트레이션.md))은 금지 대상이 아니라 **권장**된다. 단계 ④ 검증이 이에 해당한다.

## 6. 작업 진행 4단계와의 통합

| 단계 | 서브에이전트 활용 |
|---|---|
| ① 요구사항 분석 | 보통 사용자 의도·맥락 정리 — 서브에이전트보다 직접 |
| ② 현상태 분석 | **광범위 탐색 시 최대로** — 코드베이스/문서 grep, 영향 범위 식별 |
| ③ 구현·처리 계획 | 복잡한 설계는 `Plan` 위임 가능 |
| ④ 구현·처리 | 독립 변경 분리·테스트 로그 분석·반복 작업 위임 등 |
