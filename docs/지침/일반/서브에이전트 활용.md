# 서브에이전트 활용

**TL;DR**: 모든 작업에서 서브에이전트를 전면 활용한다. 오케스트레이터(메인 세션)는 대화 맥락 파악·위임 프롬프트 설계·결과 합성 등 자기 컨텍스트 확보(§1.1)만 직접 수행하고, 사용자에게 전달되는 실제 작업 산출물은 규모·난이도 불문 전량 `Workflow` 도구의 Sonnet 서브에이전트(effort 항상 `max`)에 위임한다. 호출 불가 세션에서만 한 응답에 multiple Agent 호출로 폴백한다(effort 미보장). 명확한 역할별 서브에이전트 종류(`Explore`/`general-purpose`/`Plan`)를 골라 자기완결적 프롬프트로 위임한다. 전면 위임 정책(은수님 2026-07-03 승인).

## 1. 적용 범위와 강도

| 항목 | 내용 |
|---|---|
| 적용 범위 | **모든 작업** — 코딩·문서 작성·분석·메타·조사 등 차이 없이 |
| 활용 강도 | **전면 위임** — §1.1 예외 외 실제 작업은 전량 위임. 단순 보조가 아닌 유일 경로 |
| 우선 고려 | 작업 계획 수립 시(단계 ①·②·③) "서브에이전트로 분리·병렬화 가능한 부분이 있나?"를 **반드시** 점검 |

> [!IMPORTANT]
> **전면 위임 정책** (은수님 2026-07-03 승인): 서브에이전트는 비용·지연이 있지만, 이 비용은 의도적으로 감수한다. "쓸지 말지" 판단 자체가 폐지되었다 — §1.1의 예외를 제외한 모든 실제 작업은 규모·난이도 불문 위임이 유일한 경로다.

## 1.1 오케스트레이터 자기 컨텍스트 확보 (유일한 예외)

전면 위임의 유일한 예외는 오케스트레이터가 위임을 설계하기 위해 필요한 최소 행위뿐이다. 아래 4가지 외에는 예외가 없다.

1. **대화 맥락 파악** — 사용자 요청·이전 대화 내용 이해
2. **위임 설계용 최소 조사** — 어떤 파일·심볼이 관련 있는지 훑어 위임 프롬프트를 자기완결적으로 작성하기 위한 조회
3. **오케스트레이션 관리 행위** — `git status`/`git log`, 작업 폴더·목록 조회, 커밋 등 작업 진행 관리
4. **fan-in 결과 합성** — 서브에이전트 결과를 받아 통합·보고

4단계 프로세스의 ①요구사항·③계획 설계 산출물 작성은 §6 표가 이미 "오케스트레이터 직접"로 규정한다 — 본 예외와 별개 근거로 유지된다.

> [!CAUTION]
> 위 4가지 외로 예외를 확대 해석하지 않는다. 판단이 애매하면 위임 쪽으로 기운다 (§5 안티패턴 참조).

## 2. 활용이 적합한 작업 패턴

### 2.1 작업 패턴별 매핑

| 작업 패턴 | 활용 |
|---|---|
| 광범위 코드베이스 탐색 (3+ 검색) | `Explore` 위임 |
| 오케스트레이터 자기 컨텍스트 확보용 단일 조회 (§1.1 예외) | 직접 `Grep`/`Glob` |
| 사용자에게 전달되는 답변을 위한 조회·조사 (단일 lookup 포함) | Sonnet 서브에이전트 위임 (Workflow, effort: max) |
| 다중 가설 분석 (root cause 3개+) | 가설별로 `general-purpose` 병렬 |
| 독립적인 멀티 파일 변경 | 파일군별 분리 가능하면 분기 위임 |
| 대용량 빌드/테스트 로그 분석 | `general-purpose`에 로그 경로 + 분석 지시 |
| 외부 정보 조사 (웹·문서) | `general-purpose` |
| 설계·계획 수립 | `Plan` (구현 시작 전 별도 계획 검토 받을 때) |
| 단순 반복 작업 (frontmatter 일괄 추가 등) | `general-purpose`에 명확한 지시 위임 |

### 2.2 병렬 호출

서로 독립적인 서브에이전트 호출은 병렬 처리한다. **Workflow 가용 시 `workflow()`에 병렬 노드로 정의**하고, 호출 불가 세션에서는 **한 응답에 multiple Agent 호출**로 폴백한다.

```
Workflow(우선): parallel([ agent({...}), agent({...}), agent({...}) ])
Agent(폴백): 한 응답에
  Agent(subagent_type=Explore, prompt=...)  ← LED 모듈 탐색
  Agent(subagent_type=Explore, prompt=...)  ← Touch 모듈 탐색
  Agent(subagent_type=general-purpose, ...) ← 빌드 로그 분석
```

> [!TIP]
> 의존성이 있는 작업(앞 결과를 다음 입력에 사용)은 순차로. 의존성 없으면 **무조건 병렬**.

### 2.3 fan-in 컨텍스트 예산

다수 노드를 병렬 기동한 결과를 메인으로 모을 때(fan-in) 컨텍스트가 폭발하지 않도록 통제한다.

- **노드 반환 상한**: 각 노드는 결론 위주 **최대 3줄(200자)** 구조화 반환 — (1) 핵심 결론, (2) 근거 `파일경로:라인`, (3) 다음 노드·오케스트레이터용 핸드오프 1줄. raw 로그·전체 인용·사고과정은 메인으로 전파 금지.
- **reducer 1단**: 노드 수가 많으면(가변·다수) 중간 집계 서브에이전트(reducer)를 한 단 더 두어 메인 유입량을 상수로 묶는다.
- **loop 상태 예외**: 반복(loop-until-dry) 노드는 잔여 큐·검증 결과를 담은 구조화 상태객체 반환을 허용한다(3줄 강제의 예외 — 상태 전달이 목적).

> [!NOTE]
> 다단계 fan-out·검증 루프·반복을 구조적으로 엮는 **동적 오케스트레이션 4패턴**(parallel·pipeline·loop-until-dry·adversarial-verify)은 [`워크플로우 오케스트레이션.md`](워크플로우%20오케스트레이션.md)에서 규정한다.

## 3. 서브에이전트 종류

| 종류 | 용도 | 도구 권한 |
|---|---|---|
| `Explore` | 읽기 전용 빠른 검색·코드 위치 파악 | 읽기·검색만 |
| `general-purpose` | 다단계 조사·실행·복합 작업 | 전부 |
| `Plan` | 구현 계획 설계 (코드 작성은 안 함) | 읽기·검색·계획 출력 |

> [!NOTE]
> 작업의 권한 범위에 맞춰 가장 좁은 서브에이전트를 선택한다 (불필요한 권한 부여 금지).

### 3.1 기본 모델·Effort

서브에이전트는 세션 모델(Opus 등)과 무관하게 `model: "sonnet"`(최신 Sonnet)으로 호출하고, effort는 전면 위임 정책에 따라 **항상 `"max"`** 를 지정한다(도구가 effort 지정을 지원할 때). 지정 가능 여부는 사용하는 도구에 따라 다르다.

| 경로 | model | effort | 비고 |
|---|---|---|---|
| **Workflow** `agent({...})` (1차) | `"sonnet"` | **`"max"`** (실제 적용, 항상) | extended thinking 최대 보장. 난이도별 차등(low/high/xhigh)은 전면 위임 정책(2026-07-03)으로 폐지 |
| **Agent 도구** 다중 호출 (폴백) | `"sonnet"` | **지정 불가** (인자 부재) | 세션 기본값 상속 → 로그에 `Agent-폴백(effort 미지원)` 명시 |

> [!IMPORTANT]
> **`Agent` 도구 스키마엔 `effort` 인자가 없다.** `effort: "max"`를 *실제로 보장*하려면 `Workflow` 도구의 `agent({model, effort})`를 써야 한다(Workflow opt-in standing 승인: 은수님 2026-06-18 / 전면 위임·effort 항상 max 승인: 은수님 2026-07-03). Workflow 호출이 불가한 세션에서만 `Agent` 다중 호출로 폴백하며, 이때 effort는 세션 기본값을 상속한다(미보장). 적용 모델·effort는 에이전트 로그에 기재한다 — Workflow는 `Sonnet · max`, 폴백은 `Sonnet · Agent-폴백(effort 미지원)`.

## 4. 좋은 프롬프트 작성

### 4.1 자기완결성

서브에이전트는 본 대화 컨텍스트를 **모른다.** 프롬프트에 다음을 반드시 담는다:

- 무엇을 하려는지(목적)
- 이미 알고 있는 사실·시도해본 것
- 출력 형식·길이
- 관련 파일 경로·심볼명 등 단서

### 4.2 짧은 응답 강제

- 회신 분량을 미리 제한 — "보고는 200자 이내"·"표 5행 이내" 등
- 구체적 산출물 형식 지정 — "각 가설별 ✅/⚠️/❌ 표시"

### 4.3 판단 위임

- "찾아라"보다 "판단해라" — 위임 프롬프트에 조사뿐 아니라 판단·결론까지 요구한다. 단일 lookup도 예외 없이 위임 대상이므로(§1.1) "직접이 더 빠르다"는 이유로 위임을 회피하지 않는다
- 서브에이전트의 가치는 **그 대신 생각해주는 것**

## 5. 안티패턴

| 안티패턴 | 문제 | 대안 |
|---|---|---|
| 같은 검색을 본인이 다시 검증 | 중복 비용·신뢰 부족 | 결과 신뢰. 의심되면 더 구체적인 후속 질문 |
| 좁은 명령형 프롬프트 | 서브에이전트가 맥락 부족으로 부실 답변 | 자기완결 프롬프트 (§4.1) |
| 결과 무시·재검색 | 컨텍스트 낭비 | 결과를 받아 그대로 다음 단계에 사용 |
| 중복 병렬 호출 (같은 작업 분할 X) | 결과 일관성 손상 | 한 작업은 한 서브에이전트에 |
| **실제 작업을 오케스트레이터가 직접 처리 (§1.1 예외 초과)** | 전면 위임 정책 위반 + 메인 컨텍스트 폭발 + 병렬 기회 손실 | 규모·난이도 불문 위임. §1.1 4가지 예외 외에는 예외 없음 |

> [!NOTE]
> **adversarial-verify 예외**: 위 "같은 검색을 본인이 다시 검증"·"결과 무시·재검색"의 재검증 금지는 **무계획적 중복 재실행**(같은 작업을 의심만으로 다시 돌리는 것)에 한정된다. **사전 설계된 독립 검증 노드**가 다른 에이전트의 산출물을 교차검증·반증하는 것(adversarial-verify·judge-panel, [`워크플로우 오케스트레이션.md §2`](워크플로우%20오케스트레이션.md))은 금지 대상이 아니라 **권장**된다. 단계 ④ 검증이 이에 해당한다.

## 6. 작업 진행 4단계와의 통합

| 단계 | 서브에이전트 활용 |
|---|---|
| ① 요구사항 분석 | 보통 사용자 의도·맥락 정리 — 서브에이전트보다 직접 |
| ② 현상태 분석 | **광범위 탐색 시 최대로** — 코드베이스/문서 grep, 영향 범위 식별 |
| ③ 구현·처리 계획 | 복잡한 설계는 `Plan` 위임 가능 |
| ④ 구현·처리 | 독립 변경 분리·테스트 로그 분석·반복 작업 위임 등 |
