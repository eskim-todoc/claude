# 코드 분석·디버깅 규칙

> [!IMPORTANT]
> 코드 분석 / 회귀 디버깅 / root cause 추정 작업에서 **검증되지 않은 추정으로 fix 하지 않기** 위한 규칙. 본 문서의 사례는 모두 실제 발생한 회귀 (Sound1 LED 잔상색 작업 2026-04-23) 에서 도출된 것이다.

---

## 1. 호출 경로는 추정 금지 — 반드시 `Grep` 으로 확인

### 규칙

함수가 어디서 호출되는지를 분석할 때 "이 함수는 main loop 에서만 호출된다", "이 변수는 ISR 에서 안 쓴다" 같은 추정을 금지한다. **항상 `Grep` (또는 동등 도구) 으로 호출처 / 사용처 전수 확인** 후 분석을 진행한다.

### 체크리스트

- [ ] 함수 호출 분석 시 `Grep -rn "func_name\("` 로 모든 호출처 확인
- [ ] 변수 사용 분석 시 `Grep -rn "var_name"` 로 모든 read/write 위치 확인
- [ ] ISR 핸들러 (`*_IRQHandler`) 가 직간접적으로 같은 함수를 호출하는지 별도 확인
- [ ] 호출 경로 그래프를 머릿속에서만 그리지 말고 텍스트 / Mermaid 로 명시

### 안티패턴 (실제 사례)

> **Sound1 LED 잔상색 작업**: `led_arbiter_tick()` 이 main loop 에서 호출된다고 가정하고 분석. 실제로는 `TIMER_3_IRQHandler` / `CFX_0_IRQHandler` / `FIFO_5_IRQHandler` 3 개 ISR 에서 직접 호출되어, main loop break 후 `func_sleep()` 진행 중에도 LED GPIO 가 갱신됨. 사용자가 IRQ 경로를 지적한 후에야 발견.

→ **첫 단계 분석에서 `Grep led_arbiter_tick` 한 줄이면 5 분 안에 확인 가능했음.**

## 2. Root cause 가설은 최소 3 개 수립 후 cross-check

### 규칙

회귀 / 버그 분석 시 **가설 1 개가 그럴듯해 보여도 즉시 fix 하지 말 것.** 최소 3 가지 가설을 수립하고 각각의 근거 / 반증을 검토한 후 가장 확실한 것을 선택한다.

### 체크리스트

- [ ] 가설 A / B / C 후보 명시 (1 개로 만족 금지)
- [ ] 각 가설의 **근거** (이 가설이 맞다면 어떤 증거가 있어야 하는가) 명시
- [ ] 각 가설의 **반증** (이 가설이 틀리다면 어떤 증거가 있어야 하는가) 명시
- [ ] 사용자에게 진단 정보 (RTT 로그, 동작 영상 등) 요청해 좁힐 수 있으면 우선 요청
- [ ] fix 적용 전 "이 fix 가 진짜 root cause 를 다루는가?" self-check

### 안티패턴 (실제 사례)

> **Sound1 LED 잔상색**: 첫 분석에서 `turnOffLED()` 의 GPIO 순차 LOW 처리 transient 만 root cause 로 결정 → fade-out fix 적용 → 사용자 재검증에서 잔상 그대로 → 두 번째 시도 (cross-fade Phase B) → 세 번째 (ISR 호출 경로) 까지 점진적 발견. 사용자가 3 회 검증 부담.
>
> 첫 분석에서 가설 다음 모두 검토했어야:
> - (A) GPIO 순차 LOW transient
> - (B) cross-fade Phase B 가 새 색을 LED_outputColor 에 주입
> - (C) ISR 에서 led_arbiter_tick 호출
> - (D) tdc_led_set_ind_state 잔존
>
> 그러면 첫 fix 에서 (B) + (C) 도 같이 처리했을 것.

## 3. 사용자가 직접 수정한 변경은 그 자체가 단서

### 규칙

system-reminder 등으로 "사용자가 파일을 수정했다" 알림이 오면, **그 변경의 의도를 깊이 분석한다.** 추가된 변수명 / 코멘트 / include / 함수 호출 위치 모두 사용자가 무언가를 인지하고 추가한 흔적이다. 그 인지 내용이 현재 작업과 연결될 가능성을 우선 검토한다.

### 체크리스트

- [ ] 사용자가 추가한 식별자 (변수 / 함수 / 매크로) 의 이름이 무엇을 시사하는가 분석
- [ ] 사용자가 추가한 코멘트가 어떤 부작용 / 위험을 인지했음을 시사하는가 분석
- [ ] 그 변경이 현재 회귀와 어떻게 연결되는지 가설 수립
- [ ] 그 변경을 무시 / 되돌리지 말 것 (system-reminder 가 명시: "변경은 의도적, 되돌리지 말 것")

### 안티패턴 (실제 사례)

> **Sound1 LED 잔상색**: 사용자가 `s_led_isr_suspended` 플래그를 추가하고 코멘트에 "ISR 에서 engine/LED_OUT 을 일시 정지" 라고 명시. 이는 **"ISR 이 LED 를 건드리는 경로가 있다"** 는 결정적 단서였음. 그러나 그 단서를 분석에서 활용 못 하고 GPIO transient 만 의심.
>
> 사용자가 깨달은 것 = 코드의 진실. 그 단서를 첫 분석에서 활용했으면 즉시 ISR 경로를 grep 했을 것.

## 4. 시스템 상태 시점 변화 명시 추적

### 규칙

전원 / 클럭 / IRQ / GPIO / 공유 변수 등의 **상태 변화 시점을 명시 추적**한다. "main loop break 후" / "PMIC OFF 후" / "클럭 변경 후" 같은 전환 시점이 회귀 가설 후보의 핵심.

### 체크리스트

- [ ] 분석 대상 함수 / 시퀀스의 시점별 상태를 표 / 타임라인 / Mermaid 로 시각화
- [ ] 각 시점에 어떤 IRQ 가 발생 가능한지 명시
- [ ] 전원 / 클럭 변경 시점 별도 강조
- [ ] "이 시점에 X 가 변경되면 어떻게 되는가?" 가설 추가

### 안티패턴 (실제 사례)

> **Sound1 LED 잔상색**: `func_sleep()` 진입 후 `ResetNRF / NRF_Off / QCC SHUTDOWN / FPGA SLEEP / PMIC OFF / turnOffLED / ci_power_sleep / ci_timer_init_prescaled` 진행 동안 IRQ 가 발생할 가능성을 무시. main loop break = LED 동작 정지 라고 잘못 가정.

## 5. 새 코드베이스 작업 시 핵심 구조 우선 파악

### 규칙

새로운 코드베이스 / 새 모듈 작업 시 **본격 분석 전에 다음 4 가지 핵심 구조를 우선 파악**한다:

1. **IRQ 핸들러 구조** — 어떤 IRQ 가 어떤 함수를 호출하는가
2. **main loop 구조** — 어떤 함수가 어떤 주기로 호출되는가
3. **전원 / 클럭 상태 머신** — 모드 전환 시점 / 영향
4. **데이터 흐름** — 모듈 간 통신 (예: CFX↔CM3, BLE↔CM3, ISR↔main)

### 체크리스트

- [ ] `Grep "IRQHandler"` 로 IRQ 목록 파악
- [ ] `Grep "main_loop|while \(1\)"` 로 main loop 구조 파악
- [ ] 전원 / 클럭 함수 (`*_power_*`, `*_clock_*`) 파악
- [ ] CLAUDE.md / README / 분석 문서가 있으면 우선 읽기

## 6. fix 적용 전 self-check

### 규칙

fix 를 적용하기 전, 사용자에게 보고하기 전에 다음 5 개 질문에 명시적으로 답한다:

| Q | 내용 |
|---|---|
| Q1 | 이 fix 가 진짜 root cause 를 다루는가? 증상 완화가 아닌가? |
| Q2 | 다른 가설은 모두 배제되었는가? 각각의 반증 근거는? |
| Q3 | 회귀 위험이 있는 코드 경로는? (이 함수의 다른 호출자, 의존하는 모듈) |
| Q4 | 부작용으로 인한 새 버그 발생 가능성은? |
| Q5 | 사용자에게 진단 정보를 요청하는 게 더 정확하지 않은가? |

### 체크리스트

- [ ] 위 Q1~Q5 모두 답변
- [ ] 답변이 "추정 / 모름" 이면 fix 보류, 진단 정보 요청 우선
- [ ] fix 적용 후 사용자가 검증할 수 있는 체크리스트 (RTT 로그, 동작 시나리오) 같이 제공

## 7. 빠른 진행 vs 검증의 균형

### 규칙

Auto mode 라도 **사용자가 "철저히", "확실히" 같은 표현을 쓴 작업** 은 검증 단계를 더 두텁게 한다. 빠른 fix 1 회 보다 정확한 fix 1 회가 사용자 시간 절약.

### 체크리스트

- [ ] 사용자 요청에 "철저히" / "확실히" / "신중히" 같은 표현이 있으면 분석 단계 강화
- [ ] 회귀 위험이 있는 작업은 사용자 진단 정보 요청을 우선 (점진적 fix 보다)
- [ ] 같은 회귀를 여러 번 fix 하게 만들지 말 것 (사용자 검증 부담 = 큰 비용)

---

## 8. 적용 범위

본 규칙은 **모든 코드 분석 / 디버깅 / 회귀 fix 작업** 에 적용한다. 단순 오타 수정 / 설정값 변경에는 적용 안 함.
