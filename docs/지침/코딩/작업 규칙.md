# 프로그래밍 작업 규칙

**TL;DR**: 일반 [`작업 진행 규칙`](../일반/작업%20진행%20규칙.md)의 4단계 프로세스를 코딩 작업에 적용. 코드 작성은 단계 ④. 단계 ③의 산출물 `계획.md`가 곧 구현 계획. 코딩 특화 산출물(시험방법·사용방법)·`tdc_` 접두어 등이 추가로 적용된다.

## 1. 일반 규칙 상속

본 문서는 [`일반/작업 진행 규칙.md`](../일반/작업%20진행%20규칙.md)을 상속한다. 4단계 프로세스·산출물·자체 검토·진행상황·이력의 일반 규칙은 그대로 적용되며, **본 문서는 코딩 작업의 추가·특화 사항만 다룬다.**

> [!IMPORTANT]
> 코드 작성은 단계 ④(구현·처리)에 해당한다. 단계 ①~③의 산출물(`요구사항.md`·`분석.md`·`계획.md`)을 작성하고 사용자 승인을 받기 전에는 **코드를 작성하지 않는다.**

## 2. 코딩 작업의 4단계 매핑

| 일반 단계 | 코딩 작업 시 |
|---|---|
| ① 요구사항.md | 무엇을 구현할지·기능 범위·인터페이스·검증 기준 |
| ② 분석.md | 현행 코드 구조·호출 경로·영향 모듈·회귀 위험 |
| ③ 계획.md | 변경 파일·함수·새 심볼·구현 순서 (기존 `구현계획.md`도 호환) |
| ④ 구현 | 코드 작성·빌드·시험. 필요 시 `시험방법/`·`사용방법/` 추가 산출 |

## 3. 코딩 특화 산출물

| 문서 | 조건 | 배치 |
|---|---|---|
| `시험방법/<...>.md` | 시험 절차·기준 정의 (영속) | `docs/시험방법/` |
| `사용방법/<...>.md` | 사용자 명령 입력·CLI 등 사용법 안내 (영속) | `docs/사용방법/` |

> [!NOTE]
> 작업 범위가 큰 기능이거나 외부에서 재현할 수 있도록 절차가 필요한 경우, 단계 ④ 구현 도중 또는 직후에 작성한다.

## 7. 학습 노트 (2026-05-18 회고 흡수)

> [!NOTE]
> 2026-05-18 Package C 이전에는 `docs/회고/코딩.md`에 별도 누적. 이제는 본 파일에 흡수.

### 7.1 비차단/ISR 기반 시스템에서 동기 블로킹 폴링 회피 (2026-04-27) *(maturity: stable)*

이벤트/ISR 기반 서브시스템(LED, timer, 통신 등)에 새 함수 추가 시 `for { step(); delay_ms(1); }` 형 동기 블로킹 폴링 구현을 회피한다. 호출자는 즉시 return, ISR이 매 tick step을 진행하는 상태머신 패턴을 우선 적용한다.

**Why:** 사용자는 LED 시스템을 *"메인 코어가 LED 처리에 갇히지 않는"* 비차단 ISR 기반으로 설계함. Claude가 LED `operation-scheme` 작업 중 `turnOffLED` / `led_force_fade_off` 를 30/40 ms 동기 폴링으로 구현 — 게다가 ISR을 `s_led_isr_suspended = true`로 멈춰놓고 직접 폴링하는 거꾸로 된 구조가 됨. 후속 `LED/non-blocking-fade-off` 작업에서 ISR 상태머신 변환 + 잠재 버그 자연 해소.

**How to apply:**
- 비차단/ISR 기반 서브시스템에 fade·전환·sequence 형 함수 추가 시: **호출자 즉시 return + ISR step 진행** 패턴 우선
- 폴링이 필요해 보이는 케이스: **즉시 완료 분기** 또는 **ISR 활성 여부 검사 후 분기**로 처리, 폴링 fallback 도입 회피
- "단순화 위해 폴링" 충동 시 자가 점검: 호출자 측 main loop가 그 시간 동안 무엇을 진행할 수 있는지 먼저 분석
- 설계 의도가 모호하면 구현 전 사용자에게 명시 확인 (*"이 함수 동기 폴링 vs ISR step, 어느 쪽?"*)

### 7.2 Peripheral 클럭 체인을 시스템 클럭과 동일시하지 않기 (2026-04-30) *(maturity: experimental)*

Cortex-M MCU의 peripheral (Timer/ADC/DMA/I2C/UART 등)은 시스템 클럭 직결이 아니라 분주된 sub-clock (SLOWCLK, ADCCLK, UCLK 등) 기반인 경우가 많다. peripheral의 reload·timing 매개변수는 SDK 헤더의 클럭 체인 주석/공식을 먼저 확인한 후 계산한다.

**How to apply:**
- Peripheral의 reload·timing 매개변수 계산 전: SDK 헤더의 클럭 체인 주석·공식 (`T = ... / N kHz` 등) 확인. 시스템 클럭 직결 가정 ❌
- ISR 기반 신규 모듈을 부트로더/minimal context에 추가 시: 기존 코드의 클럭 분주 설정 (`D_CLK->CFG_*` 또는 동등)을 함께 가져와야 함
- 클럭 분주 설정 후 안정화 대기 (`delay_ms(5)` 등) 도 동반
- 측정 시 ISR 주기/PWM 주기가 의도와 배수 (4배, 24배, 32배 등 분주 비율) 차이로 어긋나면 **클럭 체인 의심 1순위**

### 7.3 환경 변경 단서가 있을 때 코드 결함보다 환경 가설 우선 검증 (2026-05-07) *(maturity: stable)*

사용자가 신고와 함께 **환경 변경**(보드 교체·전원·온도·펌웨어 버전 등) 단서를 흘리면, 코드 결함 가설보다 **환경 트리거 가설을 우선 검증**한다.

**How to apply:**
- 1차 신고에 환경 변경 단서(보드·시제품·전원·온도·펌웨어 버전 변경 등)가 있는지 먼저 스캔. 있으면 환경 가설을 가설 A로 두고 코드 가설은 B/C로
- 코드 분석으로 *"이 조건에서 이 증상이 나오려면 무엇이 trigger 되어야 하는가"*까지 도달했을 때, 그 trigger가 환경 변화로 발생할 수 있는지 먼저 검토
- 정확한 코드 동작 분석을 사용자에게 보고할 때는 *"이 동작이 의도된 건가요? 환경에 따라 영향 받을 수 있는 구조"*식으로 환경 가능성을 같이 제시
- 분석·디버깅 규칙 §3 ("사용자가 직접 수정한 변경")의 확장: 사용자가 언급한 환경 차이도 동일한 우선 단서로 취급

### 7.4 디버그 트레이스 출력 함수로 `ci_printe` 회피 (2026-05-06) *(maturity: experimental)*

시점 측정·버퍼 dump 등 디버그 트레이스 목적 출력에는 `ci_printe` 대신 `ci_printw` (워닝) 또는 `ci_printi` (정보)를 사용한다. `ci_printe`는 출력 시 파일·함수·줄번호 prefix가 자동 prepend되는 구조라 메시지 본문이 메타데이터에 묻혀 가독성이 떨어진다.

**How to apply:**
- 디버그 트레이스 (시점 측정·버퍼 dump·milestone 박스 등) 신규 추가 시 `ci_printw` 또는 `ci_printi` 우선 선택. `ci_printe` 회피
- 정상 에러 보고는 기존 `ci_printe` 보존
- 출력 함수 선택 기준: 워닝(비정상이지만 recovery 가능) → `ci_printw`, 정보 milestone → `ci_printi`, 의미적 에러 → `ci_printe`

### 7.5 검증 도구를 코드 변경과 같은 commit에 포함 (CI 없는 환경) (2026-05-08) *(maturity: stable)*

CI/CD 파이프라인이 없는 단일 개발자 환경에서 형식·인터페이스 변경을 commit할 때, **그 변경을 검증할 수 있는 자동 검증 도구를 같은 commit에 포함**한다.

**How to apply:**

- 형식·인터페이스·외부 계약(API/CLI/파일 포맷) 변경 시 `tests/test_<변경명>.py` 동시 작성
- 검증 도구 요건:
  - **일관된 진입점** — `python tests/test_X.py` 한 명령으로 실행
  - **명확한 종료 코드** — 0=PASS, 1=FAIL
  - **자체 cleanup** — 임시 산출물 종료 시 제거 + `.gitignore`로 안전망
  - **결정론적 비교 기준** — 기존 정답과 바이트·해시 단위 동일성
- 검증 도구가 의존하는 *입력 데이터*도 같은 commit에 포함
- 사용자에게 머지 승인 요청 시 *"검증 N/N PASS"* 한 줄 보고

### 7.6 doxygen `/** ... */` 주석 안에 `*/` 시퀀스 금지 (2026-05-07) *(maturity: experimental)*

doxygen 또는 일반 블록 주석 (`/* ... */`) 본문에 `*/` 문자 시퀀스가 들어가면 거기서 주석이 일찍 닫히고 그 뒤 텍스트가 코드로 해석되어 줄줄이 문법 에러가 발생한다. C는 nested block comment를 지원하지 않는다.

**How to apply:**
- doxygen 또는 블록 주석 본문에 `*/` 시퀀스 금지. `*`와 `/` 사이에 **공백 1칸** 두거나 표현 자체를 바꿈
- glob/regex 패턴 인용 시: `snd_boot_*`와 `/...` 분리 (예: `snd_boot_* / ...`), 또는 `snd_boot_<suffix>` 같이 plain으로
- 에러 진단 단서: 주석 시작 라인이 정상으로 보이는데 그 직후 첫 함수 시그니처에서 *"unknown type name"*/*"expected '=' before"* 류 에러가 줄줄이 나오면 **주석 안 `*/` 시퀀스 의심 1순위**

### 7.7 RTT 출력 누락 시 측정 환경 1순위 의심 (2026-05-06) *(maturity: experimental)*

펌웨어 디버그 트레이스가 *코드 흐름상 호출되어야 하는데* 누락되면 "코드가 그 라인에 도달 못 했다" 가설로 분기하기 전에 **RTT 채널 throughput 한계**를 1순위로 의심한다. 짧은 시간에 다량 출력 시 (수백 byte/ms) 저속 RTT (예: 400 kHz)에서 byte drop 발생, 줄 단위 누락처럼 보임.

**How to apply:**
- 디버그 트레이스 출력 누락 발견 시 첫 의심 = **RTT 측정 환경 (속도, buffer 크기)** — 코드 분석 전 RTT 속도 한 단계 올려서 재측정
- 짧은 시간에 다량 출력 (수백 byte/수 ms)가 예상되면 **처음부터 RTT 1000 kHz 이상** 사용
- RTT buffer (보통 1024 B)가 main thread의 ci_print 출력 + ISR 출력으로 동시 압박될 때 drop 가능
- RTT 출력 누락 = 코드 도달 실패라는 결론은 **RTT 속도 변경 후에도 누락 재현** 시에만 내릴 수 있음
