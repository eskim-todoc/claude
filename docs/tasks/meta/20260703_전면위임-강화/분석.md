## 3. 가설·선택지

### 3.2 선택지 (설계 결정)

**쟁점: "전면 위임"의 경계를 어떻게 정의할 것인가?**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 선택지_1: 문자 그대로 전면 — 오케스트레이터는 어떤 도구도 직접 호출 금지 | 규칙이 단순·모호함 없음 | 실행 불가능 — 위임 프롬프트를 짜려면 최소한의 조사가 필요하고, 세션 시작 시 CLAUDE.md를 직접 Read해야 하는 다른 core 규칙과 충돌 |
| 선택지_2: "오케스트레이터 자기 컨텍스트 확보"만 예외, 나머지 100% 위임 (채택) | 실행 가능 + 은수님 의도("일을 어떻게 하면 최선인지 설계하는 데 중점, 진짜 작업은 서브에이전트")와 정확히 일치 | 경계선 판단에 재량이 남음 — 남용 방지 위해 §5 안티패턴에 명시적 서술 필요 |
| 선택지_3: 파일 크기·작업 시간 임계치로 예외 정의(예: 1파일·30초 이내는 직접) | 정량적이라 판단 쉬움 | 은수님이 명시적으로 거부한 "규모별 차등"(전면 위임 vs 지침 기본값 유지 양자택일에서 전자 선택)과 배치 |

**결정: 선택지_2 채택.**

**쟁점: effort 기본값을 항상 `max`로 고정할 때, `low`/`high`/`xhigh` 구분을 완전히 삭제할 것인가?**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 선택지_1: `low`/`high`/`xhigh` 옵션 자체를 문서에서 언급 삭제, `max` 고정만 서술 | 명확 | Workflow 도구 자체는 여전히 5단계 effort를 지원 — 향후 재조정 시 옵션 존재를 몰라 재조사 필요 |
| 선택지_2: `max`를 기본값으로 명시하되, 옵션 표는 참고용으로 축소 유지 (채택) | 정책(항상 max)과 도구 능력(5단계 존재) 양쪽 정보 보존 | 표가 한 줄 늘어남 (경미) |

**결정: 선택지_2 채택** — `서브에이전트 활용.md` §3.1 표에 "effort 항상 `max`(정책)"를 1행으로 명시하고, 도구가 지원하는 다른 값(`low`~`xhigh`)은 각주 수준으로 축소.

## 4. 핵심 결정

- 결정_1: **§1.1 "오케스트레이터 자기 컨텍스트 확보" 신설** — `서브에이전트 활용.md`에 정본을 두고, 예외 범위를 4가지로 열거(대화 맥락 파악·위임 설계용 최소 조사·오케스트레이션 관리 행위(git status/log 등)·fan-in 결과 합성). 4단계 프로세스의 ①③ 설계 산출물 작성은 기존 §6 표가 이미 "직접"로 규정하고 있어 재정의 불요, §1.1에서 상호 참조만 추가
- 결정_2: effort는 Workflow 경로에서 **항상 `max`** — 난이도별 차등(low 단순 작업·high 기본·xhigh 최고난도)을 정책적으로 폐지. 근거: 은수님이 "지침 기본값 유지"가 아닌 "전면 위임 + 항상 max"를 명시적으로 선택(비용·지연 트레이드오프 인지 후 결정)
- 결정_3: 본 작업의 단계 ④(4개 문서 실제 개정)는 **신설되는 정책을 즉시 자기 적용** — 오케스트레이터가 정확한 before/after 텍스트를 설계(본 분석·계획 문서에 확정)하고, 실제 파일 Edit 실행은 `Workflow` 도구로 Sonnet 서브에이전트(4개 파일 병렬, `effort: "max"`)에 위임. Package C 계열 선행 작업들의 "신 정책 첫 자기 적용" 관례와 일치
- 결정_4: `작업 목록.md`의 `20260609_워크플로우-오케스트레이션-이식` 상태 정정(진행→완료)은 본 작업 완료 처리 단계에서 함께 반영(별도 작업 분리 불필요 — 완료 처리 절차가 어차피 `작업 목록.md`를 건드림)
