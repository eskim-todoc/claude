# 이슈보고서_1: 영향 범위 조사 누락 (서브에이전트 지침 2종)

**TL;DR**: ④ 구현 착수 직후, **계획서 §2 영향 범위에 `지침/서브에이전트/오케스트레이션.md`(11곳)와 `지침/서브에이전트/활용.md`(1곳)가 빠져 있음**을 확인했다. 특히 오케스트레이션.md는 §3 검증 루프 전체가 «단계 ⑦ 구현 → ⑧ 구현 검증» 구조에 묶여 있어 **표현 교체가 아니라 재설계**가 필요하다. 계획대로 17개만 고치면 **실패_2(정책 표현 분기)가 그대로 현실화**되고 수용 기준 «grep 0»도 실패한다. 작업을 중단하고 선택을 여쭙는다.

## 1. 무엇이 문제인가

### 1.1 빠진 파일

| 파일 | 매치 | 성격 |
|---|---|---|
| `지침/서브에이전트/오케스트레이션.md` | `:11` `:36` `:38` `:42` `:43` `:49` `:65` `:67` `:68` `:92` `:93` — **11곳** | 단순 치환 불가. **구조 종속** |
| `지침/서브에이전트/활용.md` | `:209` — 1곳 (*"단계 ⑧ 구현 검증이 이에 해당한다"*) | 단순 치환 |

### 1.2 오케스트레이션.md가 단순 치환이 아닌 이유

새 체계에는 **«⑧ 구현 검증» 단계 자체가 없다.** 그런데 이 문서는 그 단계를 전제로 절이 구성돼 있다.

| 위치 | 현재 내용 | 새 체계에서의 문제 |
|---|---|---|
| `:36` §3 제목 | "검증 루프 오케스트레이션 (**단계 ⑦⑧ 연동**)" | ⑧이 없다. 게이트 2·자체 선테스트로 재정의 필요 |
| `:38` | *"**단계 ⑦ 구현·처리** 직후 **⑧ 구현 검증**을 오케스트레이션으로 수행한다"* | 새 체계의 ④ 구현·자체 선테스트에 대응시켜야 함 |
| `:43` | *"수정이 계획 변경을 유발하면 **단계 ⑤로 돌아가 계획 재승인**(§4)"* | 새 체계에선 **이슈보고서 → 게이트 1 재통과**다. 지금 제가 하고 있는 바로 이 절차 |
| `:65` `:67` `:68` | fan-out 경계를 *"단계 ⑥ 계획 승인 이후(단계 ⑦)"*로 규정 | **게이트 1** 기준으로 재작성 필요 |
| `:92` `:93` | `작업-프로세스.md §4` 참조 (구 절 번호) | 새 문서 절 구조에 맞춰 재배선 |

즉 **이 문서는 8단계 구조에 배선된 문서**이고, 계획서 Step 3~9 어디에도 들어 있지 않다.

### 1.3 기존 파일 내 라인 누락도 있다

계획서 §2 표가 파일은 맞게 잡았으나 **라인을 덜 적은** 곳이 있다. 작업 자체는 각 Step에 포함되므로 범위가 늘지는 않는다.

| 파일 | 계획서 기재 | 실제 추가 |
|---|---|---|
| `CLAUDE.md` · `AGENTS.md` | `:49~53` `:70` `:151` | **`:84`** (*"코드는 단계 ⑦"*) |
| `지침/작업 규칙.md` | `:11` `:42` `:45` `:50` `:51` `:53` | **`:46` `:47` `:48` `:60` `:62`** |
| `지침/일반/작업 진행 규칙.md` | `:3` `:11` `:34` `:36` `:60` `:62` `:67` | **`:31` `:44`** |
| `지침/코딩/작업 규칙.md` | `:3` `:11` `:15` | **`:18` `:28` `:38`** |

| 파일 | 매치 | 판정 |
|---|---|---|
| `지침/서브에이전트/로그 구조.md:111` | "십의 자리로 **단계**를 구분" | fan-out 노드 번호 규칙 — 프로세스 단계와 무관 |
| `지침/일반/프로젝트 초기 세팅.md:44~176` | "단계 ① 진단" 등 | **자체 4단계 절차** — 작업 프로세스와 별개 |
| `지침/코딩/레지스터·하드웨어 설정 검증.md:47` | "초기화 시퀀스의 다른 단계" | 무관 |
| `지침/코딩/분석·디버깅 규칙.md:35` | "첫 단계 분석에서" | 무관 |

## 2. 왜 놓쳤나 (원인)

계획서 §2에 적은 조사 명령이 이것이었다.

```sh
grep -rn "8단계\|요구사항-검증\|분석-검증\|계획-검증\|구현-검증" CLAUDE.md AGENTS.md 지침/
```

**패턴이 «명칭»과 «파일명»만 담았다.** 오케스트레이션.md는 프로세스를 `단계 ⑦`·`단계 ⑧`·`§4` 처럼 **번호로만** 참조해서 이 패턴에 한 번도 걸리지 않았다. 같은 이유로 `작업 진행 규칙.md:34,36`의 양식 링크도 빠졌다.

> [!IMPORTANT]
> 이것은 **새 체계가 막으려던 실패의 실례**다. 폐지되는 ⑥ 계획 검증의 «영향받는 참조를 Grep으로 전수 첨부» 규율이 정확히 이 지점을 잡는 장치였는데, 제가 계획 단계에서 그 규율을 느슨하게 적용했다.
>
> **새 지침 §규율에 반영할 것**: 영향 범위 Grep은 **명칭·산출물 파일명·단계 번호 기호·양식 링크**를 모두 포함한다. 한 패턴으로 부족하면 축을 나눠 두 번 돌린다.

## 3. 계획대로 진행하면 생기는 일

| 항목 | 결과 |
|---|---|
| 수용 기준 «활성 지침에 8단계 잔존 0건» | **실패** — 오케스트레이션.md에 12곳 잔존 |
| 실패_2 «정책 표현 분기» | **현실화** — 프로세스는 4단계 2게이트인데 오케스트레이션 지침은 ⑦⑧을 지시 |
| 서브에이전트 검증 루프 | **작동 불능** — 존재하지 않는 «⑧ 구현 검증»으로 루프백하라고 지시 |

## 4. 선택지

> [!IMPORTANT]
> **하나만 체크해 주세요.**

- [x] **(가) 범위를 넓혀 계속** `←권장` — Step 8에 두 파일을 추가한다. `활용.md:209`는 한 줄 치환, **`오케스트레이션.md`는 §3·§5를 새 체계에 맞게 재작성**한다(⑦⑧ 연동 → ④ 구현·자체 선테스트 + 게이트 2 연동, fan-out 경계 → 게이트 1 기준, §4 참조 → 새 절 번호). 게이트 1을 다시 받을 필요는 없다고 보는 이유는 **계획의 방향은 그대로이고 범위만 정확해지기 때문**이다
- [ ] **(나) 이번엔 17개만 하고 서브에이전트 2종은 후속 작업으로 분리** — 이번 커밋이 가벼워지지만, 그 사이 **정책 표현이 분기된 상태**로 남는다. 후속 작업을 반드시 이어서 해야 한다
- [ ] **(다) 계획서를 다시 쓰고 게이트 1을 다시 받는다** — 가장 원칙적이지만, 바뀌는 것은 §2 영향 범위 표와 Step 8의 파일 목록뿐이라 되풀이 비용이 크다
