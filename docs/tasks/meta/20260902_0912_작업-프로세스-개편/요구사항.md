# 요구사항: 작업 프로세스 개편 (인터뷰 기반 · 체크박스 승인)

**TL;DR**: 현행 8단계(산출 4 + 자체검증 4)에서 **검증 문서 4종을 폐지**하고, 검증의 주체를 Claude 자체 점검에서 **은수님 체크박스**로 옮긴다. 요구사항은 인터뷰로 뽑아 그 기록 자체가 검증을 대신하고, 분석은 계획서에 흡수하며, 구현 후 확인은 `검증리스트.md`(Claude/은수님 2열)로 받는다. 계획 결함 발견 시 작업을 중단하고 `이슈보고서.md`를 낸다. 상시 산출물 8종 → **4종**(요구사항·계획·검증리스트·이력 및 결과).

## 1. 사용자 요청 원문

> 지침에서 일반 작업 작업-프로세스를 수정해야할거 같아. 지금 내가 프롬프트 입력하면 네가 내 요구사항을 분석하고, 요구사항이 잘 분석 됐는지 검증을 하는데, 이 방법을 변경하고 싶어.
> -> 내가 프롬프트 입력 시, 네가 무엇인지 판단 -> 더 자세한 분석을 위해 원하는 수준이 될 때까지 나에게 질문/취조 시작 -> 이 과정을 요구사항 문서로 정리. 이 자체가 검증과 동일.
> 그 다음은 분석을 진행하면서 분석이 잘 됐는지까지 검증 문서를 작성하기는 하지만, 실제로 내가 검증 문서까지 보지 않아. 너무 산출물이 많아지는 상황이라고 이해하면 돼. 그래서 내가 생각할 때는,
> 현 상태 등 분석 -> 분석을 통해 계획을 구성 -> 계획서 산출. 이 안에는 체크 박스 등을 사용해 나에게 검토 받을 수 있게 정리. 체크 박스 선택 여부 등으로 나에게 계획 검증을 받는 형식.
> 그 다음, 내가 계획서 다 검토 했으니, 내가 체크한 대로 진행 해 하면, 내 선택에 따라 구현 여부가 변경되니까, 이 때 구현 후 테스트 및 체크해야할 사항들을 검증리스트로 산출해.
> 그리고서 네가 구현이 완료되었으니, 확인 후 검증리스트 작성해달라고 하면 내가 검증 리스트에서 체크를 해서 너에게 알려주는 형식이면 될거 같아. 이게 더 깔끔하지 않아?
> 여기서 구현 후 네가 자체적으로 선 테스트 돌려보고 문제 있으면 수정하고 이런 식으로 하면 되는거 같고. 만약 진행 중에 계획자체가 문제인게 밝혀지면, 작업 중단하고서 어디가 문제인지 나에게 이슈보고서 만들어서 줘. 그것도 내가 체크 형식으로 해서 검토 후 수정 반영 여부를 알려주면 되니까.
> 이 방법 어때?

**요청의 성격**: 헌법급 프로세스 개편. 단순 수정 면제 대상이 아니다.

## 2. 인터뷰 기록

> [!NOTE]
> 새 프로세스에서 **이 절이 곧 요구사항 검증**이다. 별도 `요구사항-검증.md`를 만들지 않는다 — 은수님 답변 자체가 근거이므로 Claude가 스스로 "통과"라고 적는 문서보다 정직하다.

### 2.1 원 제안에서 이미 확정된 것

| # | 내용 | 근거 |
|---|---|---|
| 확정_1 | 요구사항은 **인터뷰(질문/취조)로 뽑는다**. 원하는 수준에 이를 때까지 반복 | *"원하는 수준이 될 때까지 나에게 질문/취조 시작"* |
| 확정_2 | 인터뷰 기록이 **요구사항 검증을 대체**한다 | *"이 과정을 요구사항 문서로 정리. 이 자체가 검증과 동일"* |
| 확정_3 | 계획서에 **체크박스**를 두고 그 선택이 **계획 검증 + 승인**을 겸한다 | *"체크 박스 선택 여부 등으로 나에게 계획 검증을 받는 형식"* |
| 확정_4 | **검증리스트는 승인 후에 산출**한다. 은수님 선택에 따라 구현 범위가 바뀌기 때문 | *"내 선택에 따라 구현 여부가 변경되니까, 이 때 ... 검증리스트로 산출"* |
| 확정_5 | 구현 후 Claude가 **자체 선테스트**를 돌리고 문제가 있으면 스스로 고친다 | *"네가 자체적으로 선 테스트 돌려보고 문제 있으면 수정하고"* |
| 확정_6 | 계획 자체의 결함이 드러나면 **작업 중단 + 이슈보고서**(체크 형식) | *"작업 중단하고서 어디가 문제인지 나에게 이슈보고서 만들어서 줘"* |

### 2.2 인터뷰 질의응답

| # | 질문 | 은수님 답변 | 확정 사항 |
|---|---|---|---|
| 질문_1 | 「분석」 산출물을 어떻게 처리할까? 원문은 계획서 하나로 읽히나, 코딩·디버깅 분석은 분량이 커서 계획서가 비대해질 수 있다 | **계획서에 흡수 (문서 2종)** | `분석.md` 폐지. 계획서 §1에 「현 상태 분석」 섹션을 두고 근거를 함께 적는다 |
| 질문_2 | 검증리스트의 체크 주체를 어떻게 나눌까? | **2열 분리 (Claude / 은수님)** | 기계적 확인(빌드·테스트·링크체크)은 Claude가 구현 직후 채우고, 실기 동작·주관 판단만 은수님이 체크 |
| 질문_3 | 기존 8단계 지침·양식과 진행 중 작업 폴더는? | **전면 개편 · 소급 없음** | 양식을 새 체계로 재편. 기존 작업 폴더는 손대지 않고, 구 8단계 설명은 §학습 노트에 이력으로 보존 |
| 질문_4 | 계획서 체크박스는 «무엇»을 체크하는가? | **실행 Step + 핵심 결정 둘 다** | §실행 계획은 Step 단위 체크(미체크 = 이번엔 안 함), §핵심 결정은 선택지 중 하나 고르기. 필수 Step은 `[필수]` 표기 + 기본 체크 |
| 질문_5 | 이 개정 작업 자체는 어떻게 진행할까? | **새 프로세스 자기 적용** | 이 작업이 새 프로세스의 첫 사용 사례가 된다. 산출물은 새 방식대로 요구사항·계획 2종 |

### 2.3 Claude가 제기한 보완 사항 (은수님 이의 없음)

| # | 보완 | 이유 |
|---|---|---|
| 보완_1 | **근거 규율은 문서와 함께 버리지 않는다** | 현행 §3.4의 *"모든 사실 주장에 `파일:라인` 근거"*·*"가설 최소 3개 cross-check"*는 할루시네이션 방지의 실질이다. 검증 **문서**는 없애되 이 규율은 계획서의 **근거 열**로 이전한다 |
| 보완_2 | **자체 검증 「행위」는 유지한다** | 은수님이 안 보시는 것은 문서지 행위가 아니다. 확정_5(자체 선테스트)와 같은 맥락 |
| 보완_3 | **파급 범위가 헌법급이다** | "8단계"라는 명칭이 `CLAUDE.md`·`AGENTS.md`·마스터 체크리스트·양식 5종·폴더 구조·서브에이전트 로그 규약에 분산돼 있다. 한 곳만 고치면 정책 표현이 분기된다 (현행 §5.10 학습 노트가 경고하는 실패 양상) |

## 3. 목표

1. **검증의 주체를 옮긴다** — Claude 자체 점검 문서 4종을 폐지하고, 게이트를 은수님이 실제로 체크하는 자리로 이동
2. **상시 산출물을 8종에서 4종으로 줄인다** — 요구사항·계획·검증리스트·이력 및 결과
3. **줄이되 규율은 남긴다** — 근거 귀속·실패 시나리오·전수 영향 조사를 계획서 안으로 이전
4. **중단 프로토콜을 명문화한다** — 현행에는 "이전 단계 회귀" 판정만 있고 보고 형식이 없다
5. **정책 표현의 분기를 만들지 않는다** — 연동 지점을 전수 갱신
