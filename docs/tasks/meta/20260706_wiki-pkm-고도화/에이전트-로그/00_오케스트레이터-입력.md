# 오케스트레이터 입력

**TL;DR**: 8노드 fan-out(페르소나 6 parallel + adversarial-verify 2) — PKM 방법론 딥리서치로 위키 아키텍처 고도화 설계 근거 확보.

## 원본 입력

> "루트 폴더에 brain 이라고 폴더를 만들어도 돼. ... 이제부터는 이런 작업 내용을 작업 폴더에만 남겨두는게 아니고, 내 제 2의 뇌 역할을 할 옵시디언 기반의 위키를 만들거야. ... 파일 별로 링크도 하고, 관련 지식끼리 어떻게 연결하면 좋을지 등의 아키텍처를 구성해야해. ... 일정 주기로 업데이트... 업데이트할 내용의 요소나 크기, 범위 등은 나보단 네가 더 잘 쪼개지 않을까 싶거든. ... 작업 중간 중간 네가 판단하기에 이건 뇌에 업데이트하면 좋겠는데 싶을 때, 나한테 알리고 업데이트하는 방식이어도 괜찮을거 같아. ... 페르소나 쫙쫙 돌려서 아주 나이스한 뇌 아키텍처링 준비를 해봐."

이어서 "기존 projects/wiki 확장을 하려면, 기존에 구성된 아키텍처가 제대로 운영가능한지부터 다시 면밀히 따져봐야해"라는 후속 확인 답변까지가 본 fan-out의 직접 트리거다.

## 요구 해석

은수님은 (1) 신규 폴더가 아니라 기존 `projects/wiki`를 확장 대상으로 확정했고, (2) 확장 전에 기존 아키텍처의 **운영 실효성**을 먼저 따지라 했고, (3) "일정 주기 배치"가 아니라 "작업 중 판단 시점 트리거 + 알림" 방식의 갱신 모델을 원하며, (4) 그 설계를 위해 PKM 방법론을 페르소나 기반으로 딥리서치하라고 명시적으로 트리거어("페르소나 쫙쫙 돌려서", "딥하게 리서치")를 사용했다.

오케스트레이터가 이미 직접 수행한 것(위임 전 최소 조사, §서브에이전트 활용.md §1.1): `projects/wiki` 구조 확인, git log·mtime 대조로 "2026-05-19 이후 wiki 콘텐츠 미갱신, 그 사이 루트 meta 8작업 완료·미반영, `.wiki-sync/` 미구현" 감사 완료. 이 사실을 각 노드의 공통 컨텍스트로 제공해 중복 조사를 막는다.

## 위임 설계 근거

- [x] 왜 이 분해(8개 노드)인가 — PKM 방법론은 단일 정답이 없고 관점(원자적 노트 철학/프로젝트 기반 조직화/도구 실전기법/택소노미 설계/운영 거버넌스/기존 설계 근본원인)마다 결론이 달라 각각 독립적으로 딥리서치해야 사각지대가 안 생긴다. 은수님이 명시적으로 "페르소나 쫙쫙"을 요청했고, 서브에이전트 활용.md §1 트리거 정책상 dynamic workflow 대상이다.
- [x] 어떤 패턴 — 1단계는 **parallel**(6개 페르소나가 서로 독립적으로 조사, 모든 결과가 한꺼번에 필요), 2단계는 **adversarial-verify**(종합안이 1인 개인 프로젝트 규모에 과설계는 아닌지, 기존 지침과 충돌하지 않는지 반증). loop-until-dry는 미지 규모 탐색이 아니라 미적용, pipeline은 단계 간 의존이 없어 미적용.
- [x] 모델·effort 배분 — 전 노드 `Sonnet`(세션이 무엇이든 고정) · effort 미지정(세션 상속, Sonnet adaptive reasoning) — `max` 고정 금지 정책(서브에이전트 활용.md §3.1 CAUTION) 준수.
