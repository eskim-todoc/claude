# 06_페르소나_기존wiki정합성검토자 — pull 설계는 왜 멈췄고, 무엇을 들고 갈 것인가

**TL;DR**: 근본 원인은 설계 결함이 아니라 **실행 주체(액터) 부존재**다 — "wiki가 독립적으로 pull한다"는 설계는 그 pull을 실제로 호출할 상시 프로세스를 전제하지만, 이 시스템엔 세션 단위로만 존재하는 Claude 외에 그런 주체가 없다. `.wiki-sync/`는 "도입 예정"인 채로 한 번도 만들어지지 않았고(자동화 미구현), 설계 문서 자체도 그 미구현을 실행할 트리거를 명시하지 않았다(설계 공백). 판단 시점 트리거로 전환하면 액터 문제는 저절로 해결되지만, source 계약·판단 기준·재작성 템플릿·공개 검수 체크리스트는 트리거 시점과 무관하게 유효하므로 그대로 승계하고, hash/mtime 기반 diff 추적과 다중 YAML 상태 레지스트리는 폐기해야 한다.

## 1. 확인한 사실관계

| 확인 항목 | 결과 |
|---|---|
| `wiki vault/` 최신 커밋 | `e284a0e` (2026-05-18 17:49) — 이후 콘텐츠 변경 0건 |
| `wiki vault/` 내 2026-05-19 이후 mtime 파일 | 0건 (`find -newermt` 결과 공백) |
| `.wiki-sync/` 폴더 실존 여부 | 없음 — `sources.yaml`·`state.json`·`mappings.yaml`·`schema.md` 전부 미생성 |
| 설계 문서상 `.wiki-sync/` 상태 | `projects/wiki/CLAUDE.md`에 "(도입 예정)"으로만 기재, 실제 파일 0개 |
| 그 사이 root `docs/tasks/meta/` 완료 작업 | 2026-05-19~2026-07-03 사이 최소 8건(오케스트레이션 정책 개정, 워크플로우 이식, Mermaid 팔레트 교정, 작업목록 모듈분산화 등) — wiki 반영 0건 |
| source 계약의 전제 자체도 드리프트 | 2026-07-03 `작업목록-모듈분산화` 정책으로 루트/프로젝트 `작업 목록.md`가 "모듈별 작업 목록.md(생애주기)+루트 작업 목록.md(링크 인덱스)+모듈 현황.md(헬스)" 3축으로 분리됨. Wiki 동기화 운영.md(2026-05-18 작성)가 전제한 "단일 `docs/tasks/작업 목록.md`" 구조는 이미 stale |

`모듈 현황.md`는 원래부터 "Wiki sync 진입판단용"이라는 목적으로 설계돼 있었다(`docs/지침/일반/문서/폴더-구조.md` 29~30행). 즉 판단 신호 자체는 지침 레벨에서 이미 존재했는데, 그 신호를 소비할 주체가 없었다.

## 2. 근본 원인 분석 — 세 가설 교차검증

원인 후보 3가지를 각각 검증했다.

### 가설 A: 설계 자체의 결함(모델이 틀렸다)

**기각.** "source 프로젝트는 작업 원장만 깨끗이 유지하고, wiki가 별도로 읽어 판단한다"는 역할 분리 자체는 논리적으로 건전하다. source에 `wiki_candidate`/`publish` 같은 메타를 심지 않겠다는 판단(문서 61~68행)은 프로젝트 결합도를 낮추는 합리적 선택이었고, 이는 트리거 모델이 바뀌어도 여전히 유효하다(§4에서 유지 항목으로 재확인).

### 가설 B: 트리거 부재(설계는 옳았으나 "언제 실행하는가"가 비어 있었다)

**핵심 원인으로 확인.** 문서의 "운영 절차"(248~257행) 8단계는 전부 "이미 실행 중"이라고 가정한 절차이지, "무엇이 이 절차를 1단계부터 깨우는가"에 대한 답이 없다. cron·훅·세션 시작 체크리스트·사용자 명령 등 구체적 기동 지점이 한 군데도 명시돼 있지 않다. 결과적으로 이 파이프라인은 "누군가 알아서 실행해주겠지"라는 암묵적 가정 위에 있었다.

이는 데이터 엔지니어링에서 흔히 지적되는 반패턴과 동일하다 — pull 기반 동기화는 스케줄러나 명시적 트리거 없이는 "누가 pull을 호출하는가"라는 질문에 답할 수 없고, 결국 아무도 실행하지 않는 상태로 방치된다(batch ETL을 스케줄러 없이 두면 파이프라인이 "정지 상태로 존재"하게 되는 것과 동일 구조, [Batch vs. Event-driven Orchestration – Workato](https://www.workato.com/the-connector/event-driven-orchestration/), [ETL Pipeline Scheduling and Automation Basics](https://apxml.com/courses/intro-etl-pipelines/chapter-5-building-simple-etl-pipelines/scheduling-automation-basics)).

### 가설 C: 자동화 미구현(설계·트리거는 있었으나 실제 코드/스크립트가 없었다)

**부분적으로 사실이지만 파생 원인.** `.wiki-sync/`가 실제로 생성된 적이 없으므로 설계를 기계적으로 실행할 수단 자체가 없었던 것은 맞다. 그러나 이것만으로는 7주 공백을 설명하지 못한다 — 자동화가 없어도 Claude(또는 은수님)가 세션 중 수동으로 "운영 절차" 8단계를 수행할 수 있었다. 그런데 그렇게 하지 않은 이유는 **그 절차를 수행할 세션 진입 계기가 아예 정의돼 있지 않았기 때문**이다. 즉 가설 C는 가설 B(트리거 부재)의 결과이지 독립 원인이 아니다.

### 근본 원인의 실체: 액터 부존재

세 가설을 교차한 결론은 표면적 원인(트리거 부재)보다 한 단계 더 깊다. "wiki 프로젝트가 독립적으로 수행하는 pull 방식"(문서 24행)이라는 표현은 wiki를 마치 **자율적으로 도는 별도 프로세스**처럼 서술하지만, 이 작업 환경에는 그런 상시 프로세스가 존재하지 않는다. Claude Code는 세션 단위로만 깨어나고, 세션은 은수님의 호출로만 시작된다. "wiki가 알아서 pull한다"는 문장은 은유일 뿐 실제로 그 은유를 실행할 데몬·스케줄러·워커가 배정된 적이 없다 — 그래서 설계는 정확했지만 **"누가"에 해당하는 칸이 처음부터 비어 있었던 계획**이었다.

이 세션에서 확인한 바로는 `CronCreate`/`CronList` 같은 정기 실행 도구가 이 환경에 이미 존재한다. 이론적으로는 이걸로 주기 배치를 realize할 수 있었다는 뜻이며, 이는 은수님이 "일정 주기 배치"를 원치 않고 "판단 시점 트리거"를 원한 것이 액터 문제의 **해결**이 아니라 액터 문제를 근본적으로 **회피**하는 선택이라는 의미다 — 실행 주체를 "언젠가 도는 배치"에서 "지금 이 순간 일하고 있는 세션의 Claude 자신"으로 바꾸는 것이므로, "누가 언제 실행하는가" 문제가 구조적으로 사라진다. 이 판단은 타당하다.

## 3. 유지 vs 폐기·수정 판정

### 3-1. 그대로 유지 (트리거 시점과 무관하게 유효)

| 기존 설계 요소 | 유지 근거 |
|---|---|
| **역할 분리 원칙**: source는 원장만 유지, 문서화·공개 판단은 wiki(=이 순간의 Claude)가 함 | 판단 주체가 "별도 wiki 프로세스"에서 "현재 세션의 Claude"로 바뀔 뿐, source 프로젝트에 wiki 메타를 심지 않는다는 결합도 원칙은 그대로 성립 |
| **source에 넣지 않을 항목 표** (`wiki_candidate`/`wiki_targets`/`publish`/공개 문체 요약) | 판단 시점이 세션 중이어도 source 프로젝트 파일에 wiki 전용 필드를 추가할 이유가 없음 — 오히려 이 원칙이 있어야 "세션 중 판단"이 source 오염 없이 가능 |
| **읽는 대상 매핑** (task `이력 및 결과.md`/`분석.md`/`요구사항.md`/`계획.md`에서 무엇을 추출하는지) | 판단 시점이 바뀌어도 "task 문서 중 어디서 어떤 신호를 뽑는가"는 동일하게 유효. 단, `작업 목록.md` 항목은 §3-2에서 구조 갱신 필요 |
| **wiki화 적합/부적합 판단 기준 표** (재사용 가능한 설계 결정 vs 단순 커밋 정리 등) | 시점과 무관한 콘텐츠 분류 기준. 세션 중 "지금 이거 위키에 반영할까?"를 스스로 판단할 때도 동일 기준을 그대로 쓸 수 있음 |
| **task→wiki 재작성 3종 템플릿** (기술 설명/설계 결정/문제 해결 문서 구조) | 산출물 형식 규칙이라 트리거 모델과 독립적 |
| **공개 검수 체크리스트** (민감정보/작업 잡음/출처/링크/주제 일치/독자성) | 오히려 세션 중 즉시 반영 모델에서 더 중요해짐 — 배치라면 나중에 한 번에 검수할 기회가 있었지만, 즉시 반영은 그 순간 바로 걸러야 함 |
| **frontmatter 표준** (`publish`/`public_status`/`sensitivity`/`source_repo`/`source_tasks` 등) | 스키마 자체는 트리거 시점과 무관 |
| `모듈 현황.md` = "Wiki sync 진입판단용" 설계 의도 (폴더-구조.md에 이미 명시) | 세션 중 판단 트리거의 신호원으로 그대로 승계 가능 — 오히려 이걸 실제로 "읽고 판단하는" 루틴이 이번에 처음 생기는 것 |

### 3-2. 폐기 또는 수정 필요

| 기존 설계 요소 | 폐기/수정 판정 및 이유 |
|---|---|
| `.wiki-sync/sources.yaml` + `state.json`(mtime/hash) + `mappings.yaml` 3종 레지스트리 | **폐기.** 이 장치는 "언제 마지막으로 봤는지 모르는 외부 파일들을 주기적으로 스캔해 diff를 찾는" 배치 전제 위에 설계됐다. 판단 시점 트리거에서는 Claude가 이미 그 순간 해당 프로젝트에서 작업 중이며 무엇이 바뀌었는지 맥락을 이미 들고 있으므로, hash/mtime 기반 변경 감지 자체가 불필요해진다. 다만 "같은 내용을 중복 제안하지 않기" 위한 최소 로그(예: 단일 `위키 반영 로그.md`에 반영 완료 task 경로만 누적)는 훨씬 가벼운 형태로 남길 수 있음(§4 제안) |
| "변경 감지 방식" 표 (mtime 이하/hash 동일/신규 task 등 4분기 로직) | **폐기.** 폴링이 없으므로 감지 로직 자체가 무의미. 이 표가 존재한다는 것 자체가 설계자가 "누군가 주기적으로 도는" 그림을 그리고 있었다는 증거이기도 함 |
| "운영 절차" 8단계 (1. sources.yaml 읽기 → … → 8. state.json 갱신) | **전면 수정.** 1번부터 "고정 source 목록을 스캔한다"는 배치 전제. 새 절차는 "세션 중 산출물이 생겼을 때 그 자리에서 wiki화 적합성을 판단 → 즉시 은수님께 알림 → 승인 시 그 자리에서 재작성·검수·MOC 연결"로 재구성해야 함 (구체안은 다른 페르소나 산출물과 종합 필요) |
| "wiki 프로젝트가 독립적으로 수행" / "wiki를 독립 출판 시스템으로 키우는 방향" 이라는 프레이밍(24행, 261행) | **폐기.** 실행 주체가 "별도 시스템"이라는 은유는 이번 근본원인 분석의 핵심 오류 지점이었다. 새 설계 문서는 실행 주체를 명시적으로 "현재 세션에서 작업 중인 Claude, 판단 즉시 은수님께 확인받는다"로 고쳐 써야 하며, 다시는 "독립적으로 돈다"는 표현을 쓰지 않아야 재발을 막을 수 있음 |
| source 계약의 "docs/tasks/작업 목록.md" 단일 파일 전제 | **구조 갱신 필요.** 2026-07-03 모듈분산화 이후 실제로는 `tasks/<모듈>/작업 목록.md`(작업 단위 생애주기) + 루트 `작업 목록.md`(모듈 링크 인덱스) + `모듈 현황.md`(헬스)의 3축 구조. 판단 시점 트리거에서는 어차피 세션이 특정 모듈 작업 중이므로 이 드리프트 자체의 실무 영향은 작지만, 새 설계 문서를 쓸 때 표는 3축 구조로 갱신해야 함(그렇지 않으면 새 문서도 작성 시점부터 stale) |

## 4. 판단 시점 트리거 모델에 대한 구체 제안 (이 프로젝트 한정)

1. **"실행 주체 = 현재 세션의 Claude"를 설계 문서에 명문화한다.** `Wiki 동기화 운영.md`를 개정할 때 "wiki가 독립적으로 pull한다"는 문장을 "작업 중인 세션이 그 자리에서 판단하고 즉시 은수님께 확인 요청한다"로 교체 — 이 문장 하나가 이번 7주 공백의 재발 방지 핵심이다.
2. **`.wiki-sync/`의 3-YAML 체제 대신 단일 경량 로그를 둔다.** 예: `projects/wiki/운영/위키 반영 로그.md`에 "반영 완료 task 경로 + 반영일 + 대상 wiki 문서" 한 줄씩만 표로 누적. 목적은 diff 계산이 아니라 "이미 반영했으니 다음에 또 물어보지 않기" 최소 중복 방지뿐.
3. **`모듈 현황.md`를 판단 신호로 실제로 소비하는 루틴을 만든다.** 이미 그 용도로 설계돼 있었으나 한 번도 읽힌 적이 없다(§1). task 완료로 `이력 및 결과.md`가 "완료" 상태가 되는 시점이 가장 자연스러운 트리거 후보.
4. **wiki화 적합성 판단 기준 표·재작성 3종 템플릿·공개 검수 체크리스트는 문구 그대로 재사용한다.** 새로 설계할 필요 없이 트리거 시점만 갈아 끼우면 된다 — 이 부분까지 새로 만들면 불필요한 재작업이다.
5. **source 프로젝트 최소 계약 표는 3축 구조(모듈별 작업 목록.md/루트 인덱스/모듈 현황.md)로 갱신한 채 유지한다.** "source에 wiki 메타를 심지 않는다"는 원칙은 유지하되, 표의 파일 경로만 현재 지침에 맞게 고친다.
6. **알림은 배치 요약이 아니라 즉시·단건으로 설계한다.** 은수님이 청킹 판단을 Claude에 위임했으므로, 트리거 시점의 판단 기준은 "이 산출물 하나가 독립적으로 위키 한 문서(또는 기존 문서의 한 섹션)를 채울 만큼의 정보 밀도를 가졌는가"로 삼는 것을 제안 — task 하나 = 최소 반영 단위 후보, 여러 task가 같은 개념을 다루면 그때 통합 여부를 판단.
