# 21_검증_실용성반증 — 6개 제안 종합의 과설계 여부 판정

**TL;DR**: 6개 제안을 합치면 신규 스키마 필드 3종·플러그인 2종·승인 워크플로 1종·소급 재작업 2종이 동시에 추가된다 — 이미 19커밋·3일치 활동 만에 frontmatter 필드가 파일마다 제각각으로 갈라진 vault, 그리고 그 뒤 7주 방치라는 실측 전례에 비추면 이 조합은 **과설계(overengineered)** 다. 생존 가능한 부분(문서 서술 정정·기존 필드 1개 추가·경량 로그 1개)만 남기고 나머지는 기각 또는 무기한 보류를 권고한다.

## 1. 판정 기준: "1인 유지보수 테스트"

기업 KM 프레임워크와 개인 취미 Obsidian의 결정적 차이는 인력 규모가 아니라 **누가 스키마를 채우는가**다. 이 vault는 은수님이 손으로 태그·프론트매터를 입력하는 게 아니라 **Claude가 세션 중 Write/Edit 도구로 대신 채우는** 구조다. 따라서 판정 기준은 다음 4문항으로 좁힌다.

1. **드리프트 내성** — 이 항목을 한 번 빼먹어도 vault가 깨지지 않는가, 아니면 무언가(색인·상태·링크)가 조용히 어긋나는가?
2. **저작 부담 전이** — 이 항목의 실제 입력 노동을 Claude가 지는가, 은수님이 지는가? 은수님에게 전가되는 항목(플러그인 UI 조작, 승인 클릭, 재분류 판단)은 고위험.
3. **실측 전례와의 정합성** — 이미 존재하는 vault가 이 항목 없이도 7주를 버텼는가(=없어도 되는 것), 아니면 이 항목의 부재가 방치의 원인이었는가(=진짜 필요한 것)?
4. **신규 의존성 여부** — 플러그인·별도 파일 형식(YAML)·승인 상태 머신처럼 그 자체로 유지보수 대상이 되는 것을 새로 들이는가?

| 4단계-프로세스.md 단계④에 "완료 시 신호표로 wiki화 후보 채점" 추가 | ❌ | 모든 task 완료마다 채점표를 작성하라는 요구는 매 작업에 관료적 게이트를 하나 더 심는 것 — 4단계 프로세스 자체의 무게를 늘려 오히려 전체 착수 문턱을 높인다. 완료 즉시 "이걸 wiki에 반영할까요?"라는 1줄 판단(자유 서술)이면 충분, 별도 "신호표"라는 명명된 산출물 불필요 |
| 미반영 meta task 8건 소급 채점 | ❌ | 위 채점 체계 자체가 기각되므로 연동 기각. 일회성 소급 작업의 학습 가치보다, 지금부터 새 모델로 즉시 운영 시작하는 편이 실익 큼 |
| 오탈자·1줄 보강은 승인 없이 즉시 반영 + 한 줄 보고 | ✅ | GTD 2분 규칙과 부합, 유일하게 "즉시성" 방향과 정합. 이 항목만 채택 |

### 3.6 기존 wiki 정합성 검토자

| 항목 | 판정 | 근거 |
|---|---|---|
| "wiki가 독립적으로 pull" → "작업 세션이 즉시 판단·확인 요청"으로 문구 교체 | ✅ | 이번 개편의 핵심 그 자체 — 반드시 반영 |
| `.wiki-sync` 3-YAML 대신 `위키 반영 로그.md` 단일 경량 로그 | ✅ | 6개 제안 중 가장 저비용·저마찰. 컬럼 3~4개(task 경로/반영일/대상 문서/한줄 메모) 수준이면 상태 머신 없이도 "뭘 언제 반영했는지"는 남길 수 있음 — §3.5에서 기각된 승인 워크플로의 대체재로 채택 |
| task 완료(이력 및 결과.md → 완료) ↔ 모듈 현황.md 갱신을 트리거 후보로 연동 | ✅ | 신규 메커니즘 아님, 이미 존재하는 완료 신호를 재사용 — 저비용 |
| 판단기준표·재작성 템플릿 3종·검수 체크리스트·frontmatter 표준 그대로 재사용 | ✅ | 이미 작성된 자산 재사용, 신규 비용 0 |
| source 프로젝트 최소 계약 표를 3축 구조로 경로만 갱신 | ✅ | 순수 오타/경로 정정 |
| 청킹 기준: "task 1건 = 최소 반영 단위, 개념 겹치면 그때 통합 판단" | ✅ | 별도 규칙 신설 없이 상황 판단에 위임 — 가장 "저비용" 성격의 제안 |

## 4. 페르소나 간 발견된 충돌 (교차 검토)

1. **status 이중화**: PARA 페르소나의 frontmatter `status` 필드 vs 정보 아키텍트의 `#status/review` 태그축 — 같은 목적(검수/완료 상태 추적)에 서로 다른 두 메커니즘. **frontmatter 필드 하나만 채택**, 태그축 폐기.
2. **오프라인 갱신 추적 이중화**: PARA의 "홈.md 수동 동시 갱신 의무" vs Obsidian 파워유저의 "Bases 최근 갱신 뷰(자동)" — 후자가 전자를 대체 가능한데 둘 다 채택하면 중복 노동. **Bases 자동 뷰만 채택**, 수동 갱신 의무는 폐기.
3. **Orphan(고아 문서) 탐지 이중화**: Obsidian 파워유저의 `_내부/유지보수.md` + Dataview 쿼리 vs Zettelkasten 페르소나가 명시한 "Obsidian 백링크 패널이 이미 그 역할을 대체" — 페르소나 자신의 논리로 페르소나 자신의 제안이 불필요해짐. **백링크 패널(내장)로 충분**.
4. **거버넌스 설계자의 자기모순**: "즉시 판단·즉시 알림" 모델을 설계해야 할 페르소나가 4상태 승인 큐를 제안 — 이는 배경에서 이미 실패로 규정된 `.wiki-sync` 패턴의 재림. wiki 정합성 검토자의 "단일 경량 로그"안이 같은 필요(추적)를 훨씬 적은 비용으로 충족하므로 **후자로 대체**.

## 5. 종합 권고 — 지금 채택할 최소 집합

**신규로 실제 추가할 것 (전부 합쳐도 신규 파일 2개 + 필드 1개 + 문구 정정 수 건)**:
- `projects/wiki/운영/Wiki 동기화 운영.md` 문구 교체: "pull 독립 운영" → "세션 내 즉시 판단·확인 요청" (필수, 이번 개편의 본체)
- `projects/wiki/운영/위키 반영 로그.md` 신규 — task 경로/반영일/대상 문서/한줄메모 4컬럼, 승인 상태 없음
- frontmatter에 `status` 필드 1개만 추가 (project/area/resource/archived) — 태그축 대체 없이 이것만
- `프로젝트/MOC.md`에 "메타" 슬롯 1줄, `학습/운영정책/MOC.md` 신규 1건
- 홈.md에 Obsidian 코어 Bases "최근 갱신" 뷰 1개 (플러그인 설치 없이 가능한지 버전 확인 필요 — 안 되면 이 항목은 보류하고 그냥 수동 스킵, 강제 규칙화하지 않음)
- 청킹 기준·판단 기준표·재작성 템플릿·체크리스트는 기존 설계 문서 내용 그대로 재사용

**지금 도입하지 않을 것 (전부 보류/기각)**:
- Dataview·Templater 플러그인 설치
- `위키화 후보.md` 4상태 승인 워크플로, "신호표" 채점 체계, 8건 소급 채점
- 상위/교차 2필드 연결 블록 확장
- 태그 kebab-case 소급 일괄 정정(CFX 10개 포함) — 신규분부터 소문자만 지침화

- "문서 갱신 시 색인도 함께 갱신"을 완료 정의에 넣는 수동 규칙
- 원자 노트 "파일명=주장 문장" 강제(링크 의무만 유지, 명명 규칙은 자유)
