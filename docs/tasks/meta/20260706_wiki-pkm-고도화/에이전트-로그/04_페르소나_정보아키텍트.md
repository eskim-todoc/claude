# 04_페르소나_정보아키텍트 — 기존 4단계 구조의 교차 연결·확장성 진단

**TL;DR**: 기존 "홈→카테고리 MOC→허브→개별문서" 4단계 구조 자체는 견고하지만, ① `학습`·`일상` 카테고리가 완전히 비어 있어 7주간 쌓인 메타/정책성 지식(오케스트레이션 정책 등)이 어느 카테고리에도 속할 곳이 없고, ② 태그가 대소문자·표기 불일치로 사실상 죽어 있으며, ③ CFX 참고문서 10건 전부가 복붙 잔재로 보이는 잘못된 태그(`how-to, test, pytest, acceptance`)를 달고 있고, ④ "상위: 단일 링크" 연결 블록 관례가 다중 소속 지식을 구조적으로 배제하고, ⑤ 프로젝트 허브 생성이 `projects/` 폴더 신설 속도를 못 따라가고 있다(7개 프로젝트 중 4개만 허브 보유). 새 카테고리 신설보다 기존 5카테고리 재정의(`학습`을 프로젝트 횡단 메타/정책 지식까지 포함하도록 확장)와 태그 정합성 정리가 먼저다.

## 1. 기존 구조 재확인

`projects/wiki/운영/Wiki 탐색 구조 분석.md`가 이미 규정한 구조:

```
홈 → 카테고리 MOC (프로젝트/사용방법/참고/학습/일상) → 프로젝트 허브 또는 주제 허브 → 개별 문서
```

원칙표(§MOC 설계 원칙)의 핵심 문장은 그대로 유효하다: "홈은 얇게", "MOC는 실제 목록", "프로젝트 허브 필수", "주제 허브 병행", "개별 문서는 상위 링크", "태그는 보조". 2026-05-18 기준 1~4번 우선순위가 "완료"로 표시되어 있는데, 실제 vault를 열어보면 그 완료는 **당시 존재하던 4개 프로젝트(Sound1·auto-rtt-viewer·sound1-fw-extractor·ez8300-study)와 5개 주제 허브(LED·RTT·CFX·터치·칩) 범위 안에서만** 완료된 것이다. 즉 구조는 설계되었지만 "구조를 최신 상태로 유지하는 절차"가 없어서, 설계 시점 스냅샷 이후로는 정지했다. 이는 감사에서 이미 확인된 "pull을 실행할 주체·트리거 부재"와 동일한 패턴이 정보 아키텍처 층위에서도 반복되고 있다는 뜻이다 — 즉 태스크 로그 pull 트리거가 없는 문제뿐 아니라 **허브·MOC 자체를 신설/갱신하는 트리거도 없다.**

## 2. 실측: 카테고리별 실제 콘텐츠 밀도

| 카테고리 | 실제 페이지 수(MOC 제외) | 상태 |
|---|---|---|
| 프로젝트 | 4개 허브 (Sound1, auto-rtt-viewer, sound1-fw-extractor, ez8300-study) | 루트 CLAUDE.md 기준 실제 프로젝트는 7개 — `wiki`, `mermaid-study`, `sullivan-1-5-board-eol-test`가 허브 없음 |
| 사용방법 | 8개 | 가장 잘 갖춰짐. 표에 `출처 repo` 컬럼까지 있어 재현 가능한 유일한 MOC |
| 참고 | 5개 주제 허브(LED/RTT/CFX/터치/칩) 산하 18개 문서 | 전부 Sound1 임베디드 도메인(펌웨어·칩·신호처리)에 편중 |
| 학습 | **0개** | MOC만 존재, "작성 가이드"만 있고 실제 문서 전무 |
| 일상 | **0개** | MOC만 존재, 실제 문서 전무 |

이 표가 이번 조사의 핵심 근거다. 배경에서 이미 확인된 사실 — "7주간 docs/tasks/meta/에 8건의 작업(오케스트레이션 정책 개정 등)이 완료됐으나 wiki에 전혀 반영되지 않았다" — 를 정보 아키텍처 관점에서 재해석하면: **그 지식이 반영되지 않은 것은 pull 트리거 부재 때문만이 아니라, 애초에 그 지식이 들어갈 카테고리가 현재 taxonomy에 없기 때문이다.**

`docs/tasks/meta/` 산출물(오케스트레이션 정책, 서브에이전트 활용 규칙, 문서 메타 규칙 등)은:
- `프로젝트`가 아니다 — 특정 source repo에 종속되지 않고 전 프로젝트에 적용됨
- `참고`가 아니다 — `참고`는 현재 전적으로 하드웨어/프로토콜 레퍼런스(LED/RTT/CFX/터치/칩) 전용으로 굳어짐
- `사용방법`이 아니다 — `사용방법`은 "how-to"(도구를 어떻게 쓰는가) 전용. `사용방법/MOC.md`에 이미 root 출처 문서(`Claude Code 단축키`, `Slack 작업 완료 알림`) 2건이 들어가 있어 전례는 있지만, 이들은 "절차형" 지식이지 "정책/설계 결정형" 지식(왜 이렇게 정하는가, 대안은 무엇이었는가)이 아니다. `Wiki 동기화 운영.md`가 이미 정의한 3가지 문서 유형(기술 설명/설계 결정/문제 해결) 중 "설계 결정 문서" 템플릿이 현재 vault 어디에도 실제 사례가 없다
- `학습`이 아니다 — `학습/MOC.md`의 정의(개인 학습·기술 메모, 책/강의/블로그 출처)는 외부 지식 습득을 가리키지 자체 운영 정책을 가리키지 않는다. 다만 가장 재정의 여지가 큰 카테고리다
- `일상`이 아니다 — 명백히 아님

**결론: 5개 카테고리는 "프로젝트 종속 실무 지식"에는 맞게 설계되어 있으나, "여러 프로젝트를 관통하는 운영 정책/프로세스 지식"이라는 클래스 전체가 taxonomy에서 빠져 있다.** 이것이 이번 조사에서 찾은 가장 구체적인 확장성 결함이다.

## 3. 제안 A — `학습` 카테고리를 "프로젝트 횡단 지식"으로 재정의 (신규 카테고리 대신)

배경에 명시된 대로 신규 폴더 신설은 이미 기각되었으므로, 기존 5개 중 콘텐츠가 0건인 `학습`을 재정의하는 것이 가장 저비용이다.

- 현재 정의: "개인 학습·기술 메모"(외부 출처 한정)
- 재정의 제안: "프로젝트 횡단 지식" — 외부 학습 메모 + 여러 프로젝트에 적용되는 운영/정책/프로세스 지식(오케스트레이션 정책, 문서 규칙, Git 워크플로우 등 `docs/지침/` 유래) 둘 다 포괄
- 근거: `학습/MOC.md`의 "작성 가이드"가 이미 "주제별로 페이지 1개", "관련 주제는 태그 또는 위키링크"라고만 되어 있어 출처 형식에 강하게 결속되어 있지 않다 — 재정의 비용이 낮다
- 하위 허브 신설 제안: `학습/운영정책/MOC.md`(오케스트레이션·서브에이전트·문서 규칙 등 `docs/지침/일반/` 대응) — 참고의 `LED/RTT/CFX/터치/칩`과 동일한 패턴으로 주제 허브를 하나 추가하는 것뿐이므로 기존 구조를 깨지 않음
- 홈.md와 `학습/MOC.md`에 이 재정의를 명시해야, 다음에 유사한 메타 정책 지식이 나왔을 때 Claude가 "어디에 넣을지 판단"하는 시간을 줄일 수 있다 (현재는 그 판단 기준 자체가 없어서 미반영 상태로 방치됐을 가능성이 큼)

## 4. 제안 B — 태그 정합성 정리 (즉시 실행 가능한 저비용 개선)

실측 결과 태그 계층이 사실상 기능하지 않고 있다.

| 문제 | 실례 |
|---|---|
| 대소문자 불일치 | `RTT`(RTT MOC, auto-rtt-viewer 허브) vs `rtt`(RTT 연결 메커니즘, fw.txt 형식); `LED`(LED MOC) vs `led`(개별 LED 문서 4건 전부); `Ezairo`(ez8300-study, CFX MOC) vs `ezairo`(칩 스펙 문서); `Sound1`(Sound1 허브, LED MOC) vs `sound1`(fw.txt 출력 명세) |
| 오태그(복붙 잔재로 추정) | `참고/CFX/` 하위 10개 문서 **전부**가 `tags: [how-to, test, pytest, acceptance]`를 달고 있음 — CFX-01(아키텍처 개요), CFX-03(메모리 구조) 같은 순수 레퍼런스 문서에 "시험 절차" 계열 태그가 붙어 있어, 원래 `사용방법/시험 절차.md` 프론트매터를 복사해 만든 흔적으로 보임. 실제 CFX 고유 주제 태그(`fixed-point`, `interrupt`, `intrinsic` 등)가 하나도 없음 |
| 태그가 MOC 소속과 중복만 함 | `moc, CFX, Ezairo, reference`처럼 MOC 자체 태그가 이미 위키링크로 표현되는 소속 관계를 반복 — 웹서치로 확인한 Obsidian 커뮤니티 관행(아래 출처)과도 어긋남: "주제(topic)는 링크가 담당하고, 태그는 상태/단계(status/stage)를 담당해야 한다" |

제안:
1. 언어 표기 통일 규칙 신설: 태그는 영문 소문자 kebab 고정(`rtt`, `led`, `ezairo`, `sound1`, `cfx`) — 이미 `docs/지침/일반/문서 작성 규칙.md`가 "알파벳 약어 금지, 한글 라벨" 원칙을 갖고 있으므로, 이를 확장해 "태그는 영문 소문자 통일"을 wiki 전용 예외로 명문화
2. CFX 10개 문서의 오태그를 실제 주제 태그로 일괄 정정 (별도 저작 작업, 이번 조사 범위 밖이나 근거로 기록)
3. 태그를 상태/단계 축으로도 일부 활용 — 현재 태그는 전부 주제(topic) 축뿐이다. 예: `draft`/`review`/`stable` 같은 상태 태그를 프론트매터의 `maturity`/`public_status`와 별개로 vault 내 `#status/review` 형태 중첩 태그로 추가하면, "지금 검수 대기 중인 문서만 모아보기"가 MOC 편집 없이 가능해진다 (웹서치 출처: 중첩 태그는 2단계 이내 권장 — 예: `#status/review`는 적합, `#status/review/2026q3`는 과함)

## 5. 제안 C — "상위: 단일 링크" 관례를 다중 소속 허용으로 완화

`Wiki 탐색 구조 분석.md`의 "개별 문서 하단 연결 블록" 템플릿은 `상위: [[참고/LED/MOC]]` 처럼 단수 형태다. 실제로 칩 문서(`Ezairo 8300 클럭·타이머·I2C 스펙 정리.md`)처럼 Sound1 프로젝트 허브와 칩 참고 허브 양쪽에서 참조되는 문서가 이미 존재하고, `참고/MOC.md`의 "관련 프로젝트" 컬럼이 이미 다대다 관계를 표현하고 있다 — 즉 **MOC 층위에서는 이미 다중 소속을 인정**하면서 **개별 문서 층위의 "상위" 블록만 단수를 전제**하는 불일치가 있다.

이질적 프로젝트(임베디드 도메인 + 일반 학습 + 도구 사용법 + 일상)를 넘나드는 지식이 늘어날수록 "정확히 하나의 상위 허브"라는 가정은 깨진다. 예: 향후 "FSM 패턴" 문서가 생기면 이는 `참고`(Sound1 구현 패턴)와 `학습/운영정책`(코딩 지침의 구현 패턴, `docs/지침/코딩/구현 패턴.md`) 양쪽에 실질적으로 속한다.

제안: 연결 블록을 `상위`(단수, 주 계통) + `교차`(복수, 부차 계통) 2필드로 분리.

```markdown
## 연결
- 상위: [[참고/칩/MOC]]
- 교차: [[프로젝트/Sound1]], [[프로젝트/ez8300-study]]
- 출처: <source_repo>, <source_tasks>
```

이는 웹서치로 확인한 Obsidian MOC 관행("한 노트가 여러 MOC에 동시 소속되는 것은 정상이며, 폴더보다 MOC/링크가 유연한 이유가 바로 이것")과도 일치한다.

## 6. 제안 D — 프로젝트 허브 생성을 신규 프로젝트 온보딩 절차에 편입

루트 CLAUDE.md의 `Projects` 표에는 7개 프로젝트가 있으나 `프로젝트/MOC.md`에는 4개만 허브가 있다. `mermaid-study`, `sullivan-1-5-board-eol-test`, 그리고 `wiki` 자신은 허브가 없다. `docs/지침/일반/프로젝트 초기 세팅.md`(신규 프로젝트 5단계 자동 세팅, maturity: stable)에 "wiki 프로젝트 허브 스텁 생성"을 6번째 단계로 추가하면, 구조 설계와 실제 콘텐츠 간의 격차가 재발하지 않는다. 이는 이번 조사 범위(정보 아키텍처)를 살짝 벗어나 프로세스 영역이지만, 구조가 다시 정체되지 않으려면 "누가 언제 허브를 만드는가"가 반드시 답이 있어야 하므로 기록해둔다.

## 7. 확장성 결함 요약 (우선순위순)

| 순위 | 결함 | 근거 | 심각도 |
|---|---|---|---|
| 1 | 프로젝트 횡단 메타/정책 지식을 담을 카테고리 부재 | `학습`·`일상` 0건, `docs/tasks/meta` 8건 미반영 | 높음 — 배경 문제의 직접 원인 |

| 3 | CFX 10개 문서 오태그(복붙 잔재) | 전수 확인, 100% 재현 | 중간 — 신뢰도 문제 |

## 8. 이 프로젝트에 구체적으로 적용 가능한 제안 (요약)
