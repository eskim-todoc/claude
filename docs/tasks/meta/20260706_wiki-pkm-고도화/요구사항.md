# 요구사항: 위키 PKM 아키텍처 고도화

**TL;DR**: 은수님이 작업 폴더에만 남던 조사·학습 내용을 Obsidian 기반 "제2의 뇌"로 영속화하길 원함. 확인 결과 `projects/wiki`가 이미 그 목적으로 존재하나, 2026-05-19 이후 콘텐츠 갱신이 멈춰 있고(설계된 pull 동기화가 실제로는 한 번도 정기 운영되지 않음) `.wiki-sync/` 추적 메커니즘도 미구현 상태. 본 작업은 ① 이 운영 실효성을 정밀 진단하고, ② PKM 방법론(Zettelkasten·PARA·Johnny Decimal 등)을 페르소나 기반으로 딥리서치하며, ③ "작업 중 판단 시점에 알리고 갱신"하는 트리거 기반 운영 모델을 설계하는 것.

## 1. 사용자 요청

> "루트 폴더에 brain 이라고 폴더를 만들어도 돼. 내 얘기를 듣고 나서 네가 필요하다고 생각이 들면 말이야. 지금까지는... tasks 폴더에 작업을 하고... 이제부터는 이런 작업 내용을 작업 폴더에만 남겨두는게 아니고, 내 제 2의 뇌 역할을 할 옵시디언 기반의 위키를 만들거야. ... 파일 별로 링크도 하고, 관련 지식끼리 어떻게 연결하면 좋을지 등의 아키텍처를 구성해야해. ... 그 외에 앞으로 정리되는 문서는 brain 폴더 등에 저장했으면 하는거야. ... 일정 주기로 업데이트... 업데이트할 내용의 요소나 크기, 범위 등은 나보단 네가 더 잘 쪼개지 않을까 싶거든. ... 작업 중간 중간 네가 판단하기에 이건 뇌에 업데이트하면 좋겠는데 싶을 때, 나한테 알리고 업데이트하는 방식이어도 괜찮을거 같아. ... 페르소나 쫙쫙 돌려서 아주 나이스한 뇌 아키텍처링 준비를 해봐."

**모호 포인트 해소**: "brain 폴더 신설" 여부가 모호해 `AskUserQuestion`으로 확인. `projects/wiki`가 이미 Obsidian Vault·PKM 목적으로 존재함을 먼저 조사해 제시했고, 은수님 답변은 "기존 projects/wiki 확장을 하려면, 기존에 구성된 아키텍처가 제대로 운영가능한지부터 다시 면밀히 따져봐야해" — 즉 **신규 brain 폴더는 기각, 기존 wiki 확장 방향 확정**. 단, 확장 전에 기존 아키텍처의 운영 실효성부터 정밀 진단하라는 선행 조건이 붙음.

## 2. 목표

- 목표_1: `projects/wiki`의 기존 설계(pull 동기화·`.wiki-sync/`·MOC 탐색 구조)가 **실제로 운영 가능한 상태인지** 정밀 진단 — 설계와 실제 이력(git log·최종 수정일) 간 간극 확인
- 목표_2: PKM 방법론(Zettelkasten·PARA·Johnny Decimal·MOC·evergreen notes·atomic notes 등)을 최소 5개 페르소나로 fan-out 딥리서치 — 나이스한 지식 연결 아키텍처 설계 근거 확보
- 목표_3: "일정 주기" 배치 방식이 아니라 **작업 중 판단 시점 트리거** 방식의 운영 모델 설계 — 무엇이 wiki화 대상인지, 언제·얼마나 쪼개서 갱신 후보로 삼을지, 은수님께 어떻게 알리고 승인받을지
- 목표_4: 기존 wiki 컨벤션(홈→MOC→허브→문서 4단계 탐색, 공개 검수 체크리스트, frontmatter 표준)과 정합되는 개정 아키텍처 제시 — 전면 재설계가 아니라 확인된 간극 위에 보강

## 3. 수용 기준 (Definition of Done)

### 3.1 기능·산출물
- [ ] 수용기준_1: `분석.md`에 운영 실효성 진단 결과(설계 vs 실제 이력 비교, 미구현 요소 목록) 문서화
- [ ] 수용기준_2: `분석.md`에 PKM 방법론 비교·종합(페르소나 fan-out 결과, adversarial-verify 통과) 포함
- [ ] 수용기준_3: `계획.md`에 트리거 판단 기준·청킹 휴리스틱·은수님 알림 방식·기존 wiki 컨벤션과의 접합점을 구체적으로 명시
- [ ] 수용기준_4: `계획.md` 사용자 승인 후에만 실제 문서·설정 변경(단계 ④) 진행

### 3.2 정합성·검증
- [ ] git diff로 모든 변경 검토 가능
- [ ] cross-link 살아있음 (broken link 0)
- [ ] `이력 및 결과.md` 시계열 로그 + 완료 요약 작성

### 3.3 회귀 방지
- [ ] 본 작업은 `claude_feature_wiki-pkm-고도화` 브랜치 격리
- [ ] 각 commit이 atomic — 단계별 revert 가능
- [ ] 기존 `wiki vault/` 콘텐츠·구조 손상 없음 (구조 변경은 계획 승인 후에만)

## 4. 작업 범위 외 (Out of Scope)

- 범위외_1: 루트에 별도 "brain" 폴더 신설 — 은수님 확인으로 기각, `projects/wiki` 확장으로 대체
- 범위외_2: `.wiki-sync/` 자동화 스크립트의 실제 코딩 구현 — 이번 작업은 운영 모델 설계까지, 실 구현 여부·시점은 계획에서 제안 후 별도 승인
- 범위외_3: 기존 `wiki vault/` 콘텐츠 전수 공개 검수(민감정보·링크 정리) — 이미 알려진 별도 후속 과제, 본 작업과 분리

## 5. 위임 범위 (Claude 자율 결정)

- 위임_1: PKM 방법론 리서치의 페르소나 구성·조사 소스·비교 기준
- 위임_2: 트리거 판단 임계치·청킹 기준의 최초 제안(계획.md에서 제시, 사용자 승인으로 확정)
- 위임_3: 운영 실효성 진단에 필요한 조사 방식(git log·파일 mtime·기존 운영 문서 대조)

위임 범위 밖 (사용자 결정 영역):

- 사용자결정_1: 최종 아키텍처 계획(`계획.md`) 승인
- 사용자결정_2: `claude_develop` 병합 여부·시점
- 사용자결정_3: 트리거 알림을 받을 때 실제로 wiki 갱신을 승인할지 매번 판단 (설계상 "알리고 승인받는" 방식이므로 매 건 최종 결정권은 은수님)

- [계획.md](계획.md) — 트리거 기반 갱신 아키텍처 실행 계획
