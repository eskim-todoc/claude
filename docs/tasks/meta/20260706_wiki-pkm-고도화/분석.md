# 분석: 위키 PKM 아키텍처 고도화

**TL;DR**: `projects/wiki`의 기존 골격(폴더+MOC+위키링크)은 PKM 방법론 수렴점과 이미 일치해 대수술이 불필요하다. 진짜 문제는 "독립적으로 pull하는 wiki"라는 설계가 세션 단위로만 깨어나는 Claude Code 환경에서 애초에 실행될 액터가 없었다는 구조적 결함이었다(2026-05-19 이후 7주 0갱신, meta 8작업 미반영으로 실증). 6개 페르소나 제안을 종합 검증한 결과 총합은 1인 유지보수 한계를 넘는 과설계로 판정됐고, 최소 채택 집합(신규 필드 1개·신규 파일 2개·플러그인 0개)으로 축소한 안이 계획.md의 기반이 된다. 2026-07-06 은수님 재확인으로 캡처(언제 적어넣을지)만큼 중요한 두 축 — **회수(키워드+링크 추적 조회)**와 **개정(기존 문서 고쳐 쓰기)** — 을 §4.3·결정_7·결정_8에 추가했다.

## 1. 현 상태 (Current State)

- 현황_1: `projects/wiki/wiki vault/`는 5개 카테고리(프로젝트/·학습/·일상/·참고/·사용방법/) + 각 폴더 `MOC.md` + `[[위키링크]]` 구조로 이미 존재. 진입점 `홈.md`
- 현황_2: `학습/`·`일상/` MOC는 실제 페이지 0건. `프로젝트/MOC.md`는 `/projects/` 하위 4개 repo만 나열하고 루트 저장소 자체(`docs/tasks/meta/`) 영역은 허브 슬롯이 없음
- 현황_3: wiki repo git log 19커밋 전부 2026-05-15·05-18·05-19 사흘에 집중, 이후 오늘(2026-07-06)까지 7주간 콘텐츠 커밋 0건
- 현황_4: 같은 사흘 안에 이관된 문서조차 frontmatter 필드 구성이 파일마다 다름(예: `Sound1.md`는 `maturity`·`publish`·`public_status`·`sensitivity` 보유, 일부 이관 문서는 無) — 이미 스키마 드리프트 존재
- 현황_5: 설계 문서(`운영/Wiki 동기화 운영.md`)가 규정한 `.wiki-sync/`(sources.yaml·state.json·mappings.yaml)는 "도입 예정"으로만 적혀 있고 실제로 생성된 적이 없음
- 현황_6: `wiki vault/.obsidian/community-plugins.json`은 빈 배열 — 커뮤니티 플러그인 0개 설치. 코어 플러그인(graph·backlink·daily-notes·templates·bases)은 켜져 있으나 활용 흔적 없음(`graph.json colorGroups` 비어있음)
- 현황_7: 같은 사흘 이후 루트 `docs/tasks/meta/`에서만 8건의 작업(오케스트레이션 정책 개정, 워크플로우 오케스트레이션 이식 등)이 완료됐으나 wiki에 단 하나도 반영되지 않음
- 현황_8: `source 프로젝트 최소 계약` 표(`projects/wiki/CLAUDE.md`)는 2026-07-03 `작업목록-모듈분산화` 정책(작업 목록.md 3축 구조 — 모듈별/루트 인덱스/모듈 현황) 이전 경로 표기 그대로라 이미 실측 드리프트 상태
- 현황_9 (2026-07-06 은수님 재확인으로 발견): 지금까지 계획은 "언제·무엇을 wiki에 새로 적어넣을지"(캡처)에만 집중했고, **"나중에 새 작업을 지시받았을 때 wiki에서 관련 배경지식을 어떻게 찾아 꺼내쓸지"(검색·회수)** 절차가 빠져 있었다. 은수님 예시: Sound1 터치센서 작업에서 데이터시트·터치 방식 스터디가 `docs/참고`에 쌓였고, 이후 작업 때 그걸 다시 찾아 참고하는 패턴이 반복됨 — 이 "찾아 쓰기"가 wiki로 이전됐을 때도 똑같이 되어야 함
- 현황_10 (동일 계기로 발견): 계획이 "신규 콘텐츠 추가"만 다뤘고, **이미 wiki에 있는 문서를 새 정보로 고쳐 쓰는(개정) 절차**가 없었다 — 배경지식은 한 번 쓰고 끝나는 게 아니라 실제 작업으로 검증되면서 갱신되는 경우가 많음

## 4. 검증 결과 (adversarial-verify 2종)

### 4.1 검증 21 — 실용성 반증: `overengineered` ([전문](에이전트-로그/21_검증_실용성반증.md))

6개 페르소나 제안을 그대로 합치면 신규 스키마 필드 3종·플러그인 2종·4상태 승인 워크플로·소급 재작업 2종이 동시에 추가되어 1인 취미 유지보수 한계를 초과한다고 판정. 근거: wiki repo 커밋이 사흘에 몰리고 7주 공백이었다는 사실 자체가 "적은 것도 유지 못 했다"는 실측이고, 이미 존재하는 8개 안팎 frontmatter 필드도 파일마다 드리프트 중인데 필드를 더 얹으면 드리프트만 가속된다는 논리. 페르소나 간 미조정 중복도 3건 적발(PARA `status` 필드 vs 정보 아키텍트 `#status` 태그축 중복 등). **"위키화 후보.md" 4상태 승인 큐는 은수님이 벗어나려는 옛 실패 패턴(쌓이기만 하고 트리거 안 됨)을 이름만 바꿔 재현하는 자기모순**이라는 지적이 결정적이었다.

역제안된 최소 채택 집합(신규 플러그인 0·신규 필드 1·신규 파일 2)을 §5 핵심 결정의 기반으로 채택.

### 4.3 추가 요구사항 근거 — 검색(회수) 프로토콜과 개정 메커니즘 (2026-07-06 은수님 재확인)

은수님이 예시(Sound1 터치센서 작업)로 명확히 한 요구는 기존 6개 페르소나 리서치가 이미 다룬 개념과 직접 연결된다 — 새로 리서치를 돌리지 않고 기존 산출물로 설계 가능:

- **"키워드로 찾고 링크를 타고 퍼져나가며 관련 지식을 모은다"**는 요구는 01번(Zettelkasten)이 말한 "위키링크가 폴더/태그보다 우선하는 연결 철학"과 03번(Obsidian 파워유저)이 확인한 "backlink 패널·그래프 뷰"가 정확히 이 기능을 위한 것이다. 지금까지 계획은 이 연결 구조를 "만드는 쪽"(캡처 시 링크 의무화)만 다뤘고, 그 구조를 실제로 "타고 다니며 찾는 쪽"(회수 절차)은 규칙으로 명문화한 적이 없었다
- 04번(정보 아키텍트)이 지적한 태그 대소문자 불일치(`RTT`/`rtt` 등)는 캡처 단계에서는 사소해 보였지만, 검색 프로토콜이 실제로 작동하려면 키워드 매칭의 직접적 장애가 된다 — 전수 일괄 정정은 여전히 범위 외이나, **조회 중 우연히 만난 태그 불일치는 그 자리에서 스팟 수정**하는 것을 검색 프로토콜에 포함
- 21번 검증의 최소주의 원칙(신규 필드·파일 최소화)은 개정 메커니즘에도 동일 적용 — 문서마다 별도 "개정 이력" 섹션을 새로 만들지 않고, 이미 git 저장소인 `projects/wiki`의 커밋 로그를 이력 메커니즘으로 재사용하고, `위키 반영 로그.md`에 "신규/개정" 구분과 `last_reviewed`(기존 frontmatter 필드, 활용 안 되고 있었음) 갱신만 추가

## 5. 핵심 결정

- 결정_1: **신규 "brain" 폴더는 만들지 않는다** — `projects/wiki`가 이미 동일 목적으로 존재하며(사용자 확인 완료), 검증 결과 골격 자체는 견고해 대체가 아니라 보강이 맞다
- 결정_2: **`.wiki-sync/`(3-YAML 폴링 배치 레지스트리)는 이번에 구현하지 않는다** — 06·21번이 공통으로 "실행 액터 부재/과설계" 판정. "wiki가 독립적으로 pull"이라는 은유 자체를 "세션 내 즉시 판단→제안→갱신"으로 대체
- 결정_3: **승인 큐(4상태 워크플로)는 만들지 않는다** — 21번이 지적한 자기모순(옛 실패 패턴 재현) 수용. 그 자리에서 묻고 그 자리에서 끝내는 즉시 처리 방식만 채택, 보류 상태를 추적하는 별도 큐 없음
- 결정_4: **최소 채택 집합**(21번 역제안 기반)만 계획에 반영 — 신규 frontmatter 필드 `lifecycle` 1개, `projects/wiki/운영/위키 반영 로그.md` 신규 1건(승인 상태 없는 4컬럼 기록), 프로젝트/MOC '메타' 슬롯 + 학습/운영정책 허브 신규 1건, 홈.md 코어 Bases 뷰. Dataview·Templater·태그 일괄 정정·8건 소급 채점·원자노트 파일명 강제는 보류
- 결정_5: **트리거 시점은 기존에 이미 강제되는 체크포인트에 결합** — 신규 정기 프로세스를 만들지 않고, task의 단계④ 완료(`이력 및 결과.md` '완료' 전환) 시점에 그 자리에서 wiki화 여부를 판단해 세션 인라인 텍스트로 제안
- 결정_6: **"즉시성"과 4단계 프로세스의 스코프를 계획.md에서 명문화한다** — 22번이 지적한 최우선 공백. wiki 반영 자체(문구 재작성·MOC 링크 추가)는 원 작업의 4단계 프로세스에 부수되는 경량 조치로 별도 4단계를 새로 밟지 않되, wiki **구조** 변경(카테고리 신설·스키마 변경 등)은 여전히 4단계 적용 대상
- 결정_7 (2026-07-06 추가): **"위키 배경지식 조회" 절차를 신규 root 지침으로 명문화한다** — 새 작업 착수 시(단계①~②) 키워드 grep → 매칭 문서 확인 → 위키링크를 최대 2-hop까지 따라가며 확장 → 신규 발견 0건이면 중단(loop-until-dry와 동일 수렴 조건). root 지침으로 두어 Sound1 등 모든 프로젝트 세션에서 동일 적용. 광범위 조회는 `Explore` 서브에이전트 위임 가능(서브에이전트 활용.md §2.1과 정합)
- 결정_8 (2026-07-06 추가): **wiki 반영 시 "신규 vs 개정" 분기를 추가한다** — 위키화 판단 트리거가 발동하면 먼저(결정_7의 조회 절차로) 관련 기존 문서 존재 여부를 확인한다. 있으면 내용을 병합해 **개정**(기존 문서의 `last_reviewed` 갱신, 상충 내용은 교체하고 왜 바뀌었는지 한 줄만 남김), 없으면 **신규** 작성(기존 6-Step 계획대로). 별도 개정 이력 섹션은 만들지 않고 git 커밋 로그로 이력 추적(21번 최소주의 원칙 계승)
