# 오케스트레이터 입력

**TL;DR**: 에이전트-로그 규약 신설을 위한 현황 조사 — 4노드 fan-out(루트/rules 규약·Sound1 실태 parallel + adversarial 갭 검증), Sonnet·effort max.

## 원본 입력

> "tasks/모듈/ 폴더 내에 지금은 에이전트-로그 폴더를 만들고 서브 에이전트가 산출하는 결과를 네가 잘 저장하고 있어. 여기서 내가 원하는건 더 디테일하게야. 우리가 지금 지침 업데이트를 하는 내용이, 내가 입력한 내용을 요구 분석해서 네가 더 최적의 프롬프트로 변환하는게 가장 처음이잖아. 그래서 요구분석은 네가 직접 할 수 밖에 없다고 보거든?"

이어 `AskUserQuestion`으로 "더 디테일하게"의 범위를 확정 — 은수님이 3개 모두 선택: (1) 오케스트레이터 사고 과정, (2) 노드별 입·출력 원문, (3) 위임 설계 결정 근거.

## 요구 해석

은수님 의도: 현재 `에이전트-로그/`가 "서브에이전트 산출물 저장소"에 그치는 것을, 오케스트레이션 전 과정의 감사 기록으로 격상. 특히 오케스트레이터 자신의 "입력→최적 프롬프트 변환" 사고가 지금 로그에서 누락됨을 문제로 지목. 요구 해석은 대화 당사자만 가능하므로 오케스트레이터가 직접 수행하고(§1.1), 현황 조사(②)만 위임한다. 모호점(정본 위치·강제 수위)은 조사 후 결정으로 이관.

## 위임 설계 근거

- [x] 왜 이 분해(4개 노드)인가 — 현황이 3개 독립 계층(루트 E:\Claude 지침·rules 하네스·Sound1 실태)에 흩어져 있어 각각 병렬 조사가 최적. 여기에 은수님 3요구 vs 현황 갭을 판정하는 검증 노드 1개를 더해 4노드.
- [x] 어떤 패턴·왜 — **parallel(3 조사) + adversarial-verify(1 갭)**. 조사 3계층은 상호 독립이라 배리어 병렬, 갭 노드는 3결과를 받아 은수님 3요구를 무비판 수용하지 않고 반증 시도(중복·과잉 기록 위험 지적)하는 adversarial 역할.
- [x] 모델·effort 배분·왜 — 전 노드 Sonnet · max. 규약 설계 근거가 될 정밀 조사라 최고 effort 일괄 적용(전면 위임 정책).
