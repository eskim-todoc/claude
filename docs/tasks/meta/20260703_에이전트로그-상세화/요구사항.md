# 요구사항: 에이전트-로그 상세화

**TL;DR**: 현재 `tasks/<모듈>/<작업>/에이전트-로그/`는 서브에이전트 산출물 위주로 저장된다. 이를 오케스트레이션 전 과정의 감사 기록으로 격상 — (1) 오케스트레이터 사고 과정(은수님 입력 → 요구 해석 → 최적 위임 프롬프트로의 변환), (2) 노드별 입·출력 원문, (3) 위임 설계 결정 근거(왜 이렇게 분할·이 패턴·이 모델/effort). 방금 확정한 "① 요구분석은 오케스트레이터 직접" 원칙과 §1.1 경계에 정합. 전면위임-강화의 자매 작업.

## 1. 사용자 요청

> "tasks/모듈/ 폴더 내에 지금은 에이전트-로그 폴더를 만들고 서브 에이전트가 산출하는 결과를 네가 잘 저장하고 있어. 여기서 내가 원하는건 더 디테일하게야. 우리가 지금 지침 업데이트를 하는 내용이, 내가 입력한 내용을 요구 분석해서 네가 더 최적의 프롬프트로 변환하는게 가장 처음이잖아. 그래서 요구분석은 네가 직접 할 수 밖에 없다고 보거든?"

`AskUserQuestion`으로 "더 디테일하게"의 구체 범위를 확인 → 은수님이 **3개 모두** 선택:
- **오케스트레이터 사고 과정**: 은수님 입력을 어떻게 해석하고 왜 이 분해·이 프롬프트로 위임했는지(요구 해석 → 위임 설계)를 별도 파일로 기록
- **노드별 입·출력 원문**: 각 서브에이전트에 준 프롬프트 전문 + 반환 전문 보존
- **위임 설계 결정 근거**: 왜 N개 노드로 나눴는지, 어떤 패턴(parallel/pipeline/검증)·모델·effort를 왜 선택했는지

선행 논의(본 세션)에서 "요구 해석은 서브에이전트 위임 구조적 불가(대화 채널·맥락 부재), 요구사항.md 문서화까지 위임하면 과함" 결론이 났고, 그 오케스트레이터 고유 작업이야말로 지금 로그에서 누락되는 가장 값진 부분임을 함께 확인했다. 본 작업이 그 누락을 메운다.

## 2. 목표

- 목표_1: 에이전트-로그 표준 구조를 정의하는 규약 문서를 **정본 1곳**에 신설·정비(현재 관행이 규약으로 명문화됐는지 조사 후 결정)
- 목표_2: 3종 기록(오케스트레이터 사고 과정·노드 입출력 원문·위임 설계 근거)의 파일 구성·명명·기록 시점을 규정
- 목표_3: fan-in 컨텍스트 예산(노드 반환 3줄·raw 전파 금지)과 **충돌하지 않게** 설계 — "메인 컨텍스트로는 압축 반환, 로그 파일에는 원문 보존"의 이원화 (원문은 로그에 남되 오케스트레이터 컨텍스트로는 안 올라옴)
- 목표_4: 전면위임-강화 §1.1(오케스트레이터 직접 작업 4종)과 정합 — §1.1이 규정한 "직접 작업"의 산출을 본 로그 규약이 받아 기록하는 관계 명시
- 목표_5: 루트 저장소 자기 적용 — 본 세션 3개 작업(전면위임-강화·작업목록-분산화·본 작업) 자체의 에이전트-로그를 새 규약대로 소급 정비할지 여부 결정

## 3. 수용 기준 (Definition of Done)

### 3.1 기능·산출물
- [ ] 수용기준_1: 에이전트-로그 3종 기록 규약이 정본 문서에 명시 (파일 구성·명명·기록 시점·기록 주체)
- [ ] 수용기준_2: 오케스트레이터 사고 과정 기록 양식(입력 원문 → 요구 해석 → 위임 프롬프트 변환 근거)이 템플릿으로 존재
- [ ] 수용기준_3: 노드 입출력 원문 보존 방식이 fan-in 예산과 모순 없이 규정(로그≠컨텍스트 이원화 명시)
- [ ] 수용기준_4: 위임 설계 근거 기록 항목(노드 수·패턴·모델·effort 선택 이유) 규정

## 4. 작업 범위 외 (Out of Scope)

- 범위외_1: Sound1 등 기존 완료 작업의 에이전트-로그를 새 규약으로 **소급 재작성하지 않음**(목표_5는 "본 세션 3작업" 한정 여부만 결정, 과거 18개+ 폴더 일괄 개조는 별도 작업)
- 범위외_2: 로깅 자동화 스크립트(tasks-guard.py류) 신설·개조는 별도 — 본 작업은 규약·양식 정의까지

## 5. 위임 범위 (Claude 자율 결정)

- 위임_1: 정본 문서 위치(신규 파일 vs 기존 `서브에이전트 활용.md`/`워크플로우 오케스트레이션.md` 확장) — 조사 결과 기반 결정
- 위임_2: 3종 기록의 파일 명명·분할 방식
- 위임_3: 오케스트레이터 사고 과정 양식의 구체 필드

위임 범위 밖 (사용자 결정 영역):

- 사용자결정_1: `claude_develop` 병합·push 승인
- 사용자결정_2: 목표_5(본 세션 3작업 소급 정비 여부)의 최종 판단 — 분석 후 옵션 제시 예정

> [!NOTE]
> 본 요구사항.md는 "① 요구분석 = 오케스트레이터 직접" 원칙의 **자기 적용 사례**다 — 은수님 대화 맥락을 가진 오케스트레이터가 직접 작성했고, 현황 조사(②)만 서브에이전트에 위임한다.
