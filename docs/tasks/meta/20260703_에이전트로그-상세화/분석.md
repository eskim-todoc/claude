# 분석: 에이전트-로그 상세화

**TL;DR**: Workflow fan-out(Sonnet effort:max 4노드) 조사 결과 — 루트 지침엔 에이전트-로그 규약 전무(grep 0건), rules 하네스엔 정본 §2가 도구로 강제되나 실사례에서 원문 축약, Sound1은 관행만·폴더마다 제각각. 3요구 갭: 요구3(위임 근거)=없음, 요구1·요구2=부분. adversarial 반론 2건 채택 — (1) 요구1·요구3 중복이므로 통합, (2) 요구2 입력측 전량 verbatim은 두 트랙에서 이미 폐기된 전례라 저비용 구조 필요. 결정: 신규 정본 파일 + 요구1·3 통합 서술 + 요구2 출력측 관행 추인·입력측 오케스트레이터 선Write + fan-in 이원화 명문화.

## 3. 가설·선택지

### 3.2 선택지 (설계 결정)

**쟁점 A: 정본을 신규 파일 vs 기존 지침 확장?**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 기존 `서브에이전트 활용.md`/`워크플로우 오케스트레이션.md` 확장 | 파일 수 억제 | 행동 규칙(위임 방법)과 산출물 스키마(로그 파일 구성)가 다른 층위인데 뒤섞여 비대화. 두 파일 다 이 개념을 "전유"하지 않음 |
| **신규 파일 `에이전트 로그 구조.md`** (채택) | 층위 분리, rules 하네스 선례와 정합, 하우스 스타일(성장 주제=별도 파일)과 일치 | 파일 1개 증가 |

**결정: 신규 파일** (갭 노드 권고 + 근거 4개 채택).

**쟁점 B: 요구1(사고과정)·요구3(위임 근거)을 별도 관리?** — adversarial 반론 핵심

| 선택지 | 장점 | 단점 |
|---|---|---|
| 별도 필드·별도 파일 2개 | 항목 명확 분리 | "왜 이 분해"(요구1)와 "왜 N노드"(요구3)는 사실상 같은 질문 → 매 작업 이중 기록·상호 모순 위험 |
| **통합 서술 1곳 + 요구3을 체크리스트로 흡수** (채택) | 이중 부담 제거, 은수님 3선택의 개념적 필요는 유지하되 물리적 산출물만 압축 | 없음 |

**결정: 통합** — 은수님이 3개를 고른 건 "3가지 다 필요"이지 "3개 별도 파일"이 아니라는 해석.

**쟁점 C: 요구2(노드 입출력 원문) 강제 수위?** — adversarial 반론 핵심

| 선택지 | 장점 | 단점 |
|---|---|---|
| 입력·출력 모두 전량 verbatim 의무 | 완전 재현 | 입력측 전량 강제는 rules(meta-0011·0012)·Sound1(LED 0615) **두 독립 트랙에서 시도 후 자연 폐기된 전례** → 세 번째 폐기 위험 |
| **출력측 현행 관행 추인 + 입력측 오케스트레이터 선Write + Workflow 저널 1차 소스 인정** (채택) | 저비용 구조, 이미 작동하는 관행 활용, 하네스 자동 저널 재사용 | 규약 서술이 조금 정교해짐 |

**결정: 저비용 이원 구조** — 출력은 "노드가 자기 파일 Write"(현행) 추인, 입력은 Workflow/Agent 저널(자동)을 1차 소스로 인정하고 에이전트-로그/는 큐레이션 계층. 저널이 없는 경우만 오케스트레이터 선Write.
