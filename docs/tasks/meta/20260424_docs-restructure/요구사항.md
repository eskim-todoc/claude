# 요구사항: docs 폴더 구조 세분화

**TL;DR**: 작업당 4개 문서 누적·병렬 작업·프로젝트 확산으로 flat 구조가 한계. 영속(지침/사용방법) vs 작업(`tasks/<모듈>/<작업>/`)을 분리하고, `list.md`로 활성·완료를 중앙 관리, peer 링크+feature 태그로 cross-module 연계를 표현하면서 기존 링크는 무손실 유지한다.

## 1. 배경

현재 `docs/` 폴더는 **flat 구조 + 파일명 프리픽스** 컨벤션으로 모든 문서를 관리한다.

```
docs/
├── [지침] 작업 규칙.md
├── [지침] [Git] 브랜치, 병합 규칙.md
├── [사용방법] Slack 작업 완료 알림.md
└── ... (총 9개)
```

다음 변화로 이 방식이 한계에 부딪힘:
- `feedback_code_docs_first.md` 규칙: 코딩 작업마다 `[요구사항]` / `[분석]` / `[구현계획]` 3개 문서 누적
- `feedback_parallel_orchestration.md` 규칙: 병렬 작업 증가로 동일 시점에 여러 작업 문서 공존
- 세션 간 핸드오프용 `[진행상황]` 문서 추가 → 작업당 4개로 증가
- 프로젝트(Sound1 등)에도 동일 규칙 적용 필요 (Sound1 `docs/`는 이미 22개 파일 누적)

flat 유지 시 **파일 수 폭발, 관련 작업 묶기 어려움, 활성/완료 구분 불가**.

## 2. 목표

- 작업별 문서들을 **한 폴더에 묶어** 핸드오프·탐색·정리 용이
- 영속 문서(지침·사용방법 등)와 작업 문서 **명확히 분리**
- **활성 vs 완료** 작업 구분을 `list.md`로 중앙 관리
- **cross-module 연계 작업** 표현 (peer 링크 + feature 태그)
- 전역(`E:\Claude\docs\`)과 각 프로젝트(`projects/<이름>/docs/`)에 **동일 규칙 적용**
- 기존 문서 **링크·참조 무손실 유지** (CLAUDE.md 포함)

## 3. 비목표 (out of scope)

- 기존 문서 **내용** 수정 — 이 작업은 순수 구조 변경만 (규칙 본문 갱신은 예외)
- 커밋/병합 실행 — 사용자 **"작업 끝났어. 마무리해"** 시그널 수신 전까지 대기
- Sound1 실제 migration 실행 — 후속 작업으로 `list.md`에 등재만 (본 세션 실행 X)

## 4. 새 구조

```
docs/
├── 지침/
│   ├── 작업 규칙.md                       (마스터 체크리스트)
│   ├── 일반/
│   │   ├── 커뮤니케이션 규칙.md
│   │   └── 문서 작성 규칙.md
│   ├── Git/
│   │   ├── 브랜치, 병합 규칙.md
│   │   └── 워크플로우.md
│   └── 코딩/
│       ├── 작업 규칙.md
│       ├── 네이밍 컨벤션.md
│       └── 분석·디버깅 규칙.md
├── 사용방법/
│   └── Slack 작업 완료 알림.md
└── tasks/
    ├── list.md                            (작업 레지스트리)
    └── <모듈>/
        └── <작업슬러그>/
            ├── 요구사항.md
            ├── 분석.md
            ├── 구현계획.md
            └── 진행상황.md
```

## 5. 핵심 규칙

### 5.1 영속 문서
- 유형별 폴더(`지침/`, `사용방법/`)가 **분류 역할**을 겸함
- 파일명에서 프리픽스 `[지침]`, `[사용방법]` 제거
- 필요 시 하위 카테고리 폴더(`지침/일반/`, `지침/Git/`, `지침/코딩/`)로 2레벨까지 허용
- 프로젝트 확장 카테고리 예: `기준/`, `참고/`, `이력/` (Sound1 migration 시 추가 예정)

### 5.2 작업 문서
- 경로: `tasks/<모듈>/<작업슬러그>/`
- **2레벨 고정**: `모듈/작업슬러그` — 모듈 하위 서브토픽은 폴더가 아닌 **list의 태그**로 표현
  - 예: LED의 brightness·dimming·pattern은 서브폴더 X, 태그 `[brightness, dimming, pattern]`로 관리
  - 이유: 3레벨은 경계 판단 애매(한 작업이 복수 서브토픽에 걸침)해서 분류 경직화 위험
- 필수 파일: `요구사항.md`, `분석.md`, `구현계획.md`
- 선택 파일: `진행상황.md`, `이력 및 결과.md`, 첨부 이미지·로그 등
- 작업 슬러그는 **kebab-case 영문** 권장 (경로 다루기 용이). 한글도 허용하되 의미 명확할 때만
- 모듈 이름은 **도메인 용어** (예: 루트 = `meta`/`git`/`docs`/`tools`, Sound1 = `LED`/`touch`/`power`)

### 5.3 list.md — 작업 레지스트리
- 경로: `tasks/list.md`
- 활성(`## 활성`)·완료(`## 완료`) 섹션 분리
- 각 섹션 마크다운 테이블:

```markdown
## 활성
| 작업명 | 모듈 | 태그 | 폴더 | 상태 | 시작일 | 연계 | 요약 |
|---|---|---|---|---|---|---|---|
| docs 폴더 구조 세분화 | meta | docs, convention | [meta/docs-restructure](meta/20260424_docs-restructure/) | 진행 | 2026-04-24 | - | 계층·list·태그 도입 |

## 완료
| 작업명 | 모듈 | 태그 | 폴더 | 상태 | 시작·완료 | 연계 | 요약 |
|---|---|---|---|---|---|---|---|
```

### 5.4 cross-module 연계 표현
- **peer-to-peer**: 각 행의 `연계` 컬럼에 대상 작업 마크다운 링크. 양쪽 작업이 symmetric하게 서로 참조
- **feature 그룹**: 3개 이상 작업이 한 상위 기능을 구성하면 공통 태그 `feature:<이름>` 부착. 태그 검색으로 그룹 조회
- 두 방식은 병행 가능

### 5.5 갱신 이벤트 (자동 동기화 대상)
- 작업 시작 → `list.md` 활성 섹션 행 추가 (폴더 생성과 동시)
- `진행상황.md` 갱신 → 해당 행의 요약·상태 업데이트
- 사용자 완료 시그널 수신 → 활성 → 완료 섹션으로 이동, 완료일 기록

### 5.6 새 작업 라우팅 절차
사용자가 새 작업을 지시하면:
1. Claude가 먼저 해당 스코프(루트 or 프로젝트)의 `list.md` 조회
2. 같은 모듈·태그의 관련 작업이 있으면 사용자에게: **"기존 `<폴더>`에서 이어가시겠어요, 신규 분리하시겠어요?"** 확인
3. 확인 후 기존 폴더에서 계속 or 신규 폴더 생성

### 5.7 스코프 독립성
- 전역: `E:\Claude\docs\tasks/list.md`
- 프로젝트별: `projects/<이름>/docs/tasks/list.md`
- 각 스코프별 독립 레지스트리, 프로젝트 작업은 해당 프로젝트 list에만 등재
- cross-scope 연계는 이번 단계에선 peer 링크만 허용 (absolute 경로). feature 전용 폴더는 YAGNI
