# 요구사항: Archive 모듈 인덱스 신설 (Wiki sync 기반)

**TL;DR**: 각 repo의 `docs/tasks/_archive/` 폴더 안에 `모듈 현황.md` 단일 인덱스 파일을 두고, 모듈별 **최종 업데이트 날짜 + 최근 작업 링크**를 표 형식으로 관리한다. 적용은 루트 + 4 프로젝트(Wiki 제외), 초기 채움은 기존 archive 일괄 스캔, 갱신은 작업 종료(archive 처리) 흐름에 한 단계 추가해 Claude가 자동 수행한다. Wiki는 이 파일 1개만 Read해 `last_synced` 와 비교, 변경된 모듈만 재정리 — incremental sync 인프라.

## 1. 사용자 요청

사용자 지시 원문:

> "루트 및 프로젝트 docs 밑에 아카이브 밑에 모듈 별로 끝난 내용이 저장되잖아. 앞으로 wiki는 이 폴더들을 기반으로 내용을 채워나갈 생각이야. 그래서 모듈 별로 최종 업데이트 날짜가 언제인지를 작성해서, wiki 측에서는 이 날짜가 수정되었는지만 판별해도, 자신이 업데이트할 문서가 있는지를 알 수 있을 거 같거든?"
>
> 합의 답변:
> - **저장 방식**: 옵션 C — 각 repo `docs/tasks/_archive/모듈 현황.md` 중앙 인덱스 파일 (1 repo = 1 파일)
> - **적용 범위**: 루트 + 모든 프로젝트 (Sound1·auto-rtt-viewer·ez8300-study·sound1-fw-extractor). Wiki 자신 제외(`docs/tasks/` 미사용)
> - **갱신 방식**: Claude 작업 종료(archive 처리) 시 자동

## 2. 목표

### 요구사항_1 — `모듈 현황.md` 위치·포맷

| 항목 | 내용 |
|---|---|
| 위치 | `docs/tasks/_archive/모듈 현황.md` (각 repo 1개) |
| frontmatter | name·purpose·type=`tasks/메타`·applies_to·tags (영속 문서 정책 준수) |
| TL;DR | 본 파일의 역할·운영 정책 80~250자 |
| 본문 핵심 | 모듈 표(`모듈 \| 최종 업데이트 \| 최근 작업 \| 작업 수`) — 모듈 행 1줄씩 |
| 정렬 | 최종 업데이트 **내림차순** (최근에 변경된 모듈이 위) |

### 요구사항_2 — 표 컬럼 정의

| 컬럼 | 내용 | 예 |
|---|---|---|
| 모듈 | 모듈명 (archive 폴더명 그대로) | `meta`, `LED`, `touch` |
| 최종 업데이트 | 해당 모듈 내 가장 최근 작업의 **완료일**(YYYY-MM-DD) | `2026-05-15` |
| 최근 작업 | 최종 업데이트 일자의 작업 폴더 상대링크 | `[wiki-bootstrap](meta/20260427_wiki-bootstrap/)` |
| 작업 수 | 해당 모듈 아래 archive된 작업 개수 | `8` |

|---|---|
| 루트 (`E:\Claude`) | `docs/tasks/_archive/모듈 현황.md` |
| `projects/Sound1` | `docs/tasks/_archive/모듈 현황.md` (※ 폴더 존재 시) |
| `projects/auto-rtt-viewer` | 동일 |

### 요구사항_4 — 초기 채움 (기존 archive 일괄)

- 모든 적용 대상 repo의 `_archive/<모듈>/<작업>/` 폴더를 스캔
- 각 모듈의 `이력 및 결과.md` frontmatter 또는 본문 `기간`에서 **완료일** 추출
- 모듈 단위 `max(완료일)` + 해당 작업 링크로 표 행 생성
- 작업 수는 폴더 개수

### 요구사항_5 — 갱신 자동화 (작업 진행 규칙 §6 패치)

[`작업 진행 규칙.md §6.1`](../../../지침/일반/작업%20진행%20규칙.md) archive 처리 절차에 한 단계 추가:

| 기존 단계 | 추가 단계 |
|---|---|
| 1. 이력 및 결과.md 작성 | (변경 없음) |
| 2. `git mv` → `_archive/...` | (변경 없음) |
| 3. `작업 목록.md` 활성→완료 이동 | (변경 없음) |
| **(신규)** 4. `모듈 현황.md` 해당 모듈 행 갱신 | 최종 업데이트 = 본 작업 완료일, 최근 작업 = 본 작업 폴더, 작업 수 += 1 (또는 신규 모듈이면 행 추가) |
| 5. 커밋 → 사용자 승인 → `--no-ff` 병합 | (변경 없음) — 커밋에 `모듈 현황.md` 변경도 포함 |

### 요구사항_6 — 갱신 규칙

| 케이스 | 처리 |
|---|---|
| 신규 모듈 첫 작업 archive | 표에 신규 행 추가 |
| 기존 모듈에 새 작업 archive | 해당 행의 최종 업데이트·최근 작업·작업 수 갱신 |
| archive 내 기존 작업 수정 (드문 케이스) | 본 작업 외 — 별도 정책으로 후속 검토 (요구사항_6.1) |
| 작업 archive 취소·삭제 (매우 드문) | 본 작업 외 — 별도 정책 |

#### 요구사항_6.1 — archive 파일 수정 추적은 본 작업 범위 외

기존 archive 내 파일을 수정하는 경우(예: `이력 및 결과.md` 보정)는 본 인덱스에서 추적하지 않는다. 사유:
- archive는 "완료된 작업의 동결 산출물"이라 수정이 드뭄
- 매 파일 수정마다 인덱스 갱신은 자동화 부담
- 필요해지면 후속 작업으로 정책 추가

### 요구사항_7 — 모듈 식별자

- 본 인덱스는 각 repo 내부에서만 모듈을 식별 → **모듈명만으로 충분** (스코프는 인덱스 파일 위치로 자명)
- Wiki 측이 5 repo의 인덱스를 통합 사용할 때는 Wiki 자체에서 `<repo>/<module>` 키로 합성 (본 작업 외)

### 요구사항_8 — 지침 패치

| 파일 | 변경 |
|---|---|
| `docs/지침/일반/작업 진행 규칙.md` §6.1 | archive 처리 4단계 → 5단계 (`모듈 현황.md` 갱신 추가) |
| `docs/지침/일반/문서 작성 규칙.md` §3.4 | archive 절차에 `모듈 현황.md` 한 줄 추가 |
| `docs/지침/일반/프로젝트 초기 세팅.md` §2.3 | 신규 프로젝트의 표준 폴더에 `_archive/` + `모듈 현황.md` 빈 인덱스 옵션 명시(또는 첫 archive 시 자동 생성으로 두기 — 분석에서 결정) |
