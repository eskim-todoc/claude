## 완료 요약

### 무엇을 했는가

각 repo의 `docs/tasks/_archive/` 폴더에 모듈별 최종 업데이트 날짜·최근 작업·작업 수를 표 형식으로 누적하는 단일 인덱스 파일 `모듈 현황.md`를 신설했다. 5 repo(루트 + Sound1·auto-rtt-viewer·ez8300-study·sound1-fw-extractor) 각각 1 파일씩 총 5개, 초기 채움은 기존 archive 작업 32건(`이력 및 결과.md`의 완료일 기준)을 분석해 모듈 단위로 집계했다. Wiki 등 외부 소비자는 본 파일만 Read해 마지막 sync 시점과 비교, 변경된 모듈만 재정리할 수 있다 — incremental sync 진입판단용 인프라.

갱신 자동화를 위해 지침 3건을 패치했다:
- [`작업 진행 규칙.md §6.1`](../../../지침/일반/작업%20진행%20규칙.md): archive 처리 5단계 → 6단계 (`모듈 현황.md` 갱신 단계 추가, 본 작업이 첫 사용 사례)
- [`문서 작성 규칙.md §3.4.1`](../../../지침/일반/문서%20작성%20규칙.md): 동기적으로 4단계 → 5단계
- [`프로젝트 초기 세팅.md §2.3`](../../../지침/일반/프로젝트%20초기%20세팅.md): 신규 프로젝트의 `_archive/`·`모듈 현황.md`는 첫 archive 처리 시 자동 생성(미리 만들지 않음) NOTE 추가

### 핵심 결정

- **저장 방식 옵션 C(중앙 인덱스 파일)** 채택 — 분산 마커(옵션 B)는 파일 수 증가 부담, 집계 도출(옵션 A)은 Wiki 측 스캔 비용 ↑, 작업 목록.md 확장(옵션 D)은 작업 단위 vs 모듈 단위 의미 중첩 — 중앙 1 파일이 Wiki 측 비용·인프라 트레이드오프 최적
- **모듈 식별자는 모듈명만** — repo scope는 파일 위치로 자명. Wiki 측이 5 repo 인덱스를 통합할 때 `<repo>/<module>` 키 합성은 Wiki 측 담당
- **정렬 3단계 기준** — 최종 업데이트 내림차순 → 작업 수 내림차순 → 모듈명 사전순. 가독성·활발도 우선
- **archive 파일 수정 추적은 본 작업 외** (요구사항_6.1) — archive는 동결 산출물이라 수정 드묾, 매 수정 추적은 자동화 부담
- **신규 프로젝트의 빈 인덱스 미리 안 만들기** — 완료 작업 0건 상태에서 빈 인덱스는 노이즈, 첫 archive 시 자동 생성

### 후속 영향

- Wiki(`projects/wiki/`) sync 메커니즘은 본 작업이 제공한 인프라 위에서 별도 구현 — Wiki 콘텐츠 운영 단계(사용자 영역)
- 모든 후속 archive 처리는 [`작업 진행 규칙.md §6.1`](../../../지침/일반/작업%20진행%20규칙.md) 5번 단계로 `모듈 현황.md` 자동 갱신
- archive 내 파일 *수정* 추적 정책은 필요 시 별도 작업으로 후속 검토 (요구사항_6.1)
