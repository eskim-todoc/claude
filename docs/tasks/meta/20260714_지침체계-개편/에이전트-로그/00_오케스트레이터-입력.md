# 오케스트레이터 입력 — maturity 제거 fan-out (Step1d)

**TL;DR**: 지침 27파일의 maturity 제거를 general-purpose 3노드(parallel 패턴)로 병렬 위임. SSOT·인덱스·헌법(메인 직접)과 재작성 대상(Step2)을 제외한 순수 기계 삭제 대상만 fan-out. 은수님 지적("실제로 로그 안 남긴다")의 즉시 교정 시연.

## 1. 원본 입력 (오케스트레이터가 받은 지시)

> "지침에서 더 이상 maturity 기능은 필요 없어 … 전체 내용에서 maturity 관련 내용은 전부 제거하자." (은수님, 2026-07-14)
> + "지금 입력하는 작업을 최대한 빠르게 처리하기 위해 필요하다면 서브에이전트를 적극 활용해."

상위 작업: [`../계획.md`](../계획.md) Step1. 승인: "바로 해"(2026-07-14).

## 2. 요구 해석 (왜 이렇게 분해했는가)

- maturity 제거는 **명확·유한·기계적**(frontmatter 줄 삭제 + 인라인 마커 삭제 + 산문 정리)이라 노드별 독립 처리 가능 → parallel 패턴 적합.
- 단, **정합성 리스크가 큰 파일**(SSOT `메타-frontmatter.md`, 인덱스 README 3종, 헌법 `CLAUDE.md`)은 내부 §연쇄가 있어 메인이 직접 정밀 수정 → fan-out 제외.
- **Step2에서 전면 재작성(Write 교체)될 파일**(4단계-프로세스.md, 양식 4개)은 재작성 시 maturity 없이 새로 쓰므로 fan-out 제외(중복 방지).
- 남은 27파일을 3노드에 균등 분할(복잡 파일 10 + 단순 frontmatter 17 → 노드당 복잡 3~4 + 단순 5~7).

## 3. 위임 설계 근거 (체크 — 각 항목 1문장 근거 필수)

- [x] **노드 수(3)**: 27파일을 9개씩 — 노드당 컨텍스트 부담 적고 병렬 슬롯(≤~10) 내. 파일 수 대비 과분할·과소분할 회피.
- [x] **패턴(parallel)**: 노드 간 의존 없음(각자 다른 파일 그룹). fan-in은 grep 검증 1회로 수렴. pipeline 불필요.
- [x] **모델·effort(sonnet·미지정)**: 지침 §5 — 기계적 삭제라 Sonnet adaptive로 충분, max 고정 금지(폭주 방지).
- [x] **로그(본 폴더)**: 각 노드가 결과를 `NN_<그룹>.md`에 직접 Write(로그 구조.md §4). 오케가 반환값을 대필하지 않음.
- [x] **폭주 가드**: 유한 파일 목록·명확 종료조건(grep 0). 산출 없이 부푸는 노드는 TaskStop→메인 폴백.
