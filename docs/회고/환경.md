# 환경 회고

**TL;DR**: 설정·스크립트는 Project scope (`.claude/settings.json`) + git tracked. User scope·하드코딩 금지. 자격증명·로컬 전용은 `credentials/` 또는 `settings.local.json`.

설정·스크립트·훅의 환경 이식성 관련 학습.

## 환경 이식성 우선 (2026-04-21)

작업 산출물(설정 파일, 스크립트, 훅 등)은 어느 환경에서든 동일한 작업 상태를 유지할 수 있도록 설계.

**Why:** 사용자가 여러 PC/환경을 오가며 작업하며, `E:\Claude` 폴더를 복제해서 동일한 컨텍스트를 가져가는 워크플로우를 씀. `CLAUDE.md` 첫 줄에도 *"이 폴더를 복제하면 다른 환경에서도 컨텍스트 유지 가능"*으로 명시.

**How to apply:**
- Claude Code 설정은 User scope(`~/.claude/settings.json`)가 아니라 Project scope(`E:/Claude/.claude/settings.json`)에 둬서 git 추적 대상으로 만든다
- 공용 스크립트는 `E:/Claude/tools/`에 둔다
- 경로는 하드코딩하지 말고 `$CLAUDE_PROJECT_DIR` 환경변수를 사용한다
- 자격증명·로컬 전용 값만 `.claude/settings.local.json`이나 `credentials/`에 둔다
- 플랫폼 종속 스크립트(PowerShell 등)라도 경로만 이식 가능하면 일단 Project scope에 두고, 이식성 한계는 주석이나 docs에 명시

## 글로벌 강제 vs 이식성 trade-off — 다층 안전망 (2026-05-06)

"모든 cwd에서 강제"가 필요한 행동(예: 새 세션 시작 시 cwd `CLAUDE.md` 명시 재확인)은 Project scope만으론 불가. User scope를 함께 써야 하므로 이식성 원칙을 부분 양보. 단 단일 layer가 아닌 **다층 안전망**으로 구성한다:

1. Project scope: 루트 `CLAUDE.md` 텍스트 지침 (git tracked, 본 프로젝트 cwd 한정)
2. User scope text: 글로벌 `~/.claude/CLAUDE.md` (모든 cwd에 적용, git outside)
3. User scope hook: 글로벌 `~/.claude/settings.json`의 `SessionStart` 훅 (시스템 차원 강제, git outside)

**Why:** Project scope (1)만으론 다른 cwd에서 적용 불가. 텍스트 지침 (1)(2)은 LLM 준수에 의존하므로 hook (3)으로 시스템 강제를 한 layer 더 추가. 동시에 User scope 한계(다른 PC 비동기화)를 인정하고 Project scope에서도 동일 규칙을 명시해 사용자가 본 repo만 복제해도 의도가 보이도록.

**How to apply:**
- 행동 적용 범위가 "모든 Claude Code 세션"이면 User scope 불가피 — 단 Project scope에도 같은 규칙 텍스트로 남겨 의도가 git history에 추적되게 한다
- 새 PC 세팅 시 User scope 동기화는 수동(또는 별도 setup 스크립트). 이식성 양보를 보완하려면 `tools/`에 setup 스크립트 + 사용방법 docs 추가
- 행동 적용 범위가 "이 프로젝트만"이면 기존 원칙대로 `.claude/settings.json` (Project scope) 사용 — User scope 금지

## 자기설정 수정 가드 — `/update-config` 위임 (2026-05-06)

Claude가 자기 `~/.claude/settings.json`을 `Edit` 도구로 직접 수정하려 하면 보안 정책("Self-Modification of agent configuration")으로 자동 차단된다. 우회 시도 금지 — 사용자가 `/update-config` 슬래시 커맨드를 명시 호출해야 권한이 부여되고 그 후에만 Edit 가능.

**Why:** Claude가 자율적으로 자기 hook이나 권한 규칙을 추가하면 사용자가 모르는 사이 시스템 동작이 바뀔 수 있음. 명시적 슬래시 커맨드 호출이 사용자 의도 확인의 anchor.

**How to apply:**
- settings.json 변경이 필요하면 사용자에게 `/update-config` 호출을 요청하거나 패치 내용을 보여주고 직접 수정을 요청한다
- 차단된 Edit을 우회하려고 PowerShell·python·sed 등 다른 도구로 settings.json을 쓰는 건 가드의 의도를 깨는 우회 — 금지
- Project scope `.claude/settings.json` (cwd repo 내) 수정은 자기설정이 아니라 일반 파일 수정이므로 가드 대상 아님

## RTT 출력 누락 시 측정 환경 1순위 의심 (2026-05-06)

펌웨어 디버그 트레이스가 _코드 흐름상 호출되어야 하는데_ 누락되면 "코드가 그 라인에 도달 못 했다" 가설로 분기하기 전에 **RTT 채널 throughput 한계** 를 1순위로 의심한다. 짧은 시간에 다량 출력 시 (수백 byte / ms) 저속 RTT (예: 400 kHz) 에서 byte drop 발생, 줄 단위 누락처럼 보임.

**Why:** Sound1 V10 SPI race 측정 트레이스 작업에서 watchdog 시 `[TX] ENTER` ~ `[TX] DONE-EXIT` 5개 트레이스 + `[SPI TX]` + `[FAKE_0x34 EXIT-DMA]` 가 모두 누락 → `__WFE()` 무한 wait 가설, `writeDataToSpiTxBuff()` 진입 못 함 가설, fault 발생 가설 등 다수 분기. RTT 1000 kHz 로 올린 후 동일 빌드에서 모든 트레이스 정상 출력 → CM3 측 코드는 _처음부터_ 정상이었음. 코드 분석 시간 큰 낭비. 사용자 직접 발견: *"RTT 연결을 속도 400K로 하니까 안나오던 메시지가 1000K로 연결하니까 나오는데?"*

**How to apply:**
- 디버그 트레이스 출력 누락 발견 시 첫 의심 = **RTT 측정 환경 (속도, buffer 크기)** — 코드 분석 전 RTT 속도 한 단계 올려서 재측정
- 짧은 시간에 다량 출력 (수백 byte / 수 ms) 가 예상되면 **처음부터 RTT 1000 kHz 이상** 사용. 4 kHz / 400 kHz 디폴트 회피
- RTT buffer (보통 1024 B) 가 main thread 의 ci_print 출력 + ISR 출력으로 동시 압박될 때 drop 가능 — 출력량 분석 + 필요 시 buffer 크기 증가
- RTT 출력 누락 = 코드 도달 실패라는 결론은 **RTT 속도 변경 후에도 누락 재현** 시에만 내릴 수 있음
- 가설 분기 (예: `__WFE` wait, fault, 호출 실패) 를 작성하기 전 RTT 환경 점검 1단계 추가 — _Why_ 에 시간 낭비 사례 있음
