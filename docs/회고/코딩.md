# 코딩 회고

**TL;DR**: 비차단/ISR 기반 서브시스템에 동기 폴링 구현 회피 (호출자 즉시 return + ISR step 패턴 우선).

코드 작성 시 사용자 의도와 어긋날 수 있는 패턴, 검증된 설계 결정의 학습 누적.

## 비차단/ISR 기반 시스템에서 동기 블로킹 폴링 회피 (2026-04-27)

이벤트/ISR 기반 서브시스템(LED, timer, 통신 등)에 새 함수 추가 시 `for { step(); delay_ms(1); }` 형 동기 블로킹 폴링 구현을 회피한다. 호출자는 즉시 return, ISR 이 매 tick step 을 진행하는 상태머신 패턴을 우선 적용한다.

**Why:** 사용자는 LED 시스템을 *"메인 코어가 LED 처리에 갇히지 않는"* 비차단 ISR 기반으로 설계함. Claude 가 LED `operation-scheme` 작업 중 `turnOffLED` / `led_force_fade_off` 를 30 / 40 ms 동기 폴링(`for { LED_OUT(); delay_ms(1); }`)으로 구현 — 게다가 ISR 을 `s_led_isr_suspended = true` 로 멈춰놓고 직접 폴링하는 거꾸로 된 구조가 됨. 후속 `LED/non-blocking-fade-off` 작업에서 ISR 상태머신 변환 + 잠재 버그(suspended 영구 set 이 폴링 끝에서 풀리던 의도-구현 불일치) 자연 해소.

**How to apply:**
- 비차단/ISR 기반 서브시스템에 fade·전환·sequence 형 함수 추가 시: **호출자 즉시 return + ISR step 진행** 패턴 우선 적용
- 폴링이 필요해 보이는 케이스 (예: ISR 미활성 시점 호출): **즉시 완료 분기** 또는 **ISR 활성 여부 검사 후 분기** 로 처리, 폴링 fallback 도입 회피
- "단순화 위해 폴링" 충동 시 자가 점검: 호출자 측 main loop 가 그 시간 동안 무엇을 진행할 수 있는지 먼저 분석. main loop 가 다른 작업을 동시 진행할 수 있다면 폴링은 그 **병렬화 가능성을 막는 안티패턴**
- 설계 의도가 모호하면 구현 전 사용자에게 명시 확인 (*"이 함수 동기 폴링 vs ISR step, 어느 쪽?"*)
- 기존 서브시스템에 새 함수 추가 시: 기존 함수들이 어떤 패턴을 따르는지 (ISR 기반인지 폴링인지) 먼저 확인해서 일관성 유지

## Peripheral 클럭 체인을 시스템 클럭과 동일시하지 않기 (2026-04-30)

Cortex-M MCU 의 peripheral (Timer / ADC / DMA / I2C / UART 등) 은 시스템 클럭 직결이 아니라 분주된 sub-clock (SLOWCLK, ADCCLK, UCLK 등) 기반인 경우가 많다. peripheral 의 reload·timing 매개변수는 SDK 헤더의 클럭 체인 주석 / 공식을 먼저 확인한 후 계산한다. 또한 부트로더 / minimal context 에 ISR 기반 모듈을 추가하면 기존 코드의 **클럭 분주 설정 자체도 함께 가져와야** 한다.

**Why:** Sound1 `LED/bootloader-power-on-indicator` (Step 2 → Step 3) 에서 RSL10 General Timer 의 reload 값을 시스템 클럭 30.72 MHz 기준 계산 (`reload = 30.72 MHz / 100 kHz - 1 = 307`). 사용자 1 차 측정 오동작. [`ci_timer.h:56`](../../projects/Sound1/src/2__cm3/Gen1_5/common/ci_timer.h) 의 공식 `T = 2^prescale × (tick+1) / 40 kHz   (SLOWCLK = 1.28 MHz 기준)` 발견 — 실제 Timer base clock = **SLOWCLK / 32 = 40 kHz**. 또한 부트로더는 CM3 [`ci_power.c:154-156`](../../projects/Sound1/src/2__cm3/Gen1_5/common/ci_power.c) 의 D_CLK 분주 설정 (`SLOWCLK_PRESCALE_24 → SLOWCLK = 1.28 MHz`) 을 안 해서 SLOWCLK 자체가 디폴트값으로 동작 — 이중 문제. Step 3 보정으로 정상 동작.

**How to apply:**
- Peripheral 의 reload·timing 매개변수 계산 전: SDK 헤더의 클럭 체인 주석·공식 (`T = ... / N kHz` 등) 확인. 시스템 클럭 직결 가정 ❌
- ISR 기반 신규 모듈을 부트로더 / minimal context 에 추가 시: 기존 코드 (CM3 등) 의 클럭 분주 설정 (`D_CLK->CFG_*` 또는 동등) 을 함께 가져와야 함. 부트로더가 polling 기반이라 분주에 둔감하더라도 새 ISR 가 분주된 sub-clock 에 의존
- 클럭 분주 설정 후 안정화 대기 (`delay_ms(5)` 등) 도 동반 — 기존 코드 주석에 명시된 시간 그대로 차용
- 측정 시 ISR 주기 / PWM 주기가 의도와 배수 (4 배, 24 배, 32 배 등 분주 비율) 차이로 어긋나면 **클럭 체인 의심 1 순위**
- 디버깅 단서: SDK 헤더의 "Very important!" / "반드시 ... 로 설정" 류 주석 (예: ci_timer.h:31, ci_power.c:154) 은 클럭 분주 가정의 위치를 알려줌. 새 모듈이 그 가정을 공유하는지 확인
