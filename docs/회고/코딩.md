# 코딩 회고

**TL;DR**: 비차단/ISR 기반 서브시스템에 동기 폴링 구현 회피 (호출자 즉시 return + ISR step 패턴 우선).

코드 작성 시 사용자 의도와 어긋날 수 있는 패턴, 검증된 설계 결정의 학습 누적.

## 비차단/ISR 기반 시스템에서 동기 블로킹 폴링 회피 (2026-04-27)

이벤트/ISR 기반 서브시스템(LED, timer, 통신 등)에 새 함수 추가 시 `for { step(); delay_ms(1); }` 형 동기 블로킹 폴링 구현을 회피한다. 호출자는 즉시 return, ISR 이 매 tick step 을 진행하는 상태머신 패턴을 우선 적용한다.

**Why:** 사용자는 LED 시스템을 *"메인 코어가 LED 처리에 갇히지 않는"* 비차단 ISR 기반으로 설계함. Claude 가 LED `operation-scheme` 작업 중 `turnOffLED` / `led_force_fade_off` 를 30 / 40 ms 동기 폴링(`for { LED_OUT(); delay_ms(1); }`)으로 구현 — 게다가 ISR 을 `s_led_isr_suspended = true` 로 멈춰놓고 직접 폴링하는 거꾸로 된 구조가 됨. 후속 `LED/non-blocking-fade-off` 작업에서 ISR 상태머신 변환 + 잠재 버그(suspended 영구 set 이 폴링 끝에서 풀리던 의도-구현 불일치) 자연 해소.

**How to apply:**
- 비차단/ISR 기반 서브시스템에 fade·전환·sequence 형 함수 추가 시: **호출자 즉시 return + ISR step 진행** 패턴 우선 적용
- 폴링이 필요해 보이는 케이스 (예: ISR 미활성 시점 호출): **즉시 완료 분기** 또는 **ISR 활성 여부 검사 후 분기** 로 처리, 폴링 fallback 도입 회피
- "단순화 위해 폴링" 충동 시 자가 점검: 호출자 측 main loop 가 그 시간 동안 무엇을 진행할 수 있는지 먼저 분석. main loop 가 다른 작업을 동시 진행할 수 있다면 폴링은 그 **병렬화 가능성을 막는 안티패턴**
- 설계 의도가 모호하면 구현 전 사용자에게 명시 확인 (*"이 함수 동기 폴링 vs ISR step, 어느 쪽?"*)
- 기존 서브시스템에 새 함수 추가 시: 기존 함수들이 어떤 패턴을 따르는지 (ISR 기반인지 폴링인지) 먼저 확인해서 일관성 유지

## Peripheral 클럭 체인을 시스템 클럭과 동일시하지 않기 (2026-04-30)

Cortex-M MCU 의 peripheral (Timer / ADC / DMA / I2C / UART 등) 은 시스템 클럭 직결이 아니라 분주된 sub-clock (SLOWCLK, ADCCLK, UCLK 등) 기반인 경우가 많다. peripheral 의 reload·timing 매개변수는 SDK 헤더의 클럭 체인 주석 / 공식을 먼저 확인한 후 계산한다. 또한 부트로더 / minimal context 에 ISR 기반 모듈을 추가하면 기존 코드의 **클럭 분주 설정 자체도 함께 가져와야** 한다.

**Why:** Sound1 `LED/bootloader-power-on-indicator` (Step 2 → Step 3) 에서 RSL10 General Timer 의 reload 값을 시스템 클럭 30.72 MHz 기준 계산 (`reload = 30.72 MHz / 100 kHz - 1 = 307`). 사용자 1 차 측정 오동작. [`ci_timer.h:56`](../../projects/Sound1/src/2__cm3/Gen1_5/common/ci_timer.h) 의 공식 `T = 2^prescale × (tick+1) / 40 kHz   (SLOWCLK = 1.28 MHz 기준)` 발견 — 실제 Timer base clock = **SLOWCLK / 32 = 40 kHz**. 또한 부트로더는 CM3 [`ci_power.c:154-156`](../../projects/Sound1/src/2__cm3/Gen1_5/common/ci_power.c) 의 D_CLK 분주 설정 (`SLOWCLK_PRESCALE_24 → SLOWCLK = 1.28 MHz`) 을 안 해서 SLOWCLK 자체가 디폴트값으로 동작 — 이중 문제. Step 3 보정으로 정상 동작.

**How to apply:**
- Peripheral 의 reload·timing 매개변수 계산 전: SDK 헤더의 클럭 체인 주석·공식 (`T = ... / N kHz` 등) 확인. 시스템 클럭 직결 가정 ❌
- ISR 기반 신규 모듈을 부트로더 / minimal context 에 추가 시: 기존 코드 (CM3 등) 의 클럭 분주 설정 (`D_CLK->CFG_*` 또는 동등) 을 함께 가져와야 함. 부트로더가 polling 기반이라 분주에 둔감하더라도 새 ISR 가 분주된 sub-clock 에 의존
- 클럭 분주 설정 후 안정화 대기 (`delay_ms(5)` 등) 도 동반 — 기존 코드 주석에 명시된 시간 그대로 차용
- 측정 시 ISR 주기 / PWM 주기가 의도와 배수 (4 배, 24 배, 32 배 등 분주 비율) 차이로 어긋나면 **클럭 체인 의심 1 순위**
- 디버깅 단서: SDK 헤더의 "Very important!" / "반드시 ... 로 설정" 류 주석 (예: ci_timer.h:31, ci_power.c:154) 은 클럭 분주 가정의 위치를 알려줌. 새 모듈이 그 가정을 공유하는지 확인

## 환경 변경 단서가 있을 때 코드 결함보다 환경 가설 우선 검증 (2026-05-07)

사용자가 신고와 함께 **환경 변경**(보드 교체·전원·온도·펌웨어 버전 등) 단서를 흘리면, 코드 결함 가설보다 **환경 트리거 가설을 우선 검증**한다. 코드 동작 분석이 정확하더라도 우선순위가 어긋나면 사용자에게 *"디자인 결함입니다"* 식의 잘못된 진단을 전달하게 된다.

**Why:** Sound1 터치 센서 롱터치 stuck 신고 — 사용자 1차 메시지에 *"내부기 연결된 상태에서 롱터치 이벤트 클리어가 안 되는 것 같다"* 표현. Claude 가 [`tdc_touch.c:proc_long_touch`](../../projects/Sound1/src/2__cm3/Cortex-M3-src/systemControl/tdc_touch.c) 의 `s_is_long_touch` 플래그가 TOUCH → NOT_TOUCH 전이로만 클리어되는 동작을 정확히 짚었으나, 이를 "디자인 결함" 으로 단정하여 수정 방향까지 제시. 사용자가 2차 메시지에서 *"보드 환경이 바뀌어서 터치 센서가 계속 눌림 상태로 동작"* 이라고 환경 단서를 명시한 후에야 진짜 root cause 가 드러남 — 새 보드의 정전용량 베이스라인이 안 맞아 IQS323 의 `ch0_touch` 비트가 영구 1, NOT_TOUCH 전이 자체가 발생 안 함. ATI 보상값 재측정 (`TDC_DRV_IQS323_ATI_DUMP_ENABLE 1` 토글 → RE-ATI 덤프 → 새 보드 보상값 확보) 으로 해결. 코드 동작은 정상이었음.

**How to apply:**
- 1차 신고에 환경 변경 단서 (보드·시제품·전원·온도·펌웨어 버전 변경 등) 가 있는지 먼저 스캔. 있으면 환경 가설을 가설 A 로 두고 코드 가설은 B/C 로
- 코드 분석으로 *"이 조건에서 이 증상이 나오려면 무엇이 trigger 되어야 하는가"* 까지 도달했을 때, 그 trigger 가 환경 변화로 발생할 수 있는지 먼저 검토. 코드 결함 가설은 trigger 의 환경 원인을 모두 배제한 다음 단계
- 정확한 코드 동작 분석을 사용자에게 보고할 때는 *"이 동작이 의도된 건가요? 환경에 따라 영향 받을 수 있는 구조"* 식으로 환경 가능성을 같이 제시. *"디자인 결함입니다"* 같은 단정 회피
- 분석·디버깅 규칙 §3 ("사용자가 직접 수정한 변경") 의 확장: 직접 수정뿐 아니라 **사용자가 언급한 환경 차이**도 동일한 우선 단서로 취급

## 디버그 트레이스 출력 함수로 `ci_printe` 회피 (2026-05-06)

시점 측정·버퍼 dump 등 디버그 트레이스 목적 출력에는 `ci_printe` 대신 `ci_printw` (워닝 의미) 또는 `ci_printi` (정보 의미) 를 사용한다. `ci_printe` 는 출력 시 파일·함수·줄번호 prefix 가 자동 prepend 되는 구조라 메시지 본문이 메타데이터에 묻혀 가독성이 떨어진다.

**Why:** Sound1 V10 SPI race 측정 트레이스 작업 (`LED/power-on-early-lighting` V10 분석 노트) 에서 [`driver_SPI.c`](../../projects/Sound1/src/2__cm3/Cortex-M3-src/systemControl/driver_SPI.c) DMA 에러 분기에 `ci_printe` 로 RX/TX 버퍼 dump 추가, [`ble_communication.c`](../../projects/Sound1/src/2__cm3/Cortex-M3-src/BleCommunication/ble_communication.c) `SPI_CMMM_ERROR` recovery 분기에 `ci_printe` 로 `[SPI ERROR HANDLED]` 박스 추가. 사용자 피드백: *"printe 는 파일, 함수, 줄번호까지 출력하는 구조라 디버그 메시지가 더러워져."* — 본 dump 는 hex 값 한 줄에 다수 byte 를 압축 출력하므로 prefix 가 더해지면 줄바꿈·공백 의도가 무너진다. `ci_printw` 로 일괄 변경 후 가독성 회복.

**How to apply:**
- 디버그 트레이스 (시점 측정·버퍼 dump·milestone 박스 등) 신규 추가 시 `ci_printw` 또는 `ci_printi` 우선 선택. `ci_printe` 회피
- 정상 에러 보고 (`OVERRUN`, `UNDERRUN`, `DMA_CNTS != PACKET_SIZE` 등 의미적 에러 알림) 의 기존 `ci_printe` 는 보존 — 본 규칙은 트레이스 목적 신규 출력에 적용
- ISR 안 hex dump 등 한 줄에 다수 element 를 압축 출력할 때 prefix 자동 prepend 가 의도를 망가뜨리는지 미리 확인. 기존 출력 패턴 참고 (예: `[SPI TX] (LSB) 0x%02X ...` writeDataToSpiTxBuff 의 ci_printv) 가 가이드
- 출력 함수 선택 기준: 워닝 (비정상이지만 recovery 가능) → `ci_printw`, 정보 milestone → `ci_printi`, 의미적 에러 (assert 직전 등) → `ci_printe`

## 검증 도구를 코드 변경과 같은 commit에 포함 (CI 없는 환경) (2026-05-08)

CI/CD 파이프라인이 없는 단일 개발자 환경에서 형식·인터페이스 변경을 commit할 때, **그 변경을 검증할 수 있는 자동 검증 도구를 같은 commit에 포함**한다. 검증이 별도 commit 또는 수동 절차에 머물면 후속 회귀 시 누가·언제 다시 돌릴지 불분명해진다.

**Why:** sound1-fw-extractor `format/unified-input` 작업(2026-05-08) — `src/main.py`를 4 텍스트 입력 외부 루프 호출 구조에서 단일 `fw.txt` 입력 + 4 바이너리 출력 구조로 rewrite. 동일 commit에 `tests/build_sample.py`(out/ 바이너리 → fw.txt 샘플 생성 도구)와 `tests/test_extract.py`(추출 결과와 기존 out/ 바이트 동일성 검증, 종료 코드 0=PASS) 포함. 검증 절차가 한 명령(`python tests/test_extract.py`)으로 끝나, 향후 형식 변경 시 회귀 안전망이 commit 단위로 보존됨. 별도 commit이었다면 검증 도구를 **빠뜨리거나 깜빡 미실행한 상태로 push** 가능. CI 없이도 *발견성 + 실행 단순성*이 회귀 방어 핵심.

**How to apply:**

- 형식·인터페이스·외부 계약(API/CLI/파일 포맷) 변경 시 `tests/test_<변경명>.py` (또는 동등 스크립트) 동시 작성
- 검증 도구 요건:
  - **일관된 진입점** — `python tests/test_X.py` 한 명령으로 실행
  - **명확한 종료 코드** — 0=PASS, 1=FAIL (CI 도입 시 그대로 활용)
  - **자체 cleanup** — 임시 산출물(`out_test/` 등) 종료 시 제거 + `.gitignore`로 안전망
  - **결정론적 비교 기준** — 기존 정답(`src/out/` 등)과 바이트·해시 단위 동일성. fuzzy 매칭 회피
- 검증 도구가 의존하는 *입력 데이터*(샘플 파일 등)도 같은 commit에 포함. 또는 입력을 *생성*하는 도구(`build_sample.py`)를 두어 입력 자체는 untracked 가능
- 사용자에게 머지 승인 요청 시 *"검증 N/N PASS"* 한 줄 보고 — 사용자가 추가 수동 검증 없이 승인 가능
- 본 패턴은 형식 외 코드 리팩토링(시그니처·내부 알고리즘 변경 등)에도 확장 가능. 단, 알고리즘 정확성 골든 데이터를 미리 확보해야 함

## doxygen `/** ... */` 주석 안에 `*/` 시퀀스 금지 (2026-05-07)

doxygen 또는 일반 블록 주석 (`/* ... */`) 본문에 `*/` 문자 시퀀스가 들어가면 거기서 주석이 일찍 닫히고 그 뒤 텍스트가 코드로 해석되어 줄줄이 문법 에러가 발생한다. C 는 nested block comment 를 지원하지 않는다 — 안에 `*/` 가 보이는 순간 종료. 주석 안에서 path/glob 패턴 (`snd_boot_*/...`), regex (`.*/...`), 곱셈·나눗셈 표현 (`a * b / c`) 등을 적을 때 `*` 와 `/` 사이에 공백을 둬야 한다.

**Why:** Sound1 `bootloader/service-rtt-debug-console` 작업 Step 1 에서 [`bootloader.c:1404`](../../projects/Sound1/src/0__bootloader/source/bootloader.c) `tdc_boot_storage_init()` doxygen 헤더에 *"OTA 슬롯 선택(snd_boot_\*/tdc_boot_print_boot_file)"* 적음. `snd_boot_*/tdc_boot_print_boot_file` 안의 `*/` 가 주석 종료로 해석되어, 그 뒤 한글 텍스트 + 함수 시그니처 + 본문이 모두 코드로 파싱되어 빌드 에러. 사용자가 *"1398라인부터 문법에 어긋나 ... 주석 문법 에러잖아"* 로 직접 짚어줘서 발견. `*/` → `* /` 공백 1 칸 추가로 fix.

**How to apply:**
- doxygen 또는 블록 주석 본문에 `*/` 시퀀스 금지. `*` 와 `/` 사이에 **공백 1 칸** 두거나 표현 자체를 바꿈
- glob / regex 패턴 인용 시: `snd_boot_*` 와 `/...` 분리 (예: `snd_boot_* / ...`), 또는 `snd_boot_<suffix>` 같이 plain 으로
- 함수 무리 표현 시: `snd_boot_*` 대신 `snd_boot_set_fp 등` 또는 `snd_boot_*` 만 쓰고 `/` 동반 회피
- 에러 진단 단서: 주석 시작 라인이 정상으로 보이는데 그 직후 첫 함수 시그니처에서 *"unknown type name"* / *"expected '=' before"* 류 에러가 줄줄이 나오면 **주석 안 `*/` 시퀀스 의심 1 순위** — 주석 본문을 `Grep '\*/[a-zA-Z_]'` 로 스캔
- 주석 작성 후 한 번 검토: 주석 안에 `*/` 가 끝 외에 또 등장하지 않는지 시각 확인. 특히 한글 본문은 syntax highlighter 가 주석 종료를 시각적으로 잘못 표시할 수 있어 놓치기 쉬움 — Claude 도 작성 직후엔 잘 안 보임
