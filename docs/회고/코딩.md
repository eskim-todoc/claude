# 코딩 회고

**TL;DR**: 비차단/ISR 기반 서브시스템에 동기 폴링 구현 회피 (호출자 즉시 return + ISR step 패턴 우선).

코드 작성 시 사용자 의도와 어긋날 수 있는 패턴, 검증된 설계 결정의 학습 누적.

## 비차단/ISR 기반 시스템에서 동기 블로킹 폴링 회피 (2026-04-27)

이벤트/ISR 기반 서브시스템(LED, timer, 통신 등)에 새 함수 추가 시 `for { step(); delay_ms(1); }` 형 동기 블로킹 폴링 구현을 회피한다. 호출자는 즉시 return, ISR 이 매 tick step 을 진행하는 상태머신 패턴을 우선 적용한다.

**Why:** 사용자는 LED 시스템을 *"메인 코어가 LED 처리에 갇히지 않는"* 비차단 ISR 기반으로 설계함. Claude 가 LED `operation-scheme` 작업 중 `turnOffLED` / `led_force_fade_off` 를 30 / 40 ms 동기 폴링(`for { LED_OUT(); delay_ms(1); }`)으로 구현 — 게다가 ISR 을 `s_led_isr_suspended = true` 로 멈춰놓고 직접 폴링하는 거꾸로 된 구조가 됨. 후속 `LED/non-blocking-fade-off` 작업에서 ISR 상태머신 변환 + 잠재 버그(suspended 영구 set 이 폴링 끝에서 풀리던 의도-구현 불일치) 자연 해소.

**How to apply:**
- 비차단/ISR 기반 서브시스템에 fade·전환·sequence 형 함수 추가 시: **호출자 즉시 return + ISR step 진행** 패턴 우선 적용
- 폴링이 필요해 보이는 케이스 (예: ISR 미활성 시점 호출): **즉시 완료 분기** 또는 **ISR 활성 여부 검사 후 분기** 로 처리, 폴링 fallback 도입 회피
- "단순화 위해 폴링" 충동 시 자가 점검: 호출자 측 main loop 가 그 시간 동안 무엇을 진행할 수 있는지 먼저 분석. main loop 가 다른 작업을 동시 진행할 수 있다면 폴링은 그 **병렬화 가능성을 막는 안티패턴**
- 설계 의도가 모호하면 구현 전 사용자에게 명시 확인 (*"이 함수 동기 폴링 vs ISR step, 어느 쪽?"*)
- 기존 서브시스템에 새 함수 추가 시: 기존 함수들이 어떤 패턴을 따르는지 (ISR 기반인지 폴링인지) 먼저 확인해서 일관성 유지
