# 작업 진행 회고

**TL;DR**: 프로그래밍 전 문서 선행, "정리해" 요청 시 docs/에 md 작성, 메인 디렉토리 + 브랜치 전환이 기본(워크트리는 명시·진짜 병렬 이득시만), 사용자 "작업 끝났어. 마무리해" 시그널 전 자동 커밋·병합 안 함.

문서 선행, 정리 요청, 작업 위치(메인 vs 워크트리), 완료 시그널 관련 학습.

## 프로그래밍 전 문서 선행 작성 (2026-04-18)

사용자가 프로그래밍 관련 작업을 지시하면, **코드를 바로 작성하지 않고** 먼저 다음 문서를 해당 프로젝트의 `docs/` 폴더에 .md로 작성한다:

1. `[요구사항] <기능명>.md` — 무엇을 만들어야 하는지
2. `[현상분석] <기능명>.md` — 현행 구조, 영향 범위, 기술적 검토
3. `[구현계획] <기능명>.md` — 어떻게 구현할지 (설계·단계·파일 변경 계획)

**Why:** 사용자가 문서를 먼저 확인하고, 구현 여부를 결정한다. 승인 없이 코드 작성을 시작하면 안 됨.

**How to apply:**
- 프로그래밍 작업 지시 → docs/ 문서 작성 → 사용자에게 제시 → 승인 시 구현 시작
- 문서 prefix는 docs 파일명 컨벤션 따름 (`[요구사항]`, `[현상분석]`, `[구현계획]`, `[시험방법]`, `[사용방법]` 등)
- 단순 수정(오타, 설정값 변경 등)은 문서 없이 바로 진행해도 무방 (사용자 판단)

## 정리 요청 시 docs 폴더에 md 문서 작성 (2026-04-17)

사용자가 *"~하고 정리해"*, *"~하고 정리해봐"* 등 작업 후 정리를 요청하면, **작업이 수행된 위치에 따라** 해당 `docs/` 폴더에 .md 문서를 작성한다.

**How to apply:**
- 루트(`E:\Claude`)에서 수행한 작업 → `E:\Claude\docs/`에 정리
- 프로젝트(`projects/<이름>`)에서 수행한 작업 → `projects/<이름>/docs/`에 정리
- 문서 포맷은 항상 Markdown (.md)
- 파일명은 docs 폴더의 prefix 컨벤션을 따름

## 작업 위치 — 메인 디렉토리 기본, 워크트리는 명시 또는 병렬 이득 시 (2026-04-25)

사용자가 작업을 지시하면 원칙적으로 **메인 워킹 디렉토리(루트 repo 또는 해당 프로젝트 repo)에서 작업 브랜치 전환 방식**으로 진행한다. 사용자의 VSCode 등 IDE가 메인 디렉토리를 열어둔 상태이므로, 워크트리로 격리하면 변경사항을 IDE에서 실시간으로 볼 수 없어 단일 작업에선 비효율적.

### 워크트리 사용 조건 (둘 중 하나)

**1. 사용자 명시 트리거** — 지시문에 다음 키워드 포함:
- *"워크트리에서"*, *"병렬로"*, *"동시에 작업"*, *"백그라운드로"* 등 동의어

**2. Claude 판단 — 진짜 병렬이 이득 명확할 때**
- 예: 여러 작업을 동시에 진행하고 완료되는 순서대로 메인 디렉토리에 순차 병합하는 편이 총 소요시간을 크게 줄일 때
- 이 경우 먼저 *"워크트리로 병렬 진행할까요?"* 사용자에게 제안 후 동의 얻고 실행

### 기본 절차 (메인 디렉토리 + 브랜치 전환)

1. 메인 디렉토리의 uncommitted changes 확인 → 있으면 stash 또는 사용자 상의
2. 작업 브랜치 체크아웃 (`git checkout -b claude_<설명>` 또는 기존 브랜치)
3. 작업 수행 — 사용자가 IDE로 실시간 확인 가능
4. *작업 완료 시그널* 회고에 따라 `"작업 끝났어. 마무리해"` 대기
5. 시그널 수신 시: 커밋 → *병합 전 사용자 승인* 회고에 따라 승인 요청 → `--no-ff` 병합 → 원 브랜치 복귀 (필요 시)

### 작업 시작 시 고지

매 작업 시작 시 명시적으로 알린다:
- *"메인 디렉토리에서 `<브랜치명>` 브랜치로 진행하겠습니다"* (기본)
- *"워크트리로 병렬 진행하겠습니다"* (트리거 or 제안 승인 시)

**Why:**
- 사용자의 VSCode가 메인 경로를 지속 열어둔 상태 → 워크트리 경로는 IDE 밖에서 별도 탐색 필요
- 단일 작업의 격리 이득은 메인 디렉토리 브랜치 전환으로도 충분히 확보 (uncommitted 상태만 관리)
- 워크트리의 진짜 강점은 N개 작업 동시 격리 → 진짜 병렬 시점에만 의미

## 작업 완료 시그널 및 워크트리 생명주기 (2026-04-24)

작업 중에는 워크트리와 작업 브랜치를 유지하고, 사용자가 명시적으로 **"작업 끝났어. 마무리해"** (또는 동등한 완료 시그널)를 보내기 전까지 자동으로 커밋·병합·워크트리 정리 단계로 넘어가지 않는다.

**Why:** 사용자는 한 세션 안에서 단일 작업을 긴 호흡으로 이어가며, 중간 커밋·병합이 세션 흐름을 끊는 것을 원치 않는다. 완료 시점 판단은 사용자에게 맡기고, Claude는 마무리 시그널을 대기한다.

**How to apply:**
- 작업 단위가 끝난 듯 보여도, 명시적 완료 시그널이 없으면 **커밋하지 않음**
- 중간 저장이 필요하면 사용자에게 *"여기서 커밋할까요?"* 확인 후 진행
- 사용자 시그널 수신 시: 작업 브랜치 커밋 → 병합 전 승인 요청 → 병합 → 워크트리 정리
- 백그라운드 워크트리 에이전트가 작업 완료를 보고해도 동일 원칙: 사용자 시그널 전에는 병합하지 않음, 보고만 전달

## 신규 도출물 작성 직후 frontmatter+TL;DR 셀프 체크 (2026-05-07)

새로운 영속 .md 파일(지침·회고·tasks 산출물 등)을 `Write`로 처음 작성할 때 **frontmatter와 TL;DR 둘 다 포함됐는지** 작성 직후 즉시 셀프 체크한다.

**Why:** 4단계 적용 첫 사례에서 `이력.md`를 처음 작성할 때 frontmatter는 있었지만 본문 첫 헤더 바로 아래 `**TL;DR**:` 줄을 빠뜨렸음. 후속 갱신을 시도하다가 문자열이 매치되지 않아 발견함. 작성 직후 한 번만 확인하면 즉시 잡히는 누락이며, 시간이 지난 뒤 발견하면 재작업 비용이 늘어난다.

**How to apply:**
- 영속 `.md` 신규 작성 시 체크리스트 (Write 직후):
  - [ ] frontmatter (`---` 블록, name·purpose·type 최소)
  - [ ] 첫 `#` 헤더 직후 `**TL;DR**:` 1~3줄
  - [ ] 의미 한글 라벨 (`Q1`/`H1` 같은 알파벳 약어 금지)
- 작업 산출물(`요구사항.md`/`분석.md`/`계획.md`/`이력.md`/`진행상황.md`)도 영속 분류와 동일하게 frontmatter+TL;DR 의무
- TL;DR은 `purpose`보다 더 구체적·실행 가능한 정보 — 단순 복붙 금지

## 점검 task의 빈틈은 사용자 명시 트리거로 일괄 소급 (2026-05-07)

문서 정합성 일괄 점검 task가 *점검 기준 자체에 빈틈*이 있는 경우, 그 빈틈을 사용자가 지적했을 때 **재점검·재작업이 아니라 사용자 명시 요청을 트리거로 일괄 소급에 진입**한다. 점진적 소급(§6.5)이 디폴트이지만 사용자 명시 트리거가 있으면 그 즉시 일괄 처리 권한이 열린다.

**Why:** 실제 사례(2026-05-07) — 루트 `meta/docs-consistency-audit` task에서 frontmatter 점검을 *루트 docs/만* 했고 *프로젝트 docs 안 기존 파일들*은 점검 항목에서 누락. 사용자가 "Sound1 docs 밑 파일들이 YAML 적용이 안되어 있는데? 원래 그런 지침인가?"로 빈틈을 지적. 만약 "지침은 점진적 소급이라 위반 아님"으로만 답하면 빈틈 자체는 그대로. 옵션 (가/나/다)을 제시해 사용자가 (다)를 명시 선택 → 일괄 소급 트리거 충족 → 별도 task로 9 파일 처리.

**How to apply:**

- 점검 task에서 빈틈이 발견되면:
  1. 빈틈을 인정 (어디를 못 봤는지 구체적으로)
  2. 지침 정책상의 디폴트 처리 방식 안내 (예: "점진적 소급이 디폴트")
  3. 사용자가 일괄 처리를 원할 옵션 제시 (가/나/다 식)
- 사용자가 일괄 옵션을 선택하면 §6.5/§9.1의 "사용자 명시 요청" 트리거 충족 → 일괄 소급 task 신규 시작
- 일괄 소급 task는 **별도 task 폴더**(예: `meta/frontmatter-retrofit`)로 분리. 원 점검 task는 이미 archive됐어도 무관 — 빈틈 보완은 새 task로 추적
- 빈틈 보완 task의 이력에 *원 점검 task 링크* + *어떤 점검 기준이 누락됐는지* 명시해 미래의 점검 templating에 반영

## 메타 점검은 영역 분할 서브에이전트 병렬로 (2026-05-07)

문서 정합성·인덱스 동기화·링크 무결성 같은 **광범위 메타 점검**은 영역별로 `Explore` 서브에이전트를 분할해 한 응답에 병렬 호출하면 메인 컨텍스트 부담을 크게 낮춘다. 검증된 분할 축: **(1) 루트 docs frontmatter·인덱스 / (2) 모든 .md 링크 무결성 / (3) 각 프로젝트 표준 준수** — 한 응답 3호출, 약 85초만에 28파일·80+ 링크·6개 프로젝트 점검 완료.

**Why:** 한 메인 에이전트가 직접 읽어가며 점검하면 컨텍스트 폭발 + 중간 항목 누락 위험. 분할 서브에이전트는 각자 좁은 영역에서 체크리스트 출력에 집중하므로 결과가 명확하고, 메인은 종합·우선순위 결정·git 스코프 분리 판단에 집중할 수 있음.

**How to apply:**
- 점검 차원이 3개 이상이면 분할 후보. 예: 영역(루트/프로젝트) × 항목(frontmatter/링크/인덱스)
- 각 서브에이전트 프롬프트에 출력 형식을 체크리스트·표로 강제 (자유 서술 금지) — `서브에이전트 활용` §4.2
- 메인은 발견된 항목을 분석.md에 수합한 뒤 git 스코프 별로 처리 가능 여부 분리 (작업 규칙 §6)
- 단계 ② 분석에서 가장 효과 큼 (이미 `서브에이전트 활용` §6에 명시 — 본 사례는 그 검증)

## 같은 파일 다중 Edit은 순차 호출 (병렬 충돌) (2026-05-07)

한 응답에서 **같은 파일에 대해 Edit 도구를 다중 호출하면 string 매치 실패** 위험이 있다. 첫 호출의 변경 결과가 다른 호출의 `old_string`에 반영되지 않아 매치 어긋남이 발생.

**Why:** 같은 작업 묶음에서 분석.md에 분석_2 테이블 갱신 + 분석_1 신규 행 추가 + 결정_5 신규 섹션 추가를 한 응답에 Edit 3건으로 보냈을 때, 분석_2 Edit이 다른 호출이 먼저 변경한 상태를 보지 못해 매치 실패. 작은 글자 차이(`남기도록` vs `남도록`)도 영향.

**How to apply:**
- 한 파일에 변경할 곳이 여러 개면 다음 중 택일:
  - **(a) 더 큰 영역을 한 번의 Edit으로** — 변경 영역들을 포함하는 큰 블록을 통째 교체
  - **(b) 응답 분리** — 한 응답에 한 파일 한 Edit, 다음 응답에 다음 Edit
  - **(c) 명시 순차** — 의존성이 있다면 한 Edit 결과 확인 후 다음 Edit
- 다른 파일들 사이에는 병렬 Edit 그대로 활용 (충돌 없음)
- Edit 매치 실패 시 즉시 `Read`로 현재 파일 상태 확인 후 정확한 문자열로 재시도

## Plan Mode 자동 진입 도입 (2026-05-14)

actionable task 시작 시 Claude가 `EnterPlanMode` 도구를 **자체 호출**해 Plan Mode로 진입한 뒤 표준 ②분석·③계획 산출물을 작성하고 `ExitPlanMode`로 사용자 승인을 받은 후 Auto 모드로 ④구현하는 흐름을 의무화. 표준 4단계 산출물은 그대로 보존되며, Plan Mode는 ②③ 단계 위에 도구 차단 + 강제 승인 게이트를 덧씌우는 역할.

**Why:** 사용자가 *"내가 너의 모드를 자동으로 했지만, 모든 작업을 지시할 때 자체적으로 계획모드로 진행하게 할 수 있어?"* 제안. 조사 결과:

- **hooks** (`UserPromptSubmit` 등): mode 전환 능력 없음 — 시스템 자동 트리거 불가
- **settings.json `defaultMode: "plan"`**: 세션 전체를 Plan Mode로 묶음 → 매번 `Shift+Tab` 종료 필요, *"Auto 모드 유지 + 작업 시만 Plan"* 의도와 충돌
- **`EnterPlanMode`/`ExitPlanMode`**: 모델 호출 가능 도구임을 schema로 확인. 도구 description 자체가 *"prefer using proactively for non-trivial implementation tasks"* 권장

→ CLAUDE.md/지침으로 자체 발동 강제가 가장 깨끗한 경로. Plan Mode plan file과 표준 산출물(`docs/tasks/<모듈>/<작업>/분석.md`·`계획.md`)은 별개 메커니즘이라 충돌 없음.

**How to apply:**

- ①요구사항 명확화 후 면제 케이스 아니면 즉시 `EnterPlanMode` 호출 → 사용자 승인 (1차)
- Plan Mode 내에서 표준 경로에 `분석.md`·`계획.md` 정식 산출물 작성 (frontmatter + TL;DR + 자체 검토 포함)
- Plan Mode plan file은 표준 산출물 경로 참조 + 3~5줄 핵심 요약 전용
- `ExitPlanMode` 호출 전 self-check 4 항목: 산출물 존재·완성 / frontmatter+TL;DR / 자체 검토 / plan file 참조
- ExitPlanMode 사용자 승인 (2차) 후 Auto 모드로 ④구현

## ExitPlanMode 승인 = plan file 승인 ≠ 정식 산출물 승인 (2026-05-14)

`ExitPlanMode` 호출에 대한 사용자 승인은 **plan file (Claude Code 시스템 임시 경로의 요약본) 에 대한 게이트**일 뿐이며, 표준 경로 (`docs/tasks/<모듈>/<작업>/분석.md`·`계획.md`) 에 정식 작성하는 산출물의 사용자 검토 게이트는 **별도**다. 두 가지를 동일시하여 ExitPlanMode 승인 직후 정식 산출물 작성 → 코드 변경 → 2 commit 까지 한 번에 진행하면 [`작업 진행 규칙.md §5`](../지침/일반/작업%20진행%20규칙.md) 사용자 승인 의무 위반.

**Why:** 실제 사례 — Sound1 [`tasks/_archive/ui/program-change-command`](../../projects/Sound1/docs/tasks/_archive/ui/program-change-command/) 작업에서 [`계획 모드 자동 진입.md §4`](../지침/일반/계획%20모드%20자동%20진입.md) 가 "Plan Mode plan file vs 표준 산출물" 두 매커니즘을 별개로 명시함에도 불구하고, ExitPlanMode 승인을 정식 산출물 승인으로 간주하여 검토 게이트를 우회. 사용자(다)로부터 *"계획 문서까지 쓰고 나서 내가 검토한 다음에 구현을 할지 말지 정해야지, 구현까지 알아서 다 끝내놓고 계획문서를 내가 보게 되면 이게 무슨 의미가 있냐?"* 경고 수신. 처리 = 코드·문서 commit 둘 다 보존하고 사용자가 산출물 검토 후 별도 수정 요청 없이 실기 검증 진행 → AC-1~8 통과 → 마무리. 결과적으로 절차상 정상 통과시킨 것보다 추가 비용은 commit revert 없이도 발생하지 않았지만, **사용자 신뢰·승인 의무 자체가 우회되었다는 사실이 핵심 문제**.

**How to apply:**

- ExitPlanMode 승인 후 표준 산출물 (`분석.md`·`계획.md`) 을 정식 경로에 작성하는 시점에 **별도 사용자 검토 게이트** 명시. 작성 후 *"표준 산출물 작성을 마쳤습니다. 검토 부탁드립니다."* 류 안내 + 사용자 OK 시그널 수신 전까지 코드 변경 금지
- plan file 의 요약 (3~5 줄 + 표준 산출물 경로 참조) 과 정식 산출물 (전체 분석·결정·자체 검토 포함) 은 정보량이 다르므로, plan file 승인이 정식 산출물 승인을 대체하지 않음
- 두 게이트 모두 통과 후에야 ④ 구현 시작:
  1. Plan Mode 1차 게이트: ExitPlanMode → plan file 승인
  2. 표준 산출물 2차 게이트: `분석.md`·`계획.md` 정식 작성 → 사용자 검토 → 명시 OK
  3. ④ 구현
- "stop 없이 진행", "알아서 해" 류 사용자 지시는 **clarifying question 자율 판단** 면제이며, 사용자 승인 게이트 자체를 면제하지 않음. 게이트 면제는 사용자가 *"검토 게이트 건너뛰고 바로 구현해"* 같이 게이트를 직접 지목해 면제한 경우에 한정
- 본 사례 발생 직후 가장 안전한 처리 = **코드 commit revert + 산출물 정상 검토**. 다만 사용자가 보존을 선택했다면 그대로 보존하되, 다음 작업에서는 절차 준수로 회귀

## 정책 신설 작업의 자기 참조 — 첫 사용 사례 자기 반영 (2026-05-15)

정책·절차·인덱스를 새로 신설하는 작업이 그 신설된 절차·인덱스의 **첫 사용 사례**가 되는 경우, 계획 단계에서 *"자기 적용"* 단락을 의무 추가하고 종료 정리에서 실제 자기 반영을 수행한다. 빠뜨리면 새 절차가 *예외 1건* 으로 시작되어 시간이 흐를수록 정합성 누적 손실.

**Why:** 실제 사례 — `meta/archive-modules-index` 작업이 [`작업 진행 규칙.md §6.1`](../지침/일반/작업%20진행%20규칙.md) archive 처리 5단계를 6단계로 확장(`tasks/_archive/_modules.md` 갱신 단계 신규 추가)하면서, 본 작업 자체가 그 새 5번 단계의 첫 사용 사례가 됨. 본 작업이 archive 처리될 때 새 5번 단계가 적용되지 않으면 — 즉 루트 `_modules.md`의 `meta` 행이 갱신되지 않으면 — 새 절차가 자기 적용 안 된 상태로 정합성 깨짐. 계획.md §6.3 "종료 정리 — 자기 반영" 단락에 명시 후 실제 적용 (`meta` 행 작업 수 8 → 9, 최근 작업 `wiki-bootstrap` → `archive-modules-index`). 본 패턴 누락 시 다음 작업이 archive 될 때 `_modules.md` 정확성이 한 발 늦은 상태에서 시작됨.

**How to apply:**

- 작업이 **정책 신설·절차 확장·메타 인덱스 신설**에 해당하면 계획.md에 자기 적용 검토 섹션 의무 추가:
  - 본 작업 자체가 신설 절차의 첫 사용 사례인가?
  - 자기 반영해야 하는 산출물·인덱스·표는 무엇인가?
  - 종료 정리의 어느 단계에서 자기 반영하는가?
- 종료 정리 커밋에 자기 반영까지 포함 (또는 별도 커밋으로 분리)
- 본 패턴은 archive 인덱스·지침 갱신·CLAUDE.md Projects 표·`tasks/list.md` 등 **Claude 자신이 관리하는 메타 인덱스** 에 특히 중요. 외부 코드 변경은 자기 참조가 거의 없음
- 신설 절차의 *외부* 사례 (다른 프로젝트의 작업) 는 본 패턴과 별개 — 자기 반영은 본 작업 한정

## 묵혀 둔 미머지 원격 브랜치 회수 — 사용자 회상 트리거 (2026-05-14)

사용자가 *"전에 ~ 한 적 있지 않아? 다른 PC였는지 기억 안 난다"* 류 자연어 회상으로 잊혀진 작업물을 떠올리면, 활성 `tasks/list.md` 나 `_archive/` 에서 안 보일 가능성이 크다 — main 머지 안 된 채 `claude_*` 또는 `claude_docs_*` 브랜치로 origin 원격에만 남아 있는 작업물일 수 있기 때문이다. 표준 회수 절차: ① `git branch -a` 로 모든 로컬·원격 브랜치 점검 → ② `git log --all --oneline --grep="<키워드>"` 로 commit 메시지 검색 → ③ 후보 브랜치의 `git log <브랜치> ^claude_main --oneline` 으로 main 대비 고유 commit 추출 → ④ `git show --stat <commit>` 로 정확한 파일명 확인.

**Why:** 미머지 원격 브랜치의 작업물은 *list.md 도 모르고 _archive 도 모르는 사각지대*. 사용자 회상이 유일한 단서라 회상 표현을 캐치하지 못하면 영구 분실 위험. 한 번 발견하면 신 컨벤션으로 이전·머지·archive 해 재참조 가능 상태로 만들면 재발견 비용 0. 실 사례: Sound1 `origin/claude_docs_cfx-cm3-analysis` (2026-04-18 작성·약 한 달 묵힘) 에서 CFX·CM3 분석 3편 2293 줄 회수 — [`projects/Sound1/docs/tasks/_archive/signalProcessing/cfx-cm3-analysis/`](../../projects/Sound1/docs/tasks/_archive/signalProcessing/cfx-cm3-analysis/).

**How to apply:**

- 사용자 표현 트리거: *"전에 ~"*, *"~ 한 적 있지 않아?"*, *"기억 안 난다"*, *"다른 PC였는지"* 류 → 즉시 `git branch -a` 우선 점검 (활성 `list.md`·`_archive/` 보다 먼저)
- 한글 파일명 함정: `git ls-tree -r <브랜치> --name-only` 출력은 한글을 `\352\271\200...` 8진 escape 로 변환하므로 한글 키워드 `grep` 매칭이 안 됨. 우회 = `git show --stat <commit>` 또는 `git diff --stat <base>..<branch>` 로 commit 단위 정확한 파일명 확인
- cherry-pick 회피 — 옛 미머지 브랜치는 AI Co-Authored-By 트레일러·옛 코드 회귀 같은 부수 변경이 따라올 수 있어 위험. 대신 `git show 'origin/<브랜치>:<원본경로>' > <신경로>` 방식으로 파일 단위 추출 → 신 컨벤션 위치 배치 → frontmatter+TL;DR 추가 (본문 무변경) → 새 commit (트레일러 없음). 옛 commit 이력은 원본 브랜치에 그대로 남아 있으므로 손실 0
- 회수 후 원본 브랜치는 보존 (force-push 회피, Co-Auth 잔존 commit 보존 정책과 같은 맥락). 삭제 여부는 사용자 사후 판단
- `tasks/list.md` 갱신 이력에 회수 경위 (회상 표현 → 발견 → 처리) 한 줄 명시. 향후 재검색 시 키워드 매칭 보장
- 정기 점검 패턴 (선택): 사용자가 회상해 주기 전에도 자체적으로 `git branch -r` 점검 — `remotes/origin/claude_*` 중 `claude_main` 대비 고유 commit이 있는 브랜치 = 잠재 미머지 작업물 후보
