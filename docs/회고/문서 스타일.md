# 문서 스타일 회고

**TL;DR**: GFM + Mermaid + GitHub Alert. ASCII art 금지(다이어그램은 Mermaid), 코드 블록 언어 명시, 강조는 Alert 구문(`> [!NOTE]` 등).

Markdown 문법, 다이어그램, 시각적 강조 관련 학습.

## GFM + Mermaid + Alert Blocks 문서 스타일 (2026-04-21)

모든 `.md` 문서는 GitHub.com 또는 VSCode **GitHub Markdown Preview** 확장(`bierner.markdown-preview-github-styles`)에서 렌더링된 결과를 기준으로 작성한다.

**Why:** 사용자가 VSCode에 GitHub Markdown Preview 확장을 설치해 GitHub 렌더링 기준으로 문서를 읽음. 일관된 시각적 품질을 위해 GitHub이 네이티브 지원하는 GFM 확장 문법(Alert blocks, Mermaid 등)을 적극 활용한다.

**How to apply:**

- **다이어그램**: ASCII art 금지. ` ```mermaid ` 코드 블록 사용
  - 브랜치 흐름 → `gitGraph`
  - 절차·의사결정 → `flowchart LR` 또는 `flowchart TD`
  - 시스템 상호작용 → `sequenceDiagram`
  - 상태 전환 → `stateDiagram-v2`
  - 일정 → `gantt`
- **강조/경고**: 일반 인용(`>`) 대신 GitHub Alert 구문 사용
  - `> [!NOTE]` 참고 정보
  - `> [!TIP]` 권장 방법
  - `> [!IMPORTANT]` 핵심 사항
  - `> [!WARNING]` 주의 사항
  - `> [!CAUTION]` 치명적 경고(보안·데이터 손실 등)
- **코드 블록**: 언어 항상 명시 (` ```bash `, ` ```powershell `, ` ```c `, ` ```json `, ` ```mermaid ` 등)
- **표**: 구조화된 정보는 표로. 정렬이 필요하면 `:---`, `:---:`, `---:` 사용
- **링크**: 파일 간 링크는 상대경로. 공백은 `%20` 인코딩
- **체크리스트**: 할 일·절차 목록은 `- [ ]` / `- [x]` 사용

상세 가이드: [`docs/지침/일반/문서 작성 규칙.md`](../지침/일반/문서%20작성%20규칙.md)

## 지침 모호 표현(`선택`/`권장`) 금지 — 단호한 `필수`/`금지`로 (2026-05-06)

지침에 "선택 적용", "권장", "가능하면" 같은 모호한 표현을 쓰면 LLM은 결국 일관 적용에 실패한다. 같은 폴더 안에서도 어떤 파일은 적용되고 어떤 파일은 누락되어 사용자가 일관성 깨진 상태를 발견한 후에야 지적이 들어옴.

**Why:** 실제 사례(2026-05-06) — `문서 작성 규칙 §9.1`의 frontmatter 적용 대상에서 `tasks/<모듈>/<작업>/ 하위 = 선택 적용`으로 정의됨. 결과적으로 같은 작업 폴더 5개 파일 중 `구현계획.md`만 frontmatter가 있고 나머지 4개(`분석`/`요구사항`/`이력`/`진행상황`)는 누락. 추가로 `§3.4.2 이력.md` 템플릿 자체에 frontmatter block이 빠져 있어 LLM이 템플릿대로만 따라 작성. 누락의 책임은 LLM이 아니라 지침·템플릿의 모호함·결함.

**How to apply:**

- 지침 작성 시 적용 범위는 **`필수 적용` / `미적용` / `금지 상태`** 의 단호한 3분법으로 표기. `선택 적용`·`권장`·`가능하면`은 사용 금지
- 정말 조건부 선택이 필요하면 그 **선택 기준**(언제 적용·언제 미적용)을 if-then 형태로 명시. 판단을 LLM에 떠넘기지 않는다
- 지침에 **금지 상태**(예: "같은 폴더 내 일부 파일에만 적용된 부분 적용")를 명시 — LLM이 일관성 검증을 self-trigger 하게
- 템플릿(예: `§3.4.2 이력.md` 형식)은 지침 본문의 규칙과 **동기화 검증**: 템플릿이 빠뜨린 항목은 LLM이 그대로 빠뜨림. 신규 규칙 추가 시 관련 템플릿도 동시 갱신
- 기존 모호 지침을 발견하면 손댈 때 같이 단호화 (점진적 개선)

## 외부 인계 명세서는 도구 측 형식 명세와 분리 (2026-05-08)

같은 형식 정보라도 **청자가 다르면 별도 문서로 분리**하고 양쪽을 상호 링크한다. 도구 측 사용자(이 도구를 어떻게 쓸지) 관점의 형식 명세와 외부 작업자(이 형식을 어떻게 *생산*할지) 관점의 인계 명세는 같은 마커·정규식 정보를 담더라도 우선순위·강조점·검증 절차가 다르다.

**Why:** sound1-fw-extractor `format/unified-input` 작업(2026-05-08) — 처음에 `docs/사용방법/fw.txt 형식.md` 한 문서에 도구 사용자·Sound1 측 작업자 양쪽 정보를 합쳐 작성했다. 사용자가 *"이제 너한테 입력할 'fw.txt'는 이런 형식으로 출력을 해줘야 합니다 같은 문서가 필요해. 그걸 Sound1 측으로 줘서, 그걸 보고 'fw.txt'를 출력하는 구문을 만들게 할거야"* 로 외부 인계용 명세서 별도 작성을 요구. 통합 문서는 도구 관점·정규식 등이 외부 작업자에겐 불필요한 노이즈, 검증 절차(`clone → 추출 → 결과 확인`)는 외부 작업자에게 핵심인데 도구 사용자에겐 부수 정보. 분리 후 양쪽 상호 링크(NOTE 블록 1줄)로 발견성 유지.

**How to apply:**

- 하나의 인터페이스·형식이 둘 이상의 *역할*에서 참조되면 (예: 도구 사용자 + 외부 생산자, API 호출자 + API 제공자) 역할별 별도 문서 작성
- 각 문서 frontmatter `applies_to` 와 본문 TL;DR에 **청자 명시** (예: "Sound1 측 작업자 청자")
- 동일 정보(마커·정규식 등)는 양쪽에 약간씩 중복 OK — 한쪽이 변경되면 양쪽 동기화 점검. 단일 진실의 출처는 코드(정규식 상수 등)
- 양쪽 문서 TL;DR 직후에 `> [!NOTE]` 한 줄로 상호 참조 — 한 문서 읽다 다른 청자용 문서로 자연 이동
- 외부 인계용은 추가로 명시:
  - `## 변경 이력` 섹션 (v1.0 등 버전 부여) — 외부에 *전달*되는 명세는 명시 버전 관리 필수
  - `## 검증 방법` 섹션 — 외부 작업자가 자체 점검 가능한 절차 (도구 측 기본 사용법보다 상세)
  - 의사코드는 `extern` 선언 등 컴파일 가능 형태까지 (도구 측은 핵심 패턴만 보여도 충분)
- 한 문서가 여러 청자를 다 담으려는 충동 시 자가 점검: *"청자 A가 이 섹션 읽을 때 청자 B용 정보가 노이즈인가?"* 노이즈면 분리

## frontmatter `name` 필드는 헤더에 YAML 특수문자 포함 시 큰따옴표 (2026-05-07)

frontmatter `name` 필드 값을 본문 첫 `#` 헤더 텍스트와 동기화할 때, 헤더에 `[`/`]`/`:`/`#`/`|`/`&`/`*`/`!`/`%`/`@`/`` ` ``/`>` 같은 **YAML reserved 문자**가 포함되어 있으면 **항상 큰따옴표로 감싸 안전 처리**한다. 예: `name: "[Sound1] Ezairo LED 패턴 사양 Rev.0"`. 안 그러면 YAML 파서가 flow indicator로 해석해 frontmatter 전체가 깨진다.

**Why:** 실제 사례(2026-05-07) — Sound1 영속 9 파일 frontmatter 일괄 소급 중 `[Sound1] Ezairo LED 패턴 사양 Rev.0 by 김은수.md` 파일에서 헤더 `# [Sound1] Ezairo ...`를 그대로 `name: [Sound1] Ezairo ...`로 쓰면 YAML이 `[Sound1, Ezairo, ...]` flow sequence로 해석해 파싱 실패. 서브에이전트가 자체 판단으로 큰따옴표 처리 → 정상 동작. 한 번 보면 당연하지만 평소엔 떠오르지 않는 함정.

**How to apply:**

- frontmatter 작성 시 `name` 값이 다음 중 하나로 **시작**하면 큰따옴표 감쌈 의무:
  - `[` `]` `{` `}` (flow indicators)
  - `&` `*` `!` `|` `>` `'` `"` `%` `@` `` ` `` (YAML special)
  - `#` (comment starter)
  - `?` (mapping key)
  - `-` 다음 공백 (sequence)
- 값 **중간**에 `:` + 공백 또는 ` #`(공백+해시)이 들어가도 감쌈 의무
- 안전 디폴트 — 의심스러우면 큰따옴표. 한글·영문 조합 평범한 텍스트는 감쌈 불필요
- `purpose`/`tags` 등 다른 필드도 동일 원칙 (단 `tags`는 flow sequence라 별도 — `[a, b, c]` 형태는 정상)
- 신규 frontmatter 작성 시 헤더의 첫 글자가 위 특수문자면 즉시 따옴표 처리 self-check
