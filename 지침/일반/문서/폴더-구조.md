# 폴더 구조 및 작업 레지스트리

**TL;DR**: `지침/`(산출물)·`docs/tasks/`(작업 과정 기록) 2대 카테고리(회고는 지침에 흡수, 사용방법·참고는 Wiki). **루트 저장소는 `지침/`이 `docs/` 밖 최상위로 승격**(2026-07-13~, Sound1의 `src/`에 상응하는 실제 산출물이므로) — **프로젝트는 `docs/지침/`로 `docs/` 하위 유지**(하위 프로젝트의 지침은 산출물이 아니라 보조 문서). tasks는 모듈/작업 2레벨 고정, 작업 폴더명은 `YYYYMMDD_<slug>` 날짜 prefix. 표준 산출물 4파일: 요구사항.md·분석.md·계획.md·이력 및 결과.md. 작업 레지스트리는 3축 — **모듈별 `작업 목록.md`**(작업 단위 생애주기, 해당 모듈 한정)·**루트 `작업 목록.md`**(모듈 링크만 거는 인덱스)·`모듈 현황.md`(모듈 단위 헬스). 2026-07-03 분산화(Z-2) — 단일 표 비대화 문제 해소.

## 1. 전체 레이아웃

> [!IMPORTANT]
> **루트 저장소 예외**: 아래 다이어그램은 **프로젝트 스코프**(`projects/<이름>/docs/`) 기준이다. **루트 저장소는 `지침/`이 `docs/` 밖으로 승격**되어 있다 — 즉 루트는 `지침/`(최상위)과 `docs/tasks/`(이 다이어그램의 `tasks/` 그대로)로 나뉜다. 근거: [`docs/tasks/meta/20260713_지침-폴더-승격/`](../../../docs/tasks/meta/20260713_지침-폴더-승격/).

```
docs/                                (프로젝트 스코프 — 루트는 지침/이 docs/ 밖 최상위)
├── 지침/                           영속 — 작업 규칙·컨벤션·검증 체크리스트 (회고 흡수)
│   ├── 작업 규칙.md                (마스터 체크리스트)
│   ├── 일반/
│   │   ├── 문서 작성 규칙.md (인덱스)
│   │   ├── 문서/                  (분할 — 폴더-구조·메타-frontmatter·작성-스타일)
│   │   ├── 작업 진행 규칙.md (인덱스)
│   │   └── 작업/                  (분할 — 4단계-프로세스·완료처리)
│   ├── Git/
│   ├── 코딩/
│   └── (프로젝트 특화 지침)
└── tasks/                          작업 스코프 (루트도 동일 — docs/tasks/)
    ├── 작업 목록.md                     루트 인덱스 (모듈별 목록 파일 링크만 — Z-2, 2026-07-03~)
    ├── 모듈 현황.md                모듈 인덱스 (모듈 단위 헬스)
    └── <모듈>/                      작업 폴더 (활성·완료 무관 영구 위치)
        ├── 작업 목록.md             모듈 작업 레지스트리 (작업 단위 생애주기, 해당 모듈 한정 — Z-2)
        └── YYYYMMDD_<작업슬러그>/  (날짜 prefix — Z-1, 2026-05-18~)
            ├── 요구사항.md
            ├── 분석.md
            ├── 계획.md             (코딩 작업은 구현계획.md alias 호환)
            └── 이력 및 결과.md     (시계열 로그 + 완료 시 요약 추가)
```

## 2. 영속 문서 (persistent)

- 유형별 **폴더 이름 자체가 카테고리** 역할. 파일명에 프리픽스 안 붙임
- **지침/** 은 **각 스코프 독립** 영속 폴더:
  - 루트 `지침/` — **`docs/` 밖 최상위**(2026-07-13 승격). 전역 공통 지침 (작업 규칙·Git·코딩·일반) + 회고 흡수분 (`maturity: experimental`)
  - 프로젝트 `docs/지침/` — **`docs/` 하위 유지**(프로젝트는 지침이 산출물이 아니라 보조 문서). 프로젝트 특화 지침 (예: Sound1 `docs/지침/레지스터 변경 검증 체크리스트.md`)
- **체크리스트·검증 기준은 지침의 하위 유형**이므로 `지침/` 에 직접 배치 (`기준/` 폴더 사용 금지)
- 지침/ 하위는 2레벨까지 허용 (`일반/`, `Git/`, `코딩/`). 그 이상 깊이는 지양 — 단 분할된 거대 지침은 `일반/문서/`·`일반/작업/` 같이 3레벨 OK (2026-05-18~)
- **사용방법·참고**성 영속 지식은 rules `docs/`에 두지 않고 **별도 wiki repo**(`E:\workspace\projects\wiki`)에 둔다. 반영은 은수님이 수동으로 판단 — rules는 wiki 운영에 관여하지 않는다
- 파일명은 **의미 있는 제목**으로 간결히 (예: `커뮤니케이션 규칙.md`)
- 모든 영속 .md는 frontmatter에 `maturity: core | stable | experimental` 명시 ([`메타-frontmatter.md`](메타-frontmatter.md) §1 참조)

## 3. 작업 문서 (task-scoped)

- 경로: `tasks/<모듈>/YYYYMMDD_<작업슬러그>/`
- **2레벨 고정**: 모듈 아래 바로 작업 폴더. 서브토픽(brightness/dimming/pattern 등)은 폴더가 아닌 **작업 목록.md의 태그**로 표현
  - 이유: 3레벨은 경계 판단 애매(한 작업이 복수 서브토픽에 걸침)로 분류 경직화 위험
- 모듈 이름은 **도메인 용어** (루트: `meta`/`git`/`docs`/`tools` 등 / Sound1: `LED`/`touch`/`power` 등)
- 작업 슬러그는 **`YYYYMMDD_<kebab-case>`** 권장 (날짜 prefix 2026-05-18~). 날짜는 작업 시작일. 한글도 허용하되 의미 명확할 때만
- 필수 파일: `요구사항.md`, `분석.md`, `계획.md`, `이력 및 결과.md` (코딩 작업의 `구현계획.md`는 alias로 호환)
- 각 산출물의 **표준 양식**은 [`../작업/양식/`](../작업/양식/) 폴더 — 신규 작업 시 복사해 사용 (4개 양식 모두 maturity: core)
- `이력 및 결과.md`는 **단계 ① 시작과 동시에 생성** — 시계열 로그(진행 중 누적) + 완료 요약(종료 시 추가). 상세: [`../작업/4단계-프로세스.md §2`](../작업/4단계-프로세스.md)
- **첨부 파일 명명 (4종 외)**: 작업 폴더에 4종 표준 외 보조 문서·이미지·.txt 등이 필요한 경우 **`첨부_<단계>_<제목>.<ext>`** 형식으로 명명. <단계>는 어느 표준 산출물의 보조인지를 의미: `요구사항`·`분석`·`계획`·`이력` 중 택1.
  - 예: `첨부_분석_CFX 주파수밴드-전극-채널 매핑 Rev.2.md`, `첨부_분석_회로도.png`, `첨부_계획_단계별 일정.png`, `첨부_이력_검증 로그.txt`
  - 작업 폴더 평탄 유지 (서브폴더 X). 첨부 다수 시 정렬은 prefix로 자연스럽게 그룹화. **예외: `에이전트-로그/` 서브폴더** — 서브에이전트 오케스트레이션 감사 기록은 이 폴더에 모은다 (상세: [`../../서브에이전트/로그 구조.md`](../../서브에이전트/로그%20구조.md))
  - 본 컨벤션은 **2026-05-18 Package C 마무리**에서 도입 (그 이전 작업 폴더의 기존 첨부 파일은 일괄 rename으로 적용 완료)

## 4. 완료 처리

사용자 *"작업 끝났어. 마무리해"* 시그널 수신 시 다음 절차로 완료 처리한다. **archive 폴더 폐지(2026-05-15~)** — 작업 폴더는 위치 그대로, 해당 모듈 `작업 목록.md` 상태 컬럼으로 완료 표시.

### 4.1 절차

1. **`이력 및 결과.md` 완료 요약 섹션 추가** — 시계열 로그는 진행 중 누적되어 이미 존재 (형식은 §4.2)
2. **`tasks/<모듈>/작업 목록.md` 갱신** — 해당 모듈 목록 파일의 해당 행 `상태`를 `완료`로 변경 + `완료일` 기록 (Z-2, §5.2)
3. **`모듈 현황.md` 갱신** — 모듈 인덱스에 작업 반영 ([`../작업/완료처리.md`](../작업/완료처리.md))
4. **커밋 → 사용자 승인 → `--no-ff` 병합**

### 4.2 `이력 및 결과.md` 완료 요약 섹션 형식

`이력 및 결과.md` 본문 골격은 [`../작업/4단계-프로세스.md §2`](../작업/4단계-프로세스.md) 참조. 완료 시 추가되는 `## 완료 요약` 섹션:

```markdown
## 완료 요약

**기간:** YYYY-MM-DD ~ YYYY-MM-DD
**모듈/태그:** <모듈> / <쉼표 구분 태그>
**병합:** `<대상 브랜치>` ← `<작업 브랜치>` (`<merge commit hash>`)
**연계 작업:** → [...](...) (없으면 생략)

### 무엇을 했는가
한 문단. 결과물 중심으로.

### 핵심 결정
- 왜 이렇게 했는지 — 대안 대비 선택 이유 (1~3개)

### 후속 영향
- 추가 작업 / 지침 갱신 등 (없으면 생략)
```

> [!NOTE]
> 작업의 4개 문서(`요구사항.md`/`분석.md`/`계획.md`/`이력 및 결과.md`)는 작업 폴더에 영구 보존. `이력 및 결과.md`의 시계열 로그가 진행 중 모든 결정·이슈를 누적하고, 완료 요약 섹션은 "원본 산출물 들춰볼지 판단하기 위한 1페이지 요약" 역할.

## 5. 작업 레지스트리 — 3단 구조

### 5.1 설계 원칙 (Z-2, 2026-07-03)

작업이 누적될수록 루트 단일 표가 기하급수적으로 비대해지는 문제(실증: Sound1 12모듈·47행·88KB, 타 6개 프로젝트 합계의 6.5배)를 해소하기 위해 작업 레지스트리를 3단으로 분리한다:

| 레지스트리 | 위치 | 스코프 | 역할 |
|---|---|---|---|
| **모듈 작업 목록** | `tasks/<모듈>/작업 목록.md` | 모듈 1개 | 작업 단위 생애주기 상세 |
| **루트 작업 목록** | `tasks/작업 목록.md` | 전체 | 모듈 존재·링크만 안내하는 순수 라우터 |
| **모듈 현황** | `tasks/모듈 현황.md` | 전체 | 모듈 단위 헬스 통계(§6, 변경 없음) |

> [!IMPORTANT]
> 루트 작업 목록과 모듈 현황은 **역할이 다르다** — 통합하지 않는다(§6.1 "정렬 모순" 결정 유지). 루트 작업 목록은 통계를 갖지 않는 순수 링크 라우터, 모듈 현황은 통계 스냅샷이다.

### 5.2 모듈 작업 목록 — `tasks/<모듈>/작업 목록.md`

**목적**: 해당 모듈의 모든 작업의 활성/완료 상태·태그·요약·연계 관계를 관리. 새 작업 시 같은 모듈의 기존 작업 맥락을 한눈에 확인(구 루트 단일 표의 역할을 모듈 스코프로 계승).

**파일 구조**:

```markdown
# 작업 목록 (<모듈> tasks index)

`<모듈>` 모듈의 작업 레지스트리. 상태 정의는 [루트 인덱스](../작업%20목록.md#상태-정의) 참조.

## 작업 목록

| 작업명 | 태그 | 상태 | 시작·완료 | 폴더 | 연계 | 요약 |
|---|---|---|---|---|---|---|
| ... | ... | 진행 | YYYY-MM-DD | [...](...) | → [...](...) | ... |

## 갱신 이력

| 날짜 | 이벤트 |
|---|---|
```

컬럼 정의는 구 §5.3과 동일(작업명·태그·상태·시작완료·폴더·연계·요약) — **모듈 컬럼만 제거**(파일 스코프 자체가 모듈). 상태 정의 표는 루트에만 두고 참조(중복 방지).

**갱신 이벤트**:

| 이벤트 | 동작 |
|---|---|
| 작업 시작 (폴더 생성 시) | 해당 모듈 `작업 목록.md`가 없으면 신설(위 파일 구조로) + 행 추가(상태=`진행`). **신규 모듈이면 루트 `작업 목록.md`에도 링크 행 추가** |
| `이력 및 결과.md` 시계열 로그 갱신 | 해당 행의 `상태`·`요약` 업데이트 (필요 시) |
| 사용자 `작업 끝났어. 마무리해` 시그널 | (1) `이력 및 결과.md` 완료 요약 추가 → (2) 해당 모듈 `작업 목록.md` 행의 `상태`를 `완료`로 변경·`완료일` 기록 → (3) `모듈 현황.md` 해당 모듈 행 갱신 |

### 5.3 루트 작업 목록 — `tasks/작업 목록.md` (인덱스)

**목적**: **순수 링크 라우터**. 어떤 모듈이 있고 각 모듈의 상세 작업 목록이 어디 있는지만 안내. 통계는 갖지 않는다(모듈 현황.md 역할).

**파일 구조**:

```markdown
# 작업 목록 (tasks index)

각 모듈의 상세 작업 레지스트리는 아래 링크 참조. 통계(작업 수·최종 업데이트)는 [`모듈 현황.md`](모듈%20현황.md) 참조.

## 모듈

| 모듈 | 목록 |
|---|---|
| `<모듈>` | [tasks/<모듈>/작업 목록.md](<모듈>/작업%20목록.md) |

## 상태 정의

| 상태 | 의미 |
|---|---|
| `진행` | 작업 진행 중 |
| `대기` | 선행 조건 충족 대기 (다른 작업 완료·사용자 지시 등) |
| `차단` | 외부 요인으로 진행 불가 (이슈 명시 필요) |
| `완료` | 병합·릴리즈 완료 |
| `취소` | 작업 취소 (이유 명시) |
```

상태 정의는 여기가 **정본** — 모듈별 작업 목록.md는 링크로만 참조.

### 5.4 새 작업 라우팅 절차 (갱신)

1. 사용자가 새 작업을 지시하면 루트 `tasks/작업 목록.md`에서 관련 모듈 존재 여부 확인
2. 모듈이 있으면 해당 `tasks/<모듈>/작업 목록.md` 조회 → 같은 모듈·태그의 관련 작업이 있으면 사용자에게 확인:
   > **"기존 `<폴더>`에서 이어가시겠어요, 신규로 분리하시겠어요?"**
3. 확인 답변대로 기존 폴더 재사용 또는 신규 폴더 생성 (신규는 `YYYYMMDD_<slug>` 날짜 prefix)
4. 신규 모듈이면 루트 `작업 목록.md`에 모듈 행 추가 + 해당 모듈 `작업 목록.md` 신설·등재. 기존 모듈이면 해당 모듈 `작업 목록.md`에만 등재

## 6. 모듈 인덱스 — `tasks/모듈 현황.md`

### 6.1 목적

**모듈 단위 헬스 스냅샷**. 모듈별 최종 업데이트·작업 수·최근 작업을 한눈에.

작업 목록.md(작업 단위 생애주기 추적)와 차원이 다름. 둘 다 유지가 정답(통합 시 정렬 모순).

모듈별 작업 상세는 [`tasks/<모듈>/작업 목록.md`](#52-모듈-작업-목록--tasks모듈작업-목록md) 참조 (§5.2).

### 6.2 갱신 트리거

작업 종료 처리 시 자동 갱신 — [`../작업/완료처리.md`](../작업/완료처리.md) 참조.

## 7. Cross-module 연계 표현

### 7.1 peer-to-peer 링크

- 작업 A가 작업 B의 결과에 의존하거나 기능적으로 얽힐 때 사용
- 각 행의 `연계` 컬럼에 상대 작업 마크다운 링크 (양쪽 symmetric하게 서로 참조)
- 예:
  - A: `→ [LED/20260420_pwm-tune](../LED/20260420_pwm-tune/)`
  - B: `→ [debug/20260418_rtt-ext](../debug/20260418_rtt-ext/)`

### 7.2 feature 태그

- 3개 이상 작업이 하나의 상위 기능을 구성할 때 사용
- 공통 태그 `feature:<이름>` 을 모든 관련 작업에 부착
- 예: `feature:auto-dim` 태그로 LED·sensor·comms 작업 묶어 식별

### 7.3 두 방식은 병행 가능

| 상황 | 방식 |
|---|---|
| 2개 peer 관계 | 연계 링크 |
| 3개 이상 feature 그룹 | feature 태그 |
| 둘 다 | 연계 링크 + feature 태그 |

### 7.4 upgrade 경로 (현 단계 미도입)

feature 규모가 커져 공통 아키텍처·요구사항 문서가 필요해지면 `docs/features/<기능명>/` 폴더 도입 후 `작업 목록.md`에서 해당 feature 태그로 집계. 지금은 YAGNI로 미도입.
