# 세션 인수인계 규칙

**TL;DR**: 세션 경계에서 **다음 컨텍스트가 읽을 요약**을 프로젝트 `docs/세션_인수인계/` 에 남긴다. 파일명은 `YYYYMMDD_HHmm_<주제>.md`. **구간은 대화 컨텍스트가 아니라 git 으로 잡는다** — 직전 요약 문서가 커밋된 지점부터 `HEAD` 까지. 그래야 compact 가 여러 번 일어나도 추적이 끊기지 않는다. 반드시 담을 것은 **구간 · 지금 상태 · 한 일 · 자산 · 남은 것 · 권장 순서** 여섯이며 그중 **자산**이 이 문서의 존재 이유다.

## 1. 언제 쓰는가

| 시점 | 비고 |
|---|---|
| **세션 종료** | 다음 세션이 읽는다 |
| **compact 직전** | 같은 세션의 압축된 컨텍스트가 읽는다 |
| 큰 작업 묶음 완료 | 중간 정리 |
| 사용자가 *"요약해줘"* | 위 어느 경우든 |

> [!NOTE]
> **compact 요약과 세션 인수인계를 나누지 않는다.** 독자만 다르고 내용이 같다(지금 상태 · 남은 것 · 자산). 나누면 «어디에 쓸지» 를 매번 판단해야 하고 같은 성격의 문서가 두 곳에 흩어진다.

## 2. 어디에 쓰는가

**프로젝트별로 `docs/세션_인수인계/`** 에 모은다. 폴더에 `README.md` 인덱스를 두고 최신순 표로 관리한다.

| 항목 | 규칙 |
|---|---|
| 파일명 | `YYYYMMDD_HHmm_<주제>.md` — **시각 prefix 필수**(하루에 여러 번 나온다) |
| 인덱스 | `README.md` 에 한 줄 추가 (날짜 · 링크 · 요지) |
| 기존 파일 | 규약 도입 전 파일은 **소급해 이름을 바꾸지 않는다** — 링크·커밋 메시지에 인용돼 있어 고치면 그쪽이 깨진다 |

프로젝트 `CLAUDE.md` 의 세션 시작 절차에 **«최신 문서 1건 Read»** 를 배선한다. 규약만 만들고 진입점에 연결하지 않으면 작동하지 않는다.

## 3. 구간을 어떻게 잡는가 (핵심)

> [!CAUTION]
> **대화 컨텍스트를 앵커로 쓰면 안 된다.** compact 가 **두 번 이상** 일어나면 1차 요약과 그 뒤 대화가 통째로 다시 요약되면서 «지난 요약 이후» 라는 경계가 녹아 사라진다. 게다가 그 시점엔 세부가 이미 소실돼 있다.

**앵커는 git 이다.** 직전 요약 문서가 **커밋된 지점**부터 잡는다.

```sh
PREV=$(git log --format=%H --reverse -- "docs/세션_인수인계/<직전문서>.md" | head -1)

git log $PREV..HEAD              # 그 이후에 한 일 전부
git log $PREV..HEAD --format=%B  # 본문까지 (판단 근거가 여기 있다)
```

### 3.1 해시를 문서에 손으로 적지 않는다

«이 문서 작성 시점 `HEAD`» 를 적는 것은 **자기참조**다. 문서를 커밋하는 순간 `HEAD` 가 바뀌어 적어둔 해시가 한 커밋 뒤처진다. **파일 경로로 찾으면 그 문제가 없다.**

문서 §0 에는 **직전 기준점**(이미 확정된 과거 해시)과 **구간 커밋 수**, 그리고 위 명령만 적는다.

### 3.2 전제 - 커밋 메시지에 «왜» 를 적어야 한다

이 방식은 **커밋 메시지가 판단 근거를 담고 있을 때만** 성립한다.

| 커밋 메시지 | `git log` 로 재구성 |
|---|---|
| "무엇을 바꿨다" 만 | **불가능** — 파일 목록은 `git diff` 로도 나온다 |
| **"전제가 뒤집혔다 / 이 근거로 이렇게 판단했다 / 이 함정에 빠졌다"** | **가능** |

> [!IMPORTANT]
> **커밋 메시지는 세션의 백업이다.** 컨텍스트는 날아가지만 커밋은 남는다. 판단·근거·실측값을 본문에 적어 두면 요약을 쓸 때 그대로 재료가 된다.

### 3.3 git 이 담지 못하는 것

**접었던 대안 · 사용자의 구두 지시 · 실패한 시도**는 커밋에 없다. 이건 요약 문서 **본문**이 담아야 한다.

정리하면 역할이 이렇게 갈린다.

| 보관처 | 담는 것 |
|---|---|
| **git 커밋 메시지** | 사실 · 수치 · 판단 근거 |
| **요약 문서 본문** | 맥락 · 함정 · 접은 대안 · 구두 지시 |

둘 다 컨텍스트 **밖**에 있으므로 압축에 영향받지 않는다.

## 4. 반드시 담을 것

| # | 절 | 내용 |
|---|---|---|
| 0 | **구간** | 직전 기준점 해시 · 구간 커밋 수 · §3 의 구간 명령 |
| 1 | **지금 상태** | 브랜치 · 원격 격차 · 테스트 통과 수 · 빌드 결과 · 상시 점검 항목 |
| 2 | 한 일 | **병합 해시와 함께.** 해시가 없으면 되짚을 수 없다 |
| 3 | **자산** | **가장 중요.** 이번에 알아낸 함정 · 규칙 · 뒤집힌 전제 |
| 4 | 남은 것 | **왜 막혀 있는지까지.** "남았다" 만으로는 다음 사람이 판단 못 한다 |
| 5 | 권장 순서 | 다음 세션이 첫 30분에 할 일 |

> [!CAUTION]
> **§3 자산이 이 문서의 존재 이유다.** 무엇을 했는지는 `git log` 로도 알 수 있다. **왜 그렇게 했고 어디에 함정이 있었는지**는 여기에만 남는다.
>
> 자산에 적을 만한 것: 전제가 실측과 달랐던 사례 · 검증 도구가 거짓 판정한 원인 · 같은 실수를 두 번 한 것 · 빌드/도구의 비직관적 동작.

## 5. 안티패턴

| 하지 말 것 | 이유 |
|---|---|
| compact 요약 폴더를 따로 만들기 | 같은 성격 문서가 흩어진다. 독자만 다르고 내용은 같다 |
| «이 문서 작성 시점 HEAD» 를 적기 | 자기참조 — 커밋 순간 한 칸 뒤처진다 |
| 커밋 메시지에 «무엇» 만 적기 | `git log` 재구성이 불가능해져 요약이 컨텍스트에 의존하게 된다 |
| 남은 일을 목록으로만 적기 | **왜 막혀 있는지**가 없으면 다음 세션이 같은 조사를 반복한다 |
| 규약만 만들고 `CLAUDE.md` 에 배선 안 하기 | 작동하지 않는다 |

## 학습 노트

### 2026-08-06 · Sound1 — 이 규칙의 출처

은수님이 *"compact 후 한참 작업하다 요약해 라고 하면 지난 compact 부터 지금까지만 추려낼 수 있나?"* 를 물으면서 정립됐다.

- 그 세션에서 직전 인수인계 커밋 이후 **38커밋 · 커밋 본문 1,199줄**이 정확히 잘려 나오는 것을 실측으로 확인했다.
- 처음에는 문서에 «작성 시점 `HEAD`» 를 적으려 했으나 **자기참조**임을 발견해 파일 경로 방식으로 바꿨다.
- 그 세션의 커밋들이 «전제가 뒤집혔다 / 이 근거로 판단했다» 를 담고 있어 1,199줄이 나왔고, 그것이 이 방식이 성립하는 전제임을 드러냈다.
