# Git 규칙

**TL;DR**: `main`은 사용자 전용. Claude는 `claude_*` 브랜치에서 작업. rules와 각 프로젝트는 엄브렐러 아래 **형제 독립 repo**이며 **세션이 열린 저장소(cwd) 하나가 작업 대상**. 모든 병합 `--no-ff` + 병합 전 사용자 승인. Identity는 `김은수 <eunsu.kim@to-doc.com>`, AI 표시(Co-Authored-By 등) 절대 금지.

## 브랜치 모델

| 브랜치 | 용도 | 분기 원점 | 병합 대상 |
|---|---|---|---|
| `main` | 릴리즈 전용 (사용자 직접 관리) | — | — |
| `claude_main` | Claude 측 안정 브랜치 | `main` | `main` (사용자 승인 시) |
| `claude_develop` | 지속 개발 | `claude_main` | `claude_main` |
| `claude_feature_*` | 기능 구현/수정 | `claude_develop` | `claude_develop` |
| `claude_hotfix` | main 긴급 수정 | `claude_main` | `claude_main` + `claude_develop` |

## 브랜치 규칙

> [!CAUTION]
> `main`에 직접 커밋·푸시 **절대 금지**. 사용자가 릴리즈 시점에 직접 관리한다.

- Claude의 모든 작업은 `claude_` 접두사 브랜치에서 수행.
- 기능 개발: `claude_develop`에서 `claude_feature_<설명>` 분기 → 완료 후 `claude_develop`에 병합.
- 안정 병합: 사용자 요청 시 `claude_develop` → `claude_main` 병합.
- 긴급 수정: `claude_main`에서 `claude_hotfix` 분기 → 수정 후 양쪽에 병합.

## 병합 규칙

- **모든 병합은 `--no-ff`** (fast-forward 금지)로 수행. merge commit을 남겨서 이력 보존.
- 사용자가 명시적으로 요청할 때만 커밋 정리(squash/rebase).

## 작업 흐름 (기본: 브랜치 체크아웃)

1. 파일 수정 전, feature 브랜치 생성 후 `git checkout`으로 전환.
2. 작업 완료 후: 커밋 → **사용자 확인** → `--no-ff` 병합 → feature 브랜치 삭제.
3. 커밋 완료 후, 대상 브랜치에 병합하기 전에 **반드시 사용자에게 확인**을 받는다.

> [!IMPORTANT]
> 커밋과 병합은 별개의 단계다. 커밋이 끝났다고 바로 병합하지 말 것.

## 머지·푸시 후 기본 브랜치 복귀

`claude_main` 머지·푸시 완료 직후 즉시 작업 기본 브랜치인 `claude_develop` 으로 체크아웃 복귀한다. 모든 repo (루트 + 모든 `projects/<이름>/`) 에 동일 적용.

**Why:** `claude_main` 은 안정 브랜치이고 직접 작업 금지 영역인데, 머지 사이클 종료 후 그대로 머무르면 다음 작업의 워킹트리 변경이 `claude_main` 에 자동 누적되는 위험. 작업 진입 기준은 항상 `claude_develop` 이어야 하므로 사이클 종료 시 자동 복귀로 다음 작업 진입 비용을 0 으로 만든다.

**How to apply:**

1. `git push origin claude_develop claude_main` 완료 + (해당 시) `git branch -d claude_feature_*` 직후 즉시 `git checkout claude_develop` 실행
2. feature 브랜치 미삭제 케이스 (보존 결정 등) 에도 동일 적용
3. 작업 사이클 종료 보고는 `claude_develop` 복귀까지 완료한 상태에서 사용자에게 전달
4. 적용 범위 = 루트 + `projects/<모든>/` 동일 브랜치 모델 사용 repo 전체. 다른 projects 도 항상 `claude_develop` 상시 유지

**예외:**

- 사용자가 `claude_main` 잔존을 명시 지시한 경우만 면제 (해당 작업 단위 한정)
- `claude_main` 전용 작업 진행 중 (예: release tag, hotfix 차상위) — 시작·종료 시점만 main 외 유지 가능

> [!NOTE]
> 다른 브랜치 (`claude_develop`, `claude_feature_*`) 의 사이클에서도 마지막에 `claude_develop` 으로 돌아온 상태를 유지한다. `claude_main` 체류는 release·머지 직후 *순간*에만 허용.

## 워크트리 (사용자 명시 요청 시에만)

- 사용자가 "워크트리로 작업"이라고 명시한 경우에만 워크트리 생성.
- 디렉토리 이름: `wt_<브랜치명>` 형식.
- 병합 완료 후 워크트리 제거.

> [!WARNING]
> 병합 전에 워크트리를 제거하지 말 것. 커밋 유실 위험.

## 작업 스코프 (한 세션 = 한 repo)

> [!IMPORTANT]
> 새 구조(2026-07-13~)에서 rules와 각 프로젝트는 엄브렐러(`E:\workspace\`) 아래 **형제 독립 repo**다(git-under-git 소멸). **세션이 열린 저장소(cwd) = 작업 대상 repo**이며, 변경·커밋은 모두 그 repo 하나에 대해 이뤄진다.

### 스코프 판정

| 세션 cwd | 커밋 대상 repo |
|---|---|
| `E:\workspace\rules\` (이 저장소) | rules repo |
| `E:\workspace\projects\<이름>\` | 해당 프로젝트 repo |

한 repo에서 다른 repo의 파일은 보이지 않으므로, 옛 "한 세션에서 루트와 프로젝트를 동시에 변경" 시나리오는 발생하지 않는다. 다른 repo 작업이 필요하면 그 repo 폴더에서 **별도 세션**을 연다.

### repo 간 연계

두 repo에 걸친 작업(예: 프로젝트 변경 + rules 지침 갱신)이 필요하면, 각 repo에서 각각 세션·브랜치·커밋으로 처리하고, 의존이 있으면 `tasks/<모듈>/<작업>/`의 `연계` 컬럼·peer link로 표현한다.

### 커밋 직전 체크리스트

- [ ] `git status`로 staged 파일이 현재 repo 소속인지 확인
- [ ] 현재 브랜치가 `claude_*` 브랜치인지 확인

## 프로젝트별 적용

각 `projects/<이름>/` repo도 동일한 브랜치 모델과 작업 흐름·`--no-ff` 병합·Git Identity 규칙을 독립적으로 적용한다. 프로젝트 고유 사항은 해당 프로젝트 `CLAUDE.md`에 기술.
