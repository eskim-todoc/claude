# 레지스터·하드웨어 설정 검증

**TL;DR**: 레지스터 값이나 하드웨어 설정을 바꾸기 전 반드시 통과해야 하는 5게이트 — ① 설정 대상 식별 → ② 근거 확인 → ③ 전후 동작 시뮬레이션 → ④ 부작용 체크 → ⑤ 불확실성 명시. **추측이 섞이면 변경 금지**(추가 조사 우선). 실기 테스트 전 게이트키퍼이며, 벤더·버스 종류와 무관하게 적용한다.

> [!IMPORTANT]
> 하드웨어 설정은 **틀려도 컴파일이 통과하고, 증상이 엉뚱한 곳에서 나타난다**. 그래서 코드 리뷰가 아니라 **변경 전 게이트**로 막는다. 5게이트 중 하나라도 "미확인"이 남으면 실기 테스트로 넘어가지 않는다.

## 1. 적용 대상

| 대상 | 예 |
|---|---|
| 외부 IC 레지스터 | 버스 경유(I2C·SPI 등) 센서·코덱·PMIC의 설정 레지스터 |
| MCU peripheral 레지스터 | MMIO — 타이머·ADC·DMA·UART·I2S 등 |
| 시스템 설정 | 클럭 트리·분주비, GPIO(모드·풀·속도·핀 mux), 전원 도메인·저전력 모드, 인터럽트 우선순위·마스크 |
| 시퀀스 | 부트·초기화에서의 **설정 순서**(클럭 인에이블 → 설정 기록 → 활성화 등) |

**미적용**: 순수 소프트웨어 상수·로직 변경(하드웨어 상태에 직접 관여하지 않는 것).

## 2. 체크리스트 (5게이트)

### 2.1 설정 대상 식별

- [ ] 레지스터 주소·비트 범위(또는 설정 파라미터)와 **변경 전/후 값**을 명시
- [ ] 해당 레지스터의 **전체 비트 필드**를 근거 문서에서 확인 — 변경 대상 비트뿐 아니라 같은 레지스터의 다른 비트도
- [ ] 변경하지 않는 비트가 의도한 값으로 유지되는지 확인 (read-modify-write인지, 통째 write인지)
- [ ] **예약(reserved) 비트** 취급 규칙 확인 (0 유지 강제·write 금지 등)

### 2.2 근거 확인

- [ ] 변경하려는 값의 근거를 **원문 그대로 인용** — 데이터시트 / 레퍼런스 매뉴얼 / SDK 헤더 주석·공식 / 벤더 앱노트
- [ ] **"~일 것이다", "~인 것 같다" 같은 추측이 포함되어 있으면 변경 금지** → 추가 조사 필요
- [ ] 해당 모드/값이 다른 레지스터·기능에 미치는 영향을 근거 문서에서 확인
- [ ] 클럭·타이밍 파라미터는 **실제 공급 클럭 체인**을 확인 — 시스템 클럭 직결로 가정하지 않는다([`작업 규칙.md §7.2`](작업%20규칙.md))

### 2.3 전후 동작 시뮬레이션

- [ ] **변경 전**: 현재 동작과 문제점을 정확히 서술
- [ ] **변경 후**: 예상되는 동작을 단계별로 서술
- [ ] 변경이 **초기화 시퀀스의 다른 단계**에 영향을 주는지 (설정 순서 의존성)
- [ ] 변경이 **런타임 동작**(폴링·이벤트·인터럽트 주기·자동 보정/필터 상태)에 영향을 주는지
- [ ] 즉시 반영인지 **지연 반영**인지 (shadow 레지스터·update 이벤트·재시작 필요 여부)

### 2.4 부작용 체크

- [ ] 해당 설정을 **참조·공유하는 다른 레지스터·기능·모듈**이 있는지 확인
- [ ] **자동 보정·자동 재시작 기능**(auto-calibration, 자동 재초기화, 자동 튜닝 등)에 영향을 주는지
- [ ] **저전력·전원 모드 전환** 시 해당 설정이 유지되는지 (도메인 리셋으로 소실되는지)
- [ ] **클럭 게이팅·리셋**으로 설정이 날아가는지, 재설정 경로가 있는지
- [ ] **공유 자원 충돌** — DMA 채널·인터럽트 라인·핀 mux·타이머 채널을 다른 기능이 쓰는지 (`Grep`으로 전수 확인, 추정 금지 — [`분석·디버깅 규칙.md §1`](분석·디버깅%20규칙.md))

### 2.5 불확실성 명시

- [ ] 확실하지 않은 부분이 있으면 **"미확인"으로 명시**하고 사용자에게 알림
- [ ] 미확인 항목이 있으면 **실기 테스트 전에 해결 방안 제시** — 문서 추가 확인 / 벤더 기술지원 문의 / 실측(로그·계측기)
- [ ] 미확인이 남은 채로 변경을 강행하지 않는다 — 위험을 고지하고 사용자 판단을 받는다

## 3. 적용 예시

범용 MCU 타이머 사례 — 판정 흐름(특히 **미확인 → 보류**)을 보여주는 것이 목적이다.

```
[변경 요청] TIM3 prescaler(PSC)를 71 → 35로 변경해 tick 주기를 1ms → 0.5ms로

1. 설정 대상 식별
   - 레지스터: TIM3_PSC[15:0], 변경 전 71 → 변경 후 35
   - 같은 타이머의 ARR(자동 재적재), CR1(CEN·DIR)은 변경 없음
   - reserved 비트 없음 (16비트 전체가 prescaler 필드)

2. 근거 확인
   - 레퍼런스 매뉴얼 원문: "Counter clock = CK_PSC / (PSC[15:0] + 1)"
   - SDK 헤더 주석: TIM3는 APB1 타이머 클럭(APB1 분주 시 x2 = 72MHz) 공급
     → 시스템 클럭 직결 가정 금지 (§2.2 클럭 체인)
   - 계산: 72MHz/(71+1)=1MHz → ARR=999로 1ms. 35 적용 시 72MHz/36=2MHz → 0.5ms

3. 전후 동작 시뮬레이션
   - 변경 전: 1ms tick, ISR 1000회/초
   - 변경 후: 0.5ms tick, ISR 2000회/초 → ISR 부하 2배
   - 초기화 순서: 클럭 인에이블 후 PSC 기록 (현 시퀀스 유지, 영향 없음)
   - 지연 반영: PSC는 shadow — 다음 update 이벤트(또는 UG)까지 미반영

4. 부작용
   - 같은 타이머를 쓰는 PWM 출력 채널이 있으면 주파수도 2배 → 확인 필요
   - ISR 2배 부하가 main loop 시간 예산을 침범할 가능성
   - 저전력 모드 APB1 게이팅 시 타이머 정지 — 기존과 동일(변화 없음)

5. 불확실성
   - ⚠ 미확인_1: TIM3 PWM 채널 사용 여부 → Grep으로 TIM3 CCR 사용처 전수 확인 필요
   - ⚠ 미확인_2: ISR 2배 시 main loop 여유 → 실측 필요
   - 결론: 미확인 2건 → 실기 테스트 전 해결. 해결 전까지 변경 보류, 사용자에게 고지
```
