# 밸리데이션 계층화

**TL;DR**: 코드를 **유닛 → 모듈 → 시스템**으로 계층 분해하고 **의존성 기반 테스트 순서**("A는 B 통과 전제")를 규정한다. 핵심 3가지: ① **유닛이 다른 유닛을 사용해도 자동으로 모듈로 승격되지 않는다**(의존성은 테스트 순서로 표현) ② **통합 테스트 = 모듈 내 모든 유닛을 함께 활성화해도 각 유닛이 원래대로 동작하는지 확인** ③ 합성은 유닛+유닛=모듈, 모듈+모듈=더 큰 모듈, 전 모듈 통합=시스템. 설계는 **단순·특화**(과도 추상화 금지) + **독립성 기준 자연 분해**. §7에서 코딩·리팩터링·문서·계획 4방향 적용을 규정한다.

> [!IMPORTANT]
> 본 방법론은 **모든 리팩토링·모듈화 작업에 일관 적용**하는 표준이다. 작업 프로세스의 **③ 분석·⑤ 계획**에서 본 계층 모델로 분해하고, **⑧ 구현 검증**에서 본 테스트 정의를 따른다([`../일반/작업/작업-프로세스.md`](../일반/작업/작업-프로세스.md)).

## 1. 밸리데이션 생명주기

```mermaid
flowchart LR
    U1["유닛 구현"] --> U2["유닛 테스트"] --> I1["통합 계획"] --> I2["통합<br/>(유닛→모듈)"] --> I3["통합 테스트"] --> S["시스템 테스트"]
```

- 좌→우 순서로 진행하며, 각 단계는 **이전 단계의 통과를 전제**로 한다.
- 리팩토링·모듈화 작업의 분석·계획·검증은 이 생명주기에 맞춰 구조화한다.

## 2. 계층 정의

### 2.1 유닛 (Unit)

- **최소의 독립 테스트 단위**. 단독으로 **자극(입력) → 응답(출력)** 검증이 가능한 것.
- 권장: **순수 로직**(하드웨어 레지스터·전역 상태 비의존, 입력→출력이 결정론적). 예: 변환 수식, 정렬·시프트 계산, 상태 전이 판정.
- 유닛은 다른 유닛/모듈에 **의존성(종속성)을 가질 수 있다**.

> [!IMPORTANT]
> **유닛이 다른 유닛을 사용한다고 해서 곧바로 모듈(통합)로 승격되지 않는다.**
> 의존 관계는 "**A는 B가 통과되었다는 전제로 진행**"이라는 **테스트 순서**로 표현하면 된다.

### 2.2 모듈 (Module)

- **의미 있는 유닛(들)의 묶음**(필요 시 다른 모듈 포함). 하나의 책임 단위로 함께 동작·검증되는 그룹.
- **통합 테스트의 정의**: 모듈 내 **모든 유닛을 전부 활성화한 상태에서도 각 유닛의 기능이 원래(유닛 단독 테스트 때)대로 정상 동작하는지** 확인하는 것.

### 2.3 합성 규칙

- 유닛 + 유닛 = **유닛 통합(모듈)**
- 모듈 + 모듈 = **모듈 통합(더 큰 모듈)**
- **모든 모듈의 통합 = 시스템** → 시스템 테스트.

## 3. 의존성·종속성과 테스트 순서

- 각 유닛/모듈은 다른 유닛/모듈에 **의존**할 수 있다(상태 정보 사용, 선행 처리 필요 등).
- 의존이 있으면 **테스트 순서**가 정해진다: **의존 대상이 통과된 전제 위에서** 상위 항목을 진행.
- 이 관계 명시만으로 충분한 부분도 있다(별도 추상화·코드 분리 불필요) — "A는 B 통과 전제"라는 **문서 설명**으로 갈음 가능.

## 4. 예시

```mermaid
flowchart TB
    subgraph IM["입력 모듈"]
      SRC["소스 읽기 유닛"]
      STAMP["타임스탬프 유닛"]
    end
    subgraph PM["처리 모듈"]
      COMB["버퍼 조합 유닛"]
      PM -. "타임스탬프 유닛의 상태 정보 사용(의존)" .-> STAMP
    end
    PM -- "테스트 전제: 입력 모듈 테스트 완료" --> IM
```

- 입력 모듈 = {소스 읽기 유닛, 타임스탬프 유닛, …} — 통합 테스트: 두 유닛을 함께 켜도 각자 정상.
- 처리 모듈 = {버퍼 조합 유닛, …} + **타임스탬프 유닛 상태 정보 사용(의존)**.
- **처리 모듈 통합 테스트는 입력 모듈 테스트가 완료된 것을 전제**로 진행.

## 5. 테스트 실현 모델 (온타깃 임베디드)

호스트 테스트 하네스가 없는 온타깃 임베디드 환경의 현실적 모델:

- **최종 형태 = 온타깃 테스트**: 유닛 함수의 시작 지점에 **테스트 벡터를 하드코딩**해 자극-응답을 실기에서 검증한다.
- **구조 우선**: 테스트 코드를 미리 삽입하지 않는다. "**테스트가 가능한 구조**"만 준비한다(유닛 경계·의존성 격리·결정론적 입출력).
- **테스트만을 위한 불필요한 로직을 만들지 않는다.** 단순한 유닛은 **로직 설명(문서)**으로 검증을 갈음할 수 있다.

## 6. 설계 원칙 (단순·특화)

- **현 체계에 특화**한다. 불필요한 확장성·범용화·과도한 추상화 금지. "딱 이렇게 하려는 로직이구나" 하고 한눈에 보이게.
- 간단한 glue(레지스터 설정·FIFO·디스패치)는 **하드코딩**해도 된다. 빙빙 도는 함수 추출 금지.
- 유닛 분리는 **테스트를 위한 추상화가 아니라, 독립성 기준의 자연 분해**다. 독립적이면 유닛, 서로 의존하면 그 관계를 명시(통합/전제).

> [!NOTE]
> 이 원칙은 [`구현 패턴.md`](구현%20패턴.md) §예외("단순 1-shot·순수 계산 함수는 FSM으로 만들지 않는다 — 과도한 추상화 회피")와 같은 방향이다. 계층 분해와 FSM 모두 **필요한 만큼만** 적용한다.

## 7. 적용 — 4방향

계층 모델은 코드를 쓰는 순간부터 문서·계획까지 관통한다. 각 방향에서 아래를 염두에 둔다.

### 7.1 코딩 방법

- **유닛 경계를 의식하고 함수를 짠다** — 순수 계산과 하드웨어 접근을 한 함수에 섞지 않는다. 계산은 결정론적 유닛으로, HW 접근은 얇은 glue로.
- **의존성 격리**: 전역 상태·레지스터 직접 참조를 계산 로직 안으로 끌어들이지 않는다(인자로 받거나 호출자에서 읽어 전달).
- **FSM의 `step()` 함수는 유닛 후보**다([`구현 패턴.md`](구현%20패턴.md)) — 상태·입력 → 다음 상태·출력이 결정론적이면 그대로 유닛.
- 하드웨어 설정에 관여하는 코드는 [`레지스터·하드웨어 설정 검증.md`](레지스터·하드웨어%20설정%20검증.md) 5게이트를 함께 통과시킨다.
- **테스트용 추상화 금지** — 독립성이 자연스러운 곳만 유닛으로 가른다(§6).

### 7.2 리팩터링 방법

- **동작 보존(behavior-preserving)이 전제**다. 계층 재분해는 동작을 바꾸는 작업이 아니다.
- 기존 코드에서 **유닛 후보를 식별**(독립·결정론 입출력 우선) → 독립성 기준으로 분해. "테스트하려고" 쪼개지 않는다.
- **의존은 제거 대상이 아니다** — 없애려 애쓰지 말고 "A는 B 통과 전제"라는 순서로 표현(§3).
- 분해 전후로 **테스트 순서가 유지되는지** 확인한다. 모듈 경계를 바꾸면 통합 테스트 범위도 바뀐다.
- 큰 리팩터링은 유닛 단위로 쪼개 **단계별 commit** — 각 단계가 동작 보존을 유지하게.

### 7.3 문서 작성 방법

- **`분석.md`**: 대상 코드의 **책임·의존성·데이터흐름**을 정리하고 **유닛·모듈 후보**와 **의존성 그래프**(Mermaid)를 싣는다.
- **`계획.md`**: 계층 분해 결과 + **테스트 계층·순서**("A는 B 통과 전제") + 각 요소의 **검증 방법 라벨**을 명시한다([`../문서/양식/계획.md`](../문서/양식/계획.md)).
- **검증 방법 라벨**: 각 유닛·모듈에 **[유닛테스트]** / **[통합테스트]** / **[로직설명]** 중 하나를 표기.
- **라벨 표기**: `유닛_1`·`모듈_1` 형식 (알파벳 약어 금지 — [`../문서/작성-스타일.md`](../문서/작성-스타일.md) §6).
- **다이어그램**: Mermaid `flowchart`, 의존성은 점선 `-.->`, 테스트 전제는 실선 + 라벨.

### 7.4 계획 단계 (작업 프로세스 연계)

리팩터링·모듈화 작업의 [작업 프로세스](../일반/작업/작업-프로세스.md) 각 단계에서:

| 단계 | 계층화 관점에서 할 일 |
|---|---|
| **③ 분석** | 대상 코드의 책임·의존성·데이터흐름 분석(실코드 정독). 유닛 후보 도출 + 모듈 후보(유닛 묶음) + 의존성 그래프 |
| **⑤ 계획** | 테스트 계층·순서("A는 B 통과 전제") 명시 → 통합 계획. 각 요소에 검증 방법 라벨. 설계가 **단순·특화** 원칙을 지키는지(과도 추상화·테스트용 군더더기 없는지) 확인 |
| **⑦ 구현** | 계획한 계층 경계대로 구현. 동작 보존 유지 |
| **⑧ 구현 검증** | 유닛 → 통합 → 시스템 순으로 검증(§1 생명주기). 대규모 변경은 저술↔검증 노드를 분리해 adversarial-verify([`../서브에이전트/오케스트레이션.md`](../서브에이전트/오케스트레이션.md)) |

**⑤ 계획 체크리스트**:
- [ ] 유닛 후보 도출(독립·결정론 입출력 우선) + 각 유닛의 검증 방법 라벨
- [ ] 모듈 후보(유닛 묶음)와 의존성 그래프 작성
- [ ] 테스트 계층·순서("A는 B 통과 전제") 명시 → 통합 계획
- [ ] 설계가 단순·특화 원칙 준수(과도 추상화·테스트용 군더더기 없음)
- [ ] 동작 보존(behavior-preserving) 전제 확인
