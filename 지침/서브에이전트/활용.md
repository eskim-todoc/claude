# 서브에이전트 활용

**TL;DR**: 오케스트레이션 강도는 **트리거로 결정한다**. 은수님이 "오케스트레이션·여러 페르소나·서브에이전트들로·병렬로" 등 트리거어를 쓰면 `Workflow` 도구로 **dynamic workflow(다노드 fan-out)** 를 돌린다. 그 외에는 오케스트레이터가 판단 — **간단한 일은 세션에서 직접**, 광범위 탐색·독립 병렬·대용량 처리처럼 서브에이전트 실익이 명확할 때만 (단발/소수) 위임한다(§1.1·§5). 서브에이전트는 `model: "sonnet"`(최신 Sonnet), **effort는 미지정(세션 상속)** — Sonnet의 adaptive reasoning이 작업량에 맞춰 사고량을 자동 조절한다(§3.1). 종류(`Explore`/`general-purpose`/`Plan`)를 골라 자기완결 프롬프트로 위임한다. `~/.claude/agents/` 에 정의해 둔 **명명된 전문가 패널**은 «ui 에이전트들에게» 처럼 **접두사를 복수로 지칭**하면 그 전부를 병렬 기동한다(§3.2). 트리거 기반 오케스트레이션 정책(은수님 2026-07-03, 전면 위임 정책 대체).

## 1. 적용 범위와 강도

| 항목 | 내용 |
|---|---|
| 적용 범위 | **모든 작업** — 단 오케스트레이션 강도는 작업 성격·트리거로 조절 |
| 활용 강도 | **트리거 기반** — 오케스트레이션 트리거어 → dynamic workflow / 그 외 → 판단(간단하면 직접, 실익 명확할 때만 위임) |
| 우선 고려 | 작업 계획 수립 시 "이 작업에 서브에이전트 병렬·fan-out 실익이 있나? 은수님이 오케스트레이션을 트리거했나?"를 점검 |

> [!IMPORTANT]
> **트리거 기반 오케스트레이션 정책** (은수님 2026-07-03, 전면 위임 정책 대체): **dynamic workflow(다노드 fan-out)** 는 은수님이 *"오케스트레이션·여러 페르소나·서브에이전트들로·여러 에이전트·병렬로·fan-out·워크플로우로"* 등 트리거어를 쓸 때 돌린다. 트리거가 없으면 오케스트레이터가 판단한다 — **간단한 일은 세션에서 직접** 처리하고, 광범위 탐색·독립 병렬·대용량 처리처럼 서브에이전트 실익이 명확할 때만 (단발/소수) 위임한다. "무조건 전량 위임"은 폐지 — 과위임·폭주를 막고 간단한 일의 지연·비용을 없앤다.

## 1.1 오케스트레이터가 직접 하는 일

트리거 기반 정책에서 오케스트레이터는 다음을 **직접** 수행한다(위임하지 않는다).

1. **대화 맥락 파악** — 사용자 요청·이전 대화 내용 이해
2. **위임 설계용 최소 조사** — 어떤 파일·심볼이 관련 있는지 훑어 위임 프롬프트를 자기완결적으로 작성하기 위한 조회
3. **오케스트레이션 관리 행위** — `git status`/`git log`, 작업 폴더·목록 조회, 커밋 등 작업 진행 관리
4. **fan-in 결과 합성** — 서브에이전트 결과를 받아 통합·보고
5. **트리거 없는 간단한 작업** — 판단상 서브에이전트 실익이 낮은 소규모 조회·수정·저술은 세션에서 직접 처리

작업 프로세스의 ①요구사항·⑤계획 설계 산출물 작성도 직접(§6 표).

> [!CAUTION]
> 반대로, 은수님이 오케스트레이션 트리거어를 쓰거나 작업이 광범위 탐색·다중 페르소나·독립 병렬로 이득이 명확하면 **미루지 말고 dynamic workflow/서브에이전트를 쓴다**. 트리거를 무시한 과소 위임도 안티패턴이다(§5).

## 2. 활용이 적합한 작업 패턴

### 2.1 작업 패턴별 매핑

| 작업 패턴 | 활용 |
|---|---|
| 광범위 코드베이스 탐색 (3+ 검색) | `Explore` 위임 |
| 트리거 없는 간단한 조회·수정·저술 | 오케스트레이터 직접 (§1.1) |
| 오케스트레이션 트리거어 / 다중 페르소나·독립 병렬로 실익 명확 | **dynamic workflow** (`Workflow`) |
| 다중 가설 분석 (root cause 3개+) | 가설별로 `general-purpose` 병렬 |
| 독립적인 멀티 파일 변경 | 파일군별 분리 가능하면 분기 위임 |
| 대용량 빌드/테스트 로그 분석 | `general-purpose`에 로그 경로 + 분석 지시 |
| 외부 정보 조사 (웹·문서) | `general-purpose` |
| 설계·계획 수립 | `Plan` (구현 시작 전 별도 계획 검토 받을 때) |
| 단순 반복 작업 (frontmatter 일괄 추가 등) | `general-purpose`에 명확한 지시 위임 |

### 2.2 병렬 호출

서로 독립적인 서브에이전트 호출은 병렬 처리한다. **Workflow 가용 시 `workflow()`에 병렬 노드로 정의**하고, 호출 불가 세션에서는 **한 응답에 multiple Agent 호출**로 폴백한다.

```
Workflow(우선): parallel([ agent({...}), agent({...}), agent({...}) ])
Agent(폴백): 한 응답에
  Agent(subagent_type=Explore, prompt=...)  ← LED 모듈 탐색
  Agent(subagent_type=Explore, prompt=...)  ← Touch 모듈 탐색
  Agent(subagent_type=general-purpose, ...) ← 빌드 로그 분석
```

> [!TIP]
> 의존성이 있는 작업(앞 결과를 다음 입력에 사용)은 순차로. 의존성 없으면 **무조건 병렬**.

### 2.3 fan-in 컨텍스트 예산

다수 노드를 병렬 기동한 결과를 메인으로 모을 때(fan-in) 컨텍스트가 폭발하지 않도록 통제한다.

- **노드 반환 상한**: 각 노드는 결론 위주 **최대 3줄(200자)** 구조화 반환 — (1) 핵심 결론, (2) 근거 `파일경로:라인`, (3) 다음 노드·오케스트레이터용 핸드오프 1줄. raw 로그·전체 인용·사고과정은 메인으로 전파 금지.
- **reducer 1단**: 노드 수가 많으면(가변·다수) 중간 집계 서브에이전트(reducer)를 한 단 더 두어 메인 유입량을 상수로 묶는다.
- **loop 상태 예외**: 반복(loop-until-dry) 노드는 잔여 큐·검증 결과를 담은 구조화 상태객체 반환을 허용한다(3줄 강제의 예외 — 상태 전달이 목적).
- **로그≠컨텍스트 이원화**: 노드 산출 원문은 `에이전트-로그/` 파일에 보존해도 좋다(메인 컨텍스트로 3줄만 올리는 것과 층위가 다르므로 fan-in 예산 위반이 아니다). 상세: [`로그 구조.md`](로그%20구조.md) §6.

> [!NOTE]
> 다단계 fan-out·검증 루프·반복을 구조적으로 엮는 **동적 오케스트레이션 4패턴**(parallel·pipeline·loop-until-dry·adversarial-verify)은 [`오케스트레이션.md`](오케스트레이션.md)에서 규정한다.

## 3. 서브에이전트 종류

| 종류 | 용도 | 도구 권한 |
|---|---|---|
| `Explore` | 읽기 전용 빠른 검색·코드 위치 파악 | 읽기·검색만 |
| `general-purpose` | 다단계 조사·실행·복합 작업 | 전부 |
| `Plan` | 구현 계획 설계 (코드 작성은 안 함) | 읽기·검색·계획 출력 |

> [!NOTE]
> 작업의 권한 범위에 맞춰 가장 좁은 서브에이전트를 선택한다 (불필요한 권한 부여 금지).

### 3.1 기본 모델·Effort

서브에이전트는 세션 모델(Opus 등)과 무관하게 `model: "sonnet"`(최신 Sonnet)으로 호출하고, **effort는 미지정(세션 effort 상속)** 한다 — `agent()`에 effort 인자를 넘기지 않는다. Sonnet 5는 **adaptive reasoning**이 내장돼 있어, 세션 effort를 **상한**으로 두고 각 단계 사고량을 **작업량에 맞춰 스스로 조절**한다. 은수님은 `/effort`로 그 상한을 전역 제어한다.

> [!CAUTION]
> **`effort: "max"` 고정 금지.** max로 상한을 못박으면 결정론적 작업(확정 스펙 저술·기계적 변환)에서도 천장이 너무 높아 과잉 생성·자체검토 루프로 토큰·시간이 폭주한다(**2026-07-03 폭주 사례**: 257줄 확정 지침을 max 단일 노드로 저술 → 파일 완성 후에도 transcript 379KB로 부풀며 미수렴 → 정지·직접 전환). effort는 미지정으로 두고 Sonnet의 adaptive reasoning에 맡긴다. 그리고 **확정 스펙을 옮기는 결정론적 대형 저술은 애초에 오케스트레이터가 직접** 쓴다(트리거 없는 간단 작업, §1.1·§6).

| 경로 | model | effort | 비고 |
|---|---|---|---|
| **Workflow** `agent({...})` | `"sonnet"` | **미지정(세션 상속)** | Sonnet adaptive reasoning이 상한 안에서 작업량 따라 자동 조절. `max` 고정 금지(위 CAUTION) |
| **Agent 도구** 다중 호출 (폴백) | `"sonnet"` | **지정 불가** (인자 부재) | 세션 effort 상속 |

> [!NOTE]
> `Agent` 도구 스키마엔 `effort` 인자가 없고, `Workflow`의 `agent()`도 이제 effort를 넘기지 않으므로 — 양쪽 다 **세션 effort를 상속**한다(Sonnet adaptive reasoning으로 자동 조절). 적용 모델·effort는 에이전트 로그에 `Sonnet · (세션 effort 상속)`으로 기재한다. (Workflow opt-in standing 승인: 은수님 2026-06-18 / effort 미지정·adaptive 전환: 은수님 2026-07-03.)
### 3.2 명명된 전문가 패널 (사용자 정의 에이전트)

빌트인 셋 외에, `~/.claude/agents/<이름>.md`(Windows: `C:\Users\EUNSU\.claude\agents\`)에
정의해 둔 **명명 에이전트**를 `subagent_type`으로 부를 수 있다. 정의 파일에는 페르소나·
심사 방법·산출 형식이 들어 있고, **맥락은 들어 있지 않다** — 대상은 호출할 때 준다.

#### 등록된 패널 (2026-08-20)

| 접두사 | 이름 | 무엇을 재는가 |
|---|---|---|
| `ui-` | `ui-aesthetics` | 정렬·리듬·여백·타이포 위계 (픽셀 계측) |
| | `ui-color` | WCAG 대비비·색맹 시뮬레이션·토큰 역할 배정 |
| | `ui-trend` | 동시대성 — 「몇 년도 물건으로 보이는가」 |
| `ux-` | `ux-flow` | 과업 완결성·정보구조·화면 사이 배선 |
| | `ux-safety` | 사용 오류 → 피해 사슬 (IEC 62366-1 관점) |

#### 호칭 호출 규칙

> 은수님이 **«ui 에이전트들에게 ~해 줘»** 처럼 **접두사를 복수로 지칭**하면,
> 그 접두사를 가진 에이전트 **전부**를 한 응답에서 병렬 기동한다. 이것은 §2.2 병렬
> 호출의 트리거어에 준한다 — 되묻지 말고 바로 fan-out 한다.

- **«ui 에이전트들» / «ui 쪽 전문가들»** → `ui-aesthetics` · `ui-color` · `ui-trend`
- **«ux 에이전트들»** → `ux-flow` · `ux-safety`
- **«전문가들» / «다 물어봐» / «패널»** → 다섯 전부
- **한 분야를 콕 집으면**(«색감만 봐 줘») 그 하나만. 복수 지칭이 아닐 때 넷을 더 부르는 것은 낭비다.

#### 패널을 쓸 때 반드시 지킬 것

1. **서로의 답을 주지 않는다.** 독립으로 보게 해야 겹치는 지적이 «구조적 결함의 신호»가
   된다. 순차로 돌려 앞의 결과를 보여 주면 뒤가 그것을 따라간다.
2. **각 노드에 「결과 전문을 `에이전트-로그/NN_<역할>.md` 에 직접 Write 하라」를 명시**하고,
   **메인에는 3줄(200자)만 반환**하게 한다 (§2.3 · 로그 구조 §6). 전문을 반환받아
   오케스트레이터가 옮겨 적는 방식은 **금지** — 컨텍스트가 폭발하고, 압축되면 원문이 영영
   사라진다. (**2026-08-20 위반 사례**: 5노드 심사에서 전문을 받아 컨텍스트에만 두었고
   에이전트-로그를 만들지 않았다. 은수님 지적으로 뒤늦게 복구.)
3. **`model: "sonnet"` 고정**(§3.1). 패널이라고 예외가 아니다.
4. **종합은 오케스트레이터가 한다.** 노드 답을 이어 붙이지 말고 아래 축으로 갈라 낸다.

#### 종합 형식

| 갈래 | 무엇 |
|---|---|
| **확인된 사실** | 지적 중 **소스·측정으로 검증한 것만.** 노드 말을 액면가로 옮기지 않는다 |
| **겹침** | 누가 무엇을 짚었는지 매트릭스. **여럿이 겹칠수록 취향이 아니라 구조의 문제** |
| **갈림** | 결론이 다른 것. 어느 쪽이 옳은지 단정하지 말고 **판단 근거를 나란히** 놓는다 |
| **결정 대기** | 은수님이 정해야 할 것 |

> [!TIP]
> **노드가 틀릴 수 있다.** 특히 자료(스크린샷·로그)에 흠이 있으면 그 흠을 근거로 삼은
> 판정이 나온다. 종합 전에 **핵심 지적은 직접 확인**하고, 확인 못 한 것은 그렇다고 적는다.


## 4. 좋은 프롬프트 작성

### 4.1 자기완결성

서브에이전트는 본 대화 컨텍스트를 **모른다.** 프롬프트에 다음을 반드시 담는다:

- 무엇을 하려는지(목적)
- 이미 알고 있는 사실·시도해본 것
- 출력 형식·길이
- 관련 파일 경로·심볼명 등 단서

### 4.2 짧은 응답 강제

- 회신 분량을 미리 제한 — "보고는 200자 이내"·"표 5행 이내" 등
- 구체적 산출물 형식 지정 — "각 가설별 ✅/⚠️/❌ 표시"

### 4.3 판단 위임

- "찾아라"보다 "판단해라" — 위임 프롬프트에 조사뿐 아니라 판단·결론까지 요구한다. 단일 lookup도 예외 없이 위임 대상이므로(§1.1) "직접이 더 빠르다"는 이유로 위임을 회피하지 않는다
- 서브에이전트의 가치는 **그 대신 생각해주는 것**

### 4.4 노드 위생 (폭주 방지)

한 노드에 일을 몰아넣으면 자체검토·재시도 루프로 토큰·시간이 폭주한다(2026-07-03 사례, §3.1 CAUTION).

- **저술 ≠ 검증 — 분리한다.** "파일 저술 + 자체검증 + 외부 검증"을 한 노드에 몰아넣지 않는다. 저술 노드와 검증 노드를 나눈다(검증은 [`오케스트레이션.md §3`](오케스트레이션.md) 검증 루프).
- **불안정·재연결 중 MCP 의존 배제.** 검증 도구(예: Mermaid MCP)가 flaky하면 노드가 재시도 루프에 빠진다 — 안정화 후 별도 단계에서 검증한다.
- **노드는 단일 명확 산출물 + 범위 상한.** "무엇을 어디에 쓰고 끝"을 프롬프트에 못박아 무한 확장을 막는다.
- 감시·서킷브레이커(장시간 미수렴 노드 정지): [`오케스트레이션.md §7`](오케스트레이션.md).

## 5. 안티패턴

| 안티패턴 | 문제 | 대안 |
|---|---|---|
| 같은 검색을 본인이 다시 검증 | 중복 비용·신뢰 부족 | 결과 신뢰. 의심되면 더 구체적인 후속 질문 |
| 좁은 명령형 프롬프트 | 서브에이전트가 맥락 부족으로 부실 답변 | 자기완결 프롬프트 (§4.1) |
| 결과 무시·재검색 | 컨텍스트 낭비 | 결과를 받아 그대로 다음 단계에 사용 |
| 중복 병렬 호출 (같은 작업 분할 X) | 결과 일관성 손상 | 한 작업은 한 서브에이전트에 |
| **과소 위임** — 오케스트레이션 트리거어가 있거나 광범위 탐색·독립 병렬 실익이 명확한데 직접 처리 | 병렬·fan-out 기회 손실, 메인 컨텍스트 폭발 | 트리거·실익 시 dynamic workflow/서브에이전트 사용 (§1 IMPORTANT) |
| **과잉 위임** — 트리거·실익 없는 간단 작업까지 전량 위임 | 오버헤드·지연·토큰 낭비·폭주 위험 | 간단하면 세션에서 직접 (§1.1) |

> [!NOTE]
> **adversarial-verify 예외**: 위 "같은 검색을 본인이 다시 검증"·"결과 무시·재검색"의 재검증 금지는 **무계획적 중복 재실행**(같은 작업을 의심만으로 다시 돌리는 것)에 한정된다. **사전 설계된 독립 검증 노드**가 다른 에이전트의 산출물을 교차검증·반증하는 것(adversarial-verify·judge-panel, [`오케스트레이션.md §2`](오케스트레이션.md))은 금지 대상이 아니라 **권장**된다. 단계 ⑧ 구현 검증이 이에 해당한다.

## 6. 작업 진행 프로세스와의 통합

| 단계 | 서브에이전트 활용 |
|---|---|
| ① 요구사항 분석 | 사용자 의도·맥락 정리 — 오케스트레이터 직접 |
| ③ 현상태 분석 | 광범위 탐색·다중 가설 시 위임(트리거 또는 실익 판단) — grep·영향 범위 식별 |
| ⑤ 구현·처리 계획 | 오케스트레이터 직접. 복잡한 설계는 `Plan` 위임 가능 |
| ⑦ 구현·처리 | 독립 변경·반복 작업은 위임 가능(트리거어 시 dynamic workflow). **확정된 계획·스펙을 옮기는 대형 단일 저술은 오케스트레이터 직접**(폭주 방지 §3.1 CAUTION) |
| ②④⑥⑧ 검증 | 저술↔검증 노드 분리 — 독립 검증 노드가 산출물 교차검증(특히 ⑧ 구현 검증에서 adversarial-verify) |
